## Architecture

**Two interfaces, one engine.** `installer/detect.py`, `installer/docker_setup.py`, `installer/tiers.py`, `installer/services.py`, `installer/generate.py`, and `installer/post_install.py` are the engine: pure or near-pure functions that never prompt, confirm, or catch their own mistakes silently — they return plain result dicts (`{"success": bool, "error": str | None, ...}`) and let the caller decide what to do. `installer/cli.py` (Typer, Rich console output, plain prompts) and `installer/tui/` (Textual) are two independent front ends over that same engine — neither owns any business logic the other doesn't also have access to. When adding a capability, it belongs in the engine layer; a front end's job is only to gather input and call it.

**Entry points.** `./install` (bash) bootstraps `.venv` on first run and always `exec`s into `python -m installer "$@"` — no logic of its own beyond that bootstrap, mirrored exactly by `scripts/update.sh`/`scripts/backup.sh`/`scripts/restore.sh` (`exec .venv/bin/python -m installer update/backup/restore "$@"`, no bootstrap duplicated there since a stack can't exist without `./install` having already run at least once). `installer/__main__.py` and the `vulcan` console script (`pyproject.toml`'s `[project.scripts]`) both point at `installer.cli:app`. `installer/cli.py`'s `main()` is a `@app.callback(invoke_without_command=True)`, not a lone `@app.command()` — required because both `./install` (zero args) and `./install --tier medium --non-interactive --yes` need to work with no subcommand name, while `vulcan version`/`vulcan update`/`vulcan backup`/`vulcan restore` still need to work as real subcommands alongside it. `main()` decides interactive vs. scripted vs. TUI: `--non-interactive` always goes to `run_install()`; otherwise `--plain` goes to `run_install()` too, and the default (no flags) launches the TUI (`from installer.tui import run_tui` — imported lazily inside the branch, not at module top, so `vulcan version`/`--non-interactive` runs don't pay Textual's import cost).

**Detection (`detect.py`).** `detect_system(disk_path="/")` assembles a `SystemInfo` dataclass from `detect_cpu()`/`detect_memory()`/`detect_disk()`/`detect_gpu()`/`detect_docker()`/`detect_os()` — all read-only, all catching their own failure modes (missing tool, unreadable file) and returning `None`/`False`/a zero value rather than raising, since "not present" isn't an error here. **The disk-timing problem**: `detect_system()`'s default `disk_path="/"` only exists to drive an initial, approximate tier recommendation before the user's real media path is known: every real call site (`cli.py`'s `_gather_generation_config()`, the TUI's `MediaPathScreen`) re-runs `detect_disk(media_path)` against the *real* chosen path once it exists and overwrites `SystemInfo.disk_free_gb`/`disk_path_checked` before computing a recommendation that actually means something. `detect_render_group_gid()` (gid of the host's `render` group, `video` as fallback) exists specifically for AMD/Intel GPU passthrough — see Generation below.

**Docker bootstrap (`docker_setup.py` + `shell.py`).** `install_plan_for(os_id)` maps a distro to an install method — `get.docker.com` (ubuntu/debian/raspbian/fedora) or `pacman` (arch), `None` for anything else (caller shows manual-install instructions and stops). `run_ok()` (quiet, `capture_output=True`) is for status checks; `run_privileged()` (no output capture — sudo prompts and install-script progress need the real terminal) prefixes `sudo` only when not already root. **The group-membership gotcha**: a process's group list doesn't refresh mid-run after `usermod -aG docker <user>` — `run_docker_command(..., use_group_workaround=True)` routes through `sg docker -c "<cmd>"` (reads group membership fresh from the system, no relogin needed) for exactly the run that just added the group, falling back to `sudo` if `sg` isn't present. Both `cli.py` and the TUI track a `group_just_added` flag through the whole session for this reason.

**aarch64/ARM readiness audit — a static audit, explicitly not real-hardware verification, and this project is deliberately honest about that distinction rather than quietly upgrading its own confidence.** No ARM hardware exists in this environment, so this was scoped (with the user's explicit sign-off on the approach) to what can be genuinely checked without it, rather than pretending a manifest check is the same as a real run. What was actually confirmed, not assumed: (1) every one of the 16 Docker images `docker-compose.yml.j2` can reference has a real, published `linux/arm64` manifest — checked with `docker manifest inspect <image>` against the real registries (Docker Hub, `lscr.io`, `ghcr.io`), not read off each project's README. (2) `docker_setup.py`'s `DOCKER_SCRIPT_DISTROS` already included `"raspbian"` — the most common ARM homelab distro — before any of this ARM-specific work started; the `get.docker.com` script and Arch's `pacman -S docker` both auto-detect the host's real architecture internally, so neither of Vulcan's two install paths needed a code change to support aarch64. (3) `psutil` (the only compiled/native dependency in `pyproject.toml`) ships `manylinux_aarch64` wheels — no dependency blocks an aarch64 install. Two real, honest gaps found by reading the code, left as genuine open gaps rather than papered over: `detect_cpu()`'s `cpu_model` parsing looks for a `"model name"` line in `/proc/cpuinfo`, the x86 convention — real ARM64 Linux typically exposes `CPU implementer`/`CPU part` fields instead, so `cpu_model` will likely come back `None` ("unknown" in the CLI's own summary) on real ARM hardware; not a crash, since the function already treats a missing field as "not present" by design, but a real display gap worth knowing about going in. `detect_gpu()` only recognizes NVIDIA/AMD/Intel-branded GPUs (`nvidia-smi`/`rocm-smi`/an `lspci` string match) — hardware transcoding was designed around x86-style discrete/integrated GPUs, and typical ARM SBC hardware (e.g. a Raspberry Pi's VideoCore/V4L2 stack) was never in that scope; `detect_gpu()` returns `None` there through the same graceful "not present" path any undetected GPU already takes, so Jellyfin just runs software-only transcoding, not a crash or a silently wrong claim. **What this audit does not claim**: that Vulcan's install flow, the pulled images, or a generated stack actually run correctly end-to-end on real ARM hardware — that remains the one genuinely open, unverified gap, since a manifest existing and an install script detecting the right architecture are real, checkable facts, but neither is the same thing as a real run.

**Tier scoring (`tiers.py`).** `TIERS: dict[str, TierDefinition]` (light/medium/heavy) is the single source of truth for both scoring and service composition — `_MEDIUM_SERVICES = _LIGHT_SERVICES + [...]`, `_HEAVY_SERVICES = _MEDIUM_SERVICES + [...]`, so `TIERS["heavy"].services` is already the flat union of all three tiers' services (17 total) — exposed as `ALL_SERVICES` for anything that needs "every known service" (custom mode's picker) without re-deriving that union itself. `recommend_tier(system_info)` checks heavy→medium→light and returns the *first* tier where cores **and** RAM **and** disk all clear the threshold — deliberately no partial credit or averaging; a single weak resource caps the whole recommendation, matching "sized to what the machine can actually handle" literally. Below even Light's minimums, it still recommends Light (`meets_minimum=False` flags it) rather than nothing — blocking outright would fight the fact that every recommendation is overridable anyway. `Recommendation.explanation` lists every resource actually short of the next tier up (not a single guessed bottleneck), computed via `_shortfalls()`.

**Resource limits (`services.py`).** A 3x3 matrix, not per-service-per-tier hand-tuning: each of the 19 services declares one `RESOURCE_PROFILES[key]` ("light"/"standard"/"heavy" — its own typical footprint, independent of tier), and `RESOURCE_LIMITS[tier][profile] -> (cpus, memory)` scales all profiles together per tier. `resource_limits_for(tier_name)` returns `{key: {"cpus", "memory"}}` for every service. **Verified against real Docker Compose v2 (v5.3.1)**: `deploy.resources.limits` genuinely applies outside Swarm mode — confirmed via a throwaway container and `docker inspect` showing the exact `NanoCpus`/`Memory` requested.

**Generation (`generate.py`).** `GenerationConfig` (tier, media_path, puid, pgid, timezone, enabled_optional, gpu_vendor, custom_services, domain) is what every front end eventually builds and hands to `write_stack()`. `enabled_service_keys(config)` returns `config.custom_services` verbatim when set (custom mode — see below), else the tier's non-optional services plus whatever's in `enabled_optional`. Templates (`templates/docker-compose.yml.j2`, `templates/env.j2`) are one literal, Jinja-guarded block per known service — not a fully generic data-driven renderer, deliberately: with 17 known services each carrying small real quirks, this reads like a normal hand-written compose file instead of an abstraction built for services that don't exist yet.

- **Hardlink-safe volumes** (TRaSH Guides convention): services that both download and import media (qBittorrent, SABnzbd, Radarr, Sonarr, Lidarr) mount the *entire* `${MEDIA_PATH}` at `/data` read-write, not separate `downloads`/`media` mounts — so a hardlink from `/data/downloads/...` to `/data/media/...` stays on one filesystem. Jellyfin/Bazarr only need `${MEDIA_PATH}/media`, read-only.
- **GPU passthrough**: AMD/Intel share one path — `/dev/dri` device mapping plus `group_add` with the host's real `render` group gid (**PUID/PGID alone doesn't grant device access** — confirmed by starting a real container and checking `/dev/dri` visibility and group membership inside it). NVIDIA uses the standard `deploy.resources.reservations.devices` block, nested as a **sibling of `limits` under the same `deploy.resources` key**, not a second top-level `deploy:` block (a real duplicate-key conflict caught by reasoning about the YAML shape before writing it, not by trial and error) — flagged as not hardware-verified in this session (no NVIDIA GPU on the dev machine), schema-validity only.
- **Gluetun**: qBittorrent reroutes via `network_mode: "service:gluetun"` instead of its own ports when enabled. `write_stack()` never invents real VPN credentials — placeholders (`changeme`) with `# TODO` comments, flagged via a returned warning. `optional=True` in `_LIGHT_SERVICES` (moved up from `_MEDIUM_SERVICES` — see the default-on entry below), tier-agnostic like SABnzbd/Recyclarr/Decluttarr.
- **SABnzbd**: `optional=True` in `_LIGHT_SERVICES` (available — and its own tier-agnostic confirm question shown — starting at Light, unlike Gluetun's Medium-only gating or GPU's Heavy/Jellyfin gating), purely additive alongside qBittorrent rather than a replacement for it. Its LSIO image's web UI listens on container port 8080, the same internal port qBittorrent uses — mapped to host `8081` instead of `8080` to avoid the collision, confirmed against LinuxServer's real documented image (`lscr.io/linuxserver/sabnzbd:latest`) before designing around it. Deliberately not routed through Gluetun — Usenet is a direct SSL connection to a paid provider, not peer-to-peer, so it doesn't carry BitTorrent's IP-exposure motivation for VPN-routing. `write_stack()` returns a warning that real Usenet provider credentials still need to be entered through SABnzbd's own first-run setup wizard, the same "never invent a secret, just flag it" treatment Gluetun's VPN credentials get. **Verified against a real container**: generated a real Light-tier stack with SABnzbd enabled into a scratch directory, confirmed via `docker compose config` that qBittorrent and SABnzbd's ports don't collide (`8080` vs `8081`), then actually pulled and started the real `lscr.io/linuxserver/sabnzbd:latest` image — it came up clean (SABnzbd 5.0.4, no errors in its logs) and answered on host port 8081.
- **Recyclarr**: `optional=True` in `_LIGHT_SERVICES`, tier-agnostic like SABnzbd — it always has something real to sync against, since Radarr/Sonarr are non-optional in every tier. Two real deviations from every other service block, both confirmed against recyclarr.dev's real docs rather than assumed: (1) `ghcr.io/recyclarr/recyclarr:8` (major-version pin) — the upstream `:latest` tag **is no longer published**, so this is the one service block in the whole template that isn't `:latest`. (2) the container is rootless and takes a Compose-level `user: "${PUID}:${PGID}"` field instead of `PUID`/`PGID` environment variables the way every LSIO-family service does — no `PUID=`/`PGID=` lines in its `environment:` block at all. **Deliberately no Vulcan-authored `recyclarr.yml`**: the alternative (generating a config with hardcoded TRaSH Guides `trash_id` quality-profile references) was considered and rejected — those IDs are curated externally and can be restructured upstream, and Recyclarr's own `RECYCLARR_CREATE_CONFIG=true` env var already scaffolds a real starter config on first container start, which is a better answer than Vulcan hand-maintaining YAML sync content. `write_stack()`'s warning tells the user to edit the scaffolded `stack/config/recyclarr/recyclarr.yml` with real Radarr/Sonarr API keys afterward, pointing `base_url` at the exact container names/ports this stack already uses (`http://radarr:7878`, `http://sonarr:8989`) — the same "never invent a secret, flag it" treatment Gluetun/SABnzbd get, but for a credential embedded in a YAML file rather than `.env`. **Verified against a real container, and a real finding the warning text was rewritten around**: generated a real stack with Recyclarr enabled, confirmed via `docker compose config` that the `user:` field and pinned image tag render correctly, then actually pulled and started the real image and confirmed `RECYCLARR_CREATE_CONFIG=true` genuinely created a real `recyclarr.yml` under `stack/config/recyclarr/` on first start (not just per docs) — but its content was a `sonarr:` section only, with generic placeholders (`http://localhost:8989`, `YOUR_KEY_HERE`), not a `radarr:` section too and not Vulcan's actual container names. The warning explicitly says to add a `radarr:` section alongside the scaffolded `sonarr:` one, not just "edit the values" — confirmed necessary by reading the real generated file, not assumed from docs. Lidarr and Readarr integration were both checked and confirmed unsupported by Recyclarr (Radarr/Sonarr only) — not a gap, a real upstream limitation.

Regenerated a second time without a domain/Traefik and confirmed no routing labels render, same as every other conditionally-routed service.
- **State persistence**: `write_stack()` always also writes `stack/.vulcan-state.json` (tier, media_path, puid/pgid/timezone, enabled_optional, gpu_vendor, custom_services, generated_at) — `load_previous_state()` reads it back, tolerating a missing/corrupt file or unrecognized tier by returning `None` rather than raising. This is what makes re-running `./install` against an existing stack safe: every front end sources its prompt *defaults* from here (falling back to fresh detection only when there's no previous state), following the same precedence everywhere — **explicit flag/input > previous state > freshly-computed default**.
- **Secret preservation on regenerate**: `write_stack()` reads any existing `.env` *before* overwriting it and carries forward each of `VPN_SERVICE_PROVIDER`/`VPN_TYPE`/`WIREGUARD_PRIVATE_KEY` individually if it's not still the literal `"changeme"` placeholder — per-key, not all-or-nothing, so a user who's only filled in one of the three doesn't lose that partial progress on the next regenerate.
- **Custom mode**: `custom_services: set[str] | None` is a free pick across all 19 `ALL_SERVICES` regardless of which tier they're normally catalogued under — resource limits still scale from whichever tier is chosen (`config.tier`), not from each service's native tier. `enabled_optional` (Gluetun/SABnzbd/Recyclarr/Lidarr/Readarr/Traefik) becomes meaningless once `custom_services` is set — those are just regular entries in the free-form list, no separate toggle.
- **Real Traefik routing**: closes the long-tracked "bare skeleton, no routing labels, no domain input" gap. `domain: str | None` is only ever gathered when `"traefik"` is in `custom_services_selected` — a real, load-bearing fact found by reading the code, not assumed: **Traefik (and Lidarr) have no enable question anywhere in the normal tier flow at all**, `enabled_optional` never contains `"traefik"` outside custom mode, so custom mode's `ServiceSelectionScreen` (TUI) and the `--domain` flag/interactive prompt (CLI, right after the custom-services block resolves) are the only places a domain needs to exist. Every user-facing service (`jellyfin`, `radarr`, `sonarr`, `prowlarr`, `qbittorrent`, `sabnzbd`, `jellyseerr`, `bazarr`, `lidarr`, `readarr`, `homepage`, `uptime-kuma`) gets a `{% if 'traefik' in enabled and domain %}` guarded `labels:` block routing `<service>.<domain>` to its own **internal** container port (not the host-published one — matters for SABnzbd, whose host port is remapped to `8081` but Traefik talks to the container directly on its real `8080`). Deliberately skipped: `flaresolverr` (internal-only API), `gluetun` (not user-facing), `recyclarr`/`watchtower` (no web UI). TLS uses `tls=true` with no `certresolver` — **a real, documented Traefik behavior, not assumed**: this genuinely triggers Traefik's own auto-generated self-signed default certificate, zero external dependency, confirmed via research and then via a real `curl` showing `issuer: CN=TRAEFIK DEFAULT CERT`. Let's Encrypt/ACME is deliberately out of scope — HTTP-01 needs a port-forwarded public domain and DNS-01 needs picking one specific DNS provider's API out of dozens of legitimate choices, the same "don't hardcode one external assumption" reasoning already applied to Recyclarr's config and Gluetun/SABnzbd's credentials. `qbittorrent`'s labels are skipped whenever `gluetun` is enabled — confirmed via real research that a container using `network_mode: "service:gluetun"` has no network identity of its own for Traefik's Docker provider to discover, not solved (a real VPN-provider-dependent rabbit hole this environment can't verify), just correctly explained via a `write_stack()` warning instead of generating labels that would silently never route. Traefik's own command gains an HTTP→HTTPS redirect gated on `domain` alone, so its output is byte-identical to before this slice whenever no domain is configured. **Verified against real containers, not just `docker compose config`**: started a real Traefik + Radarr pair with a real domain, confirmed via `curl -k -H "Host: radarr.<domain>" https://localhost/` that Traefik genuinely discovered the label-based router and proxied a real `200` from Radarr, that an unmatched Host header correctly got a `404` (rule matching actually works, not just present), that plain HTTP redirected `301` to HTTPS, and separately confirmed via `docker compose config` that a Gluetun+qBittorrent+Traefik+domain combination renders qBittorrent with zero `labels:` while every other enabled service still gets them.

**Homepage dashboard pre-seeding.** Closes the last of the two deferred "polish" items from the original brainstorm (TUI back-navigation was the other). `render_homepage_services(config, host_ip)` (`generate.py`) builds `stack/config/homepage/services.yaml` directly as Python data via `yaml.safe_dump()` — not a `.j2` template, deliberately, since the content is a fully dynamic nested structure with computed URLs rather than mostly-static text with a few substitutions. Two real facts confirmed before designing, not assumed: `services.yaml` alone is sufficient (no `settings.yaml` required, per gethomepage.dev's real docs), and the bundled Dashboard Icons convention is exactly `<key>.png` — checked against the real CDN for all ten candidate services, every one resolves, so each service's own existing `tiers.py` key doubles as its icon filename with zero mapping table. `_HOMEPAGE_GROUPS` sorts the same web-facing service set Traefik's labels target (minus Homepage itself) into four real-homelab-convention groups (Media / Media Management / Downloads / Monitoring). *(Update: now backed by a real shared constant, `WEB_FACING_SERVICES` — see the entry below the Maintainerr section for the follow-up that closed this gap.)* `href` prefers `https://<key>.<domain>` when Traefik+domain are active (the already-correct routed URL), else `http://<host_ip or "localhost">:<port>` using each service's **host-published** port — the opposite convention from Traefik's labels (which use the container-internal port), and it matters for SABnzbd specifically (`8081` here, not `8080`). New `detect_host_ip()` (`detect.py`) supplies that default via a UDP "connect" to a public address — sends no real packets, just asks the kernel's routing table which local address it would use, a well-established technique confirmed working for real on this machine (`192.168.1.100`), not assumed. **A real distinction from the Traefik/Gluetun exclusion that looked identical at first but isn't**: Traefik can't route qBittorrent through Gluetun's shared network namespace because Docker's *service discovery* can't resolve a container with no network identity of its own — but a plain static `href` needs no discovery, and qBittorrent genuinely *is* reachable at `http://<host>:8080` when sharing Gluetun's namespace, since Gluetun's own port mapping exposes whatever's actually listening there. Re-derived from how `network_mode: service:` actually works rather than copying the Traefik exclusion without checking it still applied — it doesn't, so qBittorrent gets a real working tile either way. **`write_stack()` never overwrites an existing `services.yaml`** — only writes it (and only then adds the one-time "pre-seeded" warning) if the file doesn't already exist, the same "never invent a secret, never clobber a real edit" principle VPN-secret preservation already established, arguably more likely to matter here since editing a dashboard after first boot is an expected, common thing to do. **Verified against a real container**: generated a real stack (Homepage + several web-facing services + a real Traefik domain), pulled and started the real `homepage` image, confirmed it came up `healthy` with no config-parse errors in its logs, and confirmed via its own real `/api/services` endpoint that every pre-seeded group/service/href/icon actually round-tripped through the running app exactly as generated — not just that the YAML looked right on paper. Separately confirmed the no-overwrite behavior for real: hand-edited the generated file, regenerated the stack, confirmed the edit survived and no misleading "pre-seeded" warning fired the second time.

**Port-conflict diagnostics — a real user report from an actual dry-run install, not a hypothetical.** `check_ports_available()` already refused cleanly on a conflict, but only ever named a bare port number - the user's real incident (a start refused on port 8080) had no way to tell them it was *their own* orphaned containers from a stack deleted outside `vulcan uninstall`, so they resorted to a full manual Docker wipe to recover. New `identify_port_owner(port, own_project_name=None)` in `preflight.py` diagnoses what's actually holding a conflicting port before suggesting a fix, using only Docker (this project's one hard dependency already) - no new tool requirement like `lsof`/`ss`.

**A real, verified-by-testing correction to the obvious approach: `docker ps --filter publish=<port>` looked like the right tool and isn't.** Confirmed empirically, not assumed - it matched a container against a completely unrelated host port during testing (a real, reproducible false positive), and separately, a container's own container-side port needs `expose=` instead of `publish=` to match at all. Parsing the real `{{.Ports}}` field text directly (confirmed reliable against a real bound container - `0.0.0.0:PORT->CONTAINER_PORT/tcp`) is what's actually correct. `identify_port_owner()` distinguishes two real cases by comparing the found container's `com.docker.compose.project` label (the exact mechanism `stack_containers_exist()` already established for `vulcan uninstall`'s own orphan detection) against the current stack's own project name: **your own orphaned containers** (names the real fix - `vulcan uninstall`, then regenerate) versus **some other, unrelated container** (names it by container/image, no fix implied since Vulcan has no business touching it). If Docker doesn't recognize the port at all (a native, non-Docker service, or `docker ps` itself fails), this honestly returns `None` rather than guessing further - `format_port_conflicts()` (new, single source of truth shared by both the CLI and TUI rather than each building its own message) renders that case as "not identified as a Docker container - check for a native service."

**`backup_stack()` no longer archives live SQLite databases directly.** Follow-up to a "what do other homelab users get bitten by" discussion — every `*arr` app and Jellyfin itself store real state in SQLite, and the original implementation just `tar.add()`'d `config/` as-is with zero coordination with whatever's running, a real (if latent) risk of archiving a torn/mid-write database. `_is_sqlite_file(path)` detects real SQLite files generically by magic header (`b"SQLite format 3\x00"`, the stable file-format signature) rather than a hardcoded per-service filename table — the same "don't maintain a mapping that needs updating every time a service is added" reasoning already applied to Homepage's groups and Traefik's routed-service list. `backup_stack()` now stages `config/` into a `tempfile.TemporaryDirectory()` via `shutil.copytree(..., ignore=<skip real SQLite files>)`, then `_snapshot_sqlite_database()` writes a proper point-in-time copy of each real SQLite file into the staged tree using Python's stdlib `sqlite3.Connection.backup()` (opening the live file read-only via the `file:...?mode=ro` URI form, so this process never takes a write lock or creates a stray `-wal`/`-shm` file) before the staged directory gets tarred exactly as before — **zero new dependencies**, `sqlite3` and `tempfile` are both stdlib. A `sqlite3.Error` during snapshotting falls back to a plain `shutil.copy2()` of the live file rather than dropping it, with a warning naming the specific file. `restore_stack()` needed **no changes at all** — a snapshot is a normal, complete, valid SQLite file at the same relative archive path a raw copy would have used. **Verified against a real concurrent-write scenario before designing around it**: a background thread continuously inserting/committing into a real SQLite file while a separate read-only connection ran `.backup()` produced a snapshot with a genuine point-in-time row count, strictly consistent with the live count once the writer stopped — no torn row, no lock conflict, and the snapshot passed `PRAGMA integrity_check`. **Verified end-to-end against a real running container, not just a synthetic test file**: started a real `radarr` container, let it initialize its own genuine `config/radarr/radarr.db`, ran `vulcan backup` while the container was still running (the exact scenario this fix targets), and confirmed the archived database passed `PRAGMA integrity_check` and contained Radarr's real schema (`Movies`, `Config`, `NamingConfig` tables) — not a placeholder.

**Pre-pull mode (`vulcan pull`, "Pull Images Now" in the TUI).** Scoped answer to "can Vulcan work offline" — Vulcan actually assumes internet at several genuinely separate points (the Python venv bootstrap, Docker's own install script if missing, every generated stack's image pulls, and Recyclarr/Watchtower's inherently-online design), and this slice only closes one of them: making the image-pull step optional-in-advance, so a stack can be built at a desk with internet and started later with zero network access. `pull_stack(compose_path, env_path)` is `update_stack()`'s existing pull step, extracted rather than duplicated — `update_stack()` now calls it for its own first half, so there's exactly one place that knows how to pull a stack's images. `vulcan pull` is a new standalone subcommand, sibling to `update`/`backup`/`restore`: pulling touches nothing running and nothing on disk beyond Docker's own local image cache, so — per this project's existing "non-mutating actions need no confirmation" rule (already applied to `backup`) — it gets no `typer.confirm()` gate, unlike `update`. **Airgap mode (`--offline`/the `WelcomeScreen` checkbox, `vulcan export`/`vulcan import`).** Closes the two gaps pre-pull mode left open: a machine that needs Docker installed but has no internet at all (pre-pull assumes Docker's already present), and a machine that's *never* online, not just online-now-offline-later (pre-pull's `docker compose pull` still needs a live connection on the same machine it's run on). **Only one function in `docker_setup.py` actually needs internet**, confirmed by reading it, not assumed: `install_docker()` (the `get.docker.com` curl / `pacman -Sy` fetch). `start_docker_service()`/`add_user_to_docker_group()` are pure local `systemctl`/`usermod` calls; `ensure_compose_v2()`'s primary check (`docker compose version`) is local too — only its Arch-only fallback (`pacman -S docker-compose`) needs network, a narrow pre-existing edge case this slice doesn't chase down, documented here rather than silently left unmentioned. `vulcan export`/`vulcan import` join `update`/`pull`/`backup`/`restore` as CLI-only lifecycle commands (no TUI involvement, same as `backup`/`restore` already are) — moving already-pulled images to a machine that's never touched the network at all. **`docker compose config --images` and multi-image `docker save`/`docker load` were verified against real images before designing around them, not assumed**: `docker compose config --images` prints the fully-resolved image list (no need to parse Vulcan's own compose template as YAML); `docker save -o images.tar alpine:3.19 busybox:1.36` bundled both into one file, and after `docker rmi`-ing both, `docker load -i images.tar` restored them under the exact same tags and digests — `docker compose up -d` against the reloaded images came up immediately with zero pull activity. `export_images()` is the one place in this codebase that needs a *captured* subprocess call (`docker compose config --images`'s output has to be parsed) rather than the pass-through `run_docker_command()` every other Docker-mutating call uses — a plain `subprocess.run(..., capture_output=True, text=True)`, not routed through `run_docker_command()`, which deliberately never captures. Exports land in a new `exports/` directory (gitignored, added alongside `backups/`) as `vulcan-images-<timestamp>.tar`, kept separate from `backups/` since these are multi-hundred-MB-to-GB image blobs, not small KB config archives — `latest_export()` mirrors `latest_backup()`'s exact lexicographic-timestamp-sort safety. Neither command needs a `typer.confirm()` gate: `export` only reads already-local images into a new file, `import` only adds/overwrites local image tags — the same "touches nothing running" class as `pull`/`backup`, not `restore`'s genuinely destructive class. The Python function backing `vulcan import` can't be named `import` (reserved word) — `@app.command(name="import")` on `import_command()`, a trick this codebase hasn't needed anywhere else. **Verified end-to-end through the actual `vulcan` commands, not raw `docker` calls**: generated a real stack, ran `vulcan pull` then `vulcan export`, confirmed via `tar -xOf ... manifest.json` that the tarball's `RepoTags` genuinely matched `docker compose config --images`'s output, removed both images locally, ran `vulcan import` with no argument (confirming the `latest_export()` fallback picked the right file), confirmed via `docker images` both were back under the exact same digests, and confirmed `docker compose up -d` came up in under a second with zero pull activity.

**Read-only media-path redundancy detection (`detect_media_redundancy()`/`describe_media_redundancy()` in `detect.py`).** Follow-up to a discussion on whether Vulcan should manage RAID/partitioning itself — deliberately not: everything else Vulcan does is reversible (regenerate a compose file, restore a backup), while creating/modifying storage is genuinely destructive and belongs to mature, purpose-built tools (mdadm, ZFS, btrfs, TrueNAS/Unraid). This is the safe alternative: **report** whether `media_path` has any drive-level redundancy, the same read-only style as CPU/GPU detection, never suggest or perform a storage change. `findmnt -no SOURCE,FSTYPE,TARGET -T <path>` resolves any arbitrary path (not just a mountpoint) to its backing device/pool, filesystem, and real mountpoint — confirmed real on this machine. Branches by filesystem: an mdadm array (`device` starts with `/dev/md`) reads `/proc/mdstat` for that array's raid level (`raid1`/`4`/`5`/`6`/`10` = redundant, `raid0`/`linear` = not); btrfs runs `btrfs filesystem show <mountpoint>` and checks `Total devices N` (`N > 1` = redundant); ZFS resolves the pool name and runs `zpool status <pool>`, redundant if its config-tree output contains a `mirror`/`raidz` line; anything else (ext4/xfs/vfat directly on a plain device) is single-device, not redundant. A missing `btrfs`/`zpool` binary means "can't determine" (`redundant: None`), never a false "not redundant" — a real bug caught and fixed before shipping, not by testing, but by reading the branch structure: the original `elif filesystem == "btrfs" and shutil.which("btrfs")` combined check silently fell through to the plain-device `else` when the tool was missing, which would have wrongly reported "no redundancy" instead of "unknown." **A second real bug, this one only caught by running against a real filesystem**: `btrfs filesystem show` rejects an arbitrary path underneath its mountpoint (`ERROR: not a valid btrfs filesystem`) even though `findmnt -T` resolves that same path fine — the fix was passing `findmnt`'s own resolved `TARGET` (the real mountpoint) to `btrfs filesystem show`, not the raw `media_path` argument. Surfaced once, right when `detect_disk(media_path)` already runs: the TUI (`MediaPathScreen`) stores it as `self.app.media_redundancy` and `ReviewScreen` renders it in the summary (plus a plain-text warning line when not redundant, since that screen's summary is a single `Static`, not per-line Rich-tagged CLI output); the CLI (`_gather_generation_config()`) computes and prints it immediately, the same way the "Recommended tier" line already is — deliberately not threaded through `GenerationConfig`, since it's purely observational and doesn't affect what gets generated. **Honestly bounded verification**: the plain-device and single-device-btrfs branches are verified against this real machine's actual `/home` (confirmed `redundant: False`, `device_count: 1`) and through a real end-to-end CLI run (a `tmpfs`-backed media path correctly reported as non-redundant). The mdadm-active-array and ZFS-mirror branches are test-suite-verified only, against documented formats — this machine has `mdadm` installed but no spare devices and no passwordless sudo to safely build even a loop-device test array, and no `zfs`/`zpool` tooling at all. Same category of caveat this project already applies to NVIDIA GPU passthrough: shipped, clearly not hardware-verified yet, not claimed as more solid than it is.

**`restore_stack(backup_path, compose_path, env_path, stack_dir)` is the reverse of `backup_stack()` — and the first genuinely destructive local-file operation in the project.** `latest_backup(backup_dir)` finds the most recent `vulcan-backup-*.tar.gz` by a plain lexicographic sort — safe only because `backup_stack()`'s own timestamp format (`%Y%m%dT%H%M%SZ`) already sorts correctly as a string, no datetime parsing needed. Two real details, not assumed: (1) extraction always passes `filter="data"` to `tarfile.extractall()` — the path-traversal-safe mode from PEP 706, confirmed via real research to be backported to every Python version this project supports (3.11/3.12), not just 3.12+, so no version branching was needed to use it unconditionally. (2) if a compose file already exists at the target, `restore_stack()` runs `docker compose down` against **that pre-restore file** before extracting anything — deliberately that ordering and not the reverse, since after extraction the compose file becomes the restored version, which might not even reference the same services the old one had running; stopping first avoids a container racing with its own config directory being overwritten out from under it. `restore_stack()` never touches `stack/.vulcan-state.json` — `backup_stack()` never archived it either, so there's nothing to restore there; symmetric by construction, not an oversight. **A real bug caught only by testing against a real drifted stack, not by the mocked test suite**: `tarfile.extractall()` only ever adds or overwrites members present in the archive — it never deletes files already on disk that the archive doesn't mention. The first real verification pass restored an old `docker-compose.yml`/`.env` correctly but left a stray file (added to `config/prowlarr/` after the backup was taken) sitting there untouched, silently defeating what "restore" is supposed to mean. Fixed by having `restore_stack()` `shutil.rmtree()` the existing `config/` directory before extracting — re-verified against the same real scenario (a real container running, a real backup, a real stray file added afterward) and confirmed the stray file is now genuinely gone post-restore, not just that extraction "succeeded."

**Both the down-before-extract ordering and the stray-file cleanup have been verified against a real running container**, not just mocked: started a real `prowlarr` container from a real generated stack, took a real backup, drifted both the compose file and a config file (including adding a file with no archive counterpart), then ran `restore_stack()` for real — confirmed via `docker ps` that the container was genuinely stopped/removed by the `down` step before any file touched disk, confirmed the restored `docker-compose.yml`/`config/prowlarr/settings` matched the backup exactly, confirmed the stray file was gone, and confirmed `docker compose up -d` against the restored stack came back up cleanly afterward.

**`vulcan uninstall` - the reverse of a plain install.** Added specifically so the CLI/TUI install flow can be repeatedly tested from a genuinely clean slate, without hand-deleting containers and directories between runs. `uninstall_stack()` (`installer/post_install.py`) reuses `restore_stack()`'s exact "stop first, only if a compose file exists" shape (`if Path(compose_path).exists(): run_docker_command([..., "down"])`, a clean error and nothing deleted if that fails) rather than reinventing it, then `shutil.rmtree(stack_dir)`. **Confirmed by reading `templates/docker-compose.yml.j2`, not assumed, that this is a complete wipe**: every service mounts `./config/<key>` as a bind mount into `stack/config/` — no top-level `volumes:` block exists anywhere in the template, so there's no separate named-volume cleanup needed; deleting `stack/` after `down` removes containers, network, and all app state in one pass. `config.media_path` (the actual media library) lives outside `stack/` entirely and is never touched, the same "Vulcan never creates or modifies storage itself" principle already established for read-only redundancy detection. `backups/`/`exports/` are left alone by default too — they're archives the user explicitly asked Vulcan to create, not part of "the install," so uninstalling shouldn't silently take them with it; a `--purge-artifacts` flag opts into deleting those too, for the "wipe genuinely everything, including old test backups" case. Same `--non-interactive`/`--yes` pair and default-deny `typer.confirm()` gate every other mutating lifecycle command already uses, with the confirm text stating explicitly what is and isn't touched. **Verified against real infrastructure, and it surfaced a real, pre-existing mess unrelated to this feature**: several containers from an earlier verification pass (`jellyfin`/`sonarr`/`radarr`/`prowlarr`) were found still running with no `stack/` directory behind them at all — traced to an earlier stray-directory cleanup that deleted `stack/` directly without running `docker compose down` first, never through any code path this project ships; cleared manually before testing, since a real `vulcan uninstall` run is the only path that removes `stack/` at all and it always stops containers first. **`uninstall_stack()` gained a real permission-handling fallback, found while verifying the auth-layer slice below, not anticipated when `uninstall` itself was built.** Authelia's official image (unlike every LinuxServer.io image in this stack) runs as its own internal root user rather than taking `PUID`/`PGID` - its runtime-created files (`db.sqlite3`, `notification.txt`, `configuration.yml` once written) end up root-owned, and a plain `shutil.rmtree(stack_dir)` genuinely raised `PermissionError` against a real Authelia container's real files, not a hypothetical. `_remove_stack_dir()` now catches that specific exception and falls back to emptying the directory from inside a throwaway `alpine` container (`docker run --rm -v <stack_dir>:/target alpine sh -c "rm -rf /target/*"`) before removing the now-empty tree normally - the exact same real technique this project's own history already used once before to clean up stray root-owned test state by hand, now automated. **Port-conflict override — step two of the three-part port-conflict plan, turning the diagnosis (shipped earlier) into an actual fix instead of a dead end.** `check_ports_available()` already named a real cause; the only thing this project ever did with that was print it and refuse. `preflight.py` gained two structured signals to act on it: `check_ports_available()`'s return dict now also carries `port_services` (conflicting host port → the `GenerationConfig.port_overrides` key that actually controls it, parsed from the already-written compose file's own service names) and `own_orphan` (a bool per conflicting port, from a new `port_owner_is_own_orphan()` sharing `identify_port_owner()`'s exact same real `docker ps` lookup via a new private `_find_container_on_port()`, so the two can never disagree about what's holding a port). **Auto-cleanup needed a narrower operation than `uninstall_stack()`, not a call to it.** The "own orphaned containers" case means containers from a *previous* deployment are still holding a port while the *current* run is mid-generate, about to start the fresh `stack/` it just wrote — `uninstall_stack()`'s unconditional `_remove_stack_dir()` would delete that same freshly-written compose file out from under the run trying to use it. **CLI (`_resolve_port_conflicts()`, new in `cli.py`).** Replaces the old hard refusal in `_generate_and_maybe_start()`'s start path: loops (fixing one conflict can surface another, e.g. a typed port colliding with a second still-conflicting service) over `check_ports_available()` → offer a fix per conflicting port → `write_stack()` again → re-check for real, until clean or the user gives up. A typed port is validated against `resolve_ports(config).values()` before being accepted (rejects a self-inflicted collision with another of the stack's own services - `_port_in_use()`'s real socket-bind check can't catch two not-yet-running services claiming the same port in one compose file, since neither is actually bound yet). `non_interactive` mode skips the whole loop and keeps the original one-shot refusal - there's no one to answer a prompt. **A real bug, found only by reproducing the actual orphan scenario against real Docker, not by any mocked test**: the first version asked once per *conflicting port*, but `remove_orphaned_containers()` tears down the whole labeled project in one call - a real 5-port conflict from one leftover stack meant the first confirm genuinely fixed everything and the next four just re-asked to clean up containers already gone (`docker compose` logged a harmless but confusing "No resource found to remove"). **Back navigation.** Every screen except `WelcomeScreen` (nothing before it) has a `Button("Back", id="back")` calling `self.app.pop_screen()` — genuinely just `pop_screen()`, no manual "go to screen X" logic anywhere, confirmed correct by reading Textual 8.2.8's actual `App.pop_screen()`/`_replace_screen()` source rather than assumed: popping reveals whatever is *really* beneath on the stack (so `ReviewScreen`'s "Back" correctly lands on `TierConfigScreen` or `ServiceSelectionScreen` depending on which one actually pushed it, no special-casing needed), the screen being left is genuinely unmounted, and the screen being revealed is **not** remounted — it gets `ScreenResume`, not `Mount`, so `on_mount()` never re-fires and every widget's value is exactly what the user left it as. Since every "Continue"/"Customize" handler already pushes a *fresh* screen instance rather than a cached one, there's never a stale-forward-screen problem: going back destroys the screen being left, and going forward again from any revealed screen always builds a new next screen from current app state. "Back" navigates the UI stack only — it does not undo a real mutation that already happened (Docker actually installed, `stack/docker-compose.yml` actually written, a container actually started), the same principle a browser back button already follows after a submitted form; going back and regenerating is exactly the same supported "re-run is safe" operation as running `./install` again against an existing stack. Two screens run a background `@work(thread=True)` worker whose completion callback touches `self.query_one(...)` — `DockerReadyScreen.run_fix()` and `ReviewScreen._run_start()` — popping mid-worker would let that callback fire against an already-removed screen, so Back is explicitly disabled for the duration of each (re-enabled after `DockerReadyScreen.fix_complete()`; no re-enable needed after `ReviewScreen`'s start, since it always ends in `self.app.exit(...)` either way). The CLI's `--plain` prompt flow stays forward-only — a separate, much bigger kind of feature (re-prompting logic), not attempted here.

**`detect_cpu()`'s ARM `cpu_model` gap, closed in code (2026-08-09) — but still genuinely unverified against real ARM hardware, and that distinction matters.** The aarch64 readiness audit above named this as a known display gap and stopped there, since real ARM hardware wasn't available to fix it against. Closed the code side properly instead of leaving it as a permanent caveat: `detect_cpu()` now falls back, in order, from x86's `"model name"` line to `/proc/device-tree/model` (the real board-model string virtually every ARM SBC's device tree exposes — Raspberry Pi's own docs point at this exact file — e.g. `"Raspberry Pi 4 Model B Rev 1.4"`), then to decoding `/proc/cpuinfo`'s own `CPU implementer`/`CPU part` fields for systems with no device tree at all (some ACPI-based ARM servers). The implementer/part table (`_ARM_IMPLEMENTERS`/`_ARM_CORTEX_PARTS`) uses real, documented ARM Ltd. MIDR_EL1 values — the same stable IDs the Linux kernel and `lscpu` itself decode against, not invented — deliberately not exhaustive, just the vendors/cores a real homelab box is likely to report. **Honestly still unverified against real ARM output, the same caveat this project already applies to NVIDIA GPU passthrough and the ZFS/mdadm redundancy branches**: every new test (`tests/test_detect.py`) mocks a real, documented `/proc/cpuinfo`/`/proc/device-tree/model` *format*, not a genuinely captured one from actual hardware — this machine has neither. Doesn't close the "real ARM64 hardware run" item in ROADMAP.md on its own; it closes the specific `cpu_model` display gap that item's own writeup called out as a known, separate limitation.

**Dashy — a second, independent dashboard option alongside Homepage, from a direct user request ("can I also have dashy as an alternative in case users prefer one or the other").** Deliberately not exclusive with Homepage: both are just ordinary optional toggles, so either, neither, or both can be enabled at once — no new "pick one" mechanism was needed, since nothing about this project's existing optional-service model assumes mutual exclusivity in the first place. A 22nd `ServiceDefinition`, tier-agnostic in `_LIGHT_SERVICES` like Homepage, but defaulting **off** (`dashy_default = False`) rather than Homepage's opt-out default — Dashy is being added *for people who specifically want it*, not promoted as broadly valuable the way Homepage was.

**Real image/config confirmed by fetching Dashy's own current files directly, not assumed from memory** — the exact same discipline this project already applied to Decluttarr (where an AI-summarized doc fetch invented a config tag that didn't exist) and to InvokeAI's sibling-project research. `lissy93/dashy:latest`, container port 8080 published at host 4000 (both confirmed via Dashy's own real `docker-compose.yml`), config file at `/app/user-data/conf.yml` with a real `pageInfo`/`appConfig`/`sections`-of-`items` schema (confirmed via Dashy's own real `user-data/conf.yml`) — genuinely different from Homepage's flat list-of-single-key-dict groups, so `render_dashy_config()` (`generate.py`) builds that shape directly rather than reusing `render_homepage_services()`'s output format. Confirmed via Dashy's own real docs that it has **no `HOMEPAGE_ALLOWED_HOSTS`-style host-validation requirement** — the exact gotcha that made Homepage completely unreachable on a fresh install until it was found and fixed (see above) — so no equivalent env var/warning was needed here.

**Reuses `_HOMEPAGE_GROUPS`/`_service_href()` rather than a second "which services get tiled" table.** `"dashy"` was added to `WEB_FACING_SERVICES` (so it gets the standard per-service Traefik routing label block, `templates/docker-compose.yml.j2`) and to `_HOMEPAGE_GROUPS`'s Infrastructure group — but only so *Homepage's own* tiles can include a Dashy entry when both are enabled, the same "routable like anything else, tiled by the other dashboard" treatment Traefik's own dashboard already gets. `render_dashy_config()` explicitly excludes `key == "dashy"` from its own generated sections (it must never tile itself), and `render_stack_summary()` excludes `"dashy"` from its generic per-group extend loop since it already gets its own explicit first-class line (mirroring Homepage's identical self-exclusion-by-omission, just spelled out explicitly here since Dashy - unlike Homepage - genuinely does appear as a member of `_HOMEPAGE_GROUPS`). Icons reuse the same public Dashboard Icons CDN (`cdn.jsdelivr.net/gh/walkxcode/dashboard-icons`) Homepage's own bundled icon set already comes from — confirmed by directly fetching several real icon URLs (including `dashy.png` itself) before relying on it, since Dashy's icon field takes a URL directly rather than resolving a bundled filename the way Homepage's does. `stack/config/dashy/conf.yml` is pre-seeded once and never overwritten on a regenerate, the same rule Homepage's `services.yaml`/Decluttarr's `config.yaml` already follow.

**A real, pre-existing `TierConfigScreen` layout bug, found only because a third checkbox row finally exposed it — not introduced by adding Dashy.** Direct widget-region inspection (not guesswork) showed `Checkbox` widgets inside the screen's `Horizontal` rows were rendering with height 3 while their parent `Horizontal` containers had no explicit height at all — rows silently overlapped, and clicking one checkbox could land on a sibling row's widget instead depending on exactly where its computed center fell. This was already true for the pre-existing SABnzbd/Recyclarr and Gluetun/GPU/Homepage rows (confirmed by inspecting the tree *before* this slice's changes too), it just happened to never matter until a new row's content occupied the exact overlap zone. Fixed with an explicit `.checkbox-row { height: 3; }` CSS class on all three checkbox rows. Fixing the overlap then pushed the screen's total content past the 24-row test viewport, so `TierConfigScreen`'s root container became a real `VerticalScroll` (same fix `ReviewScreen` already needed for the identical class of "content genuinely exceeds a fixed budget" problem) — with `can_focus=False` explicitly set, since `VerticalScroll` is focusable by default and would otherwise steal Textual's initial auto-focus away from the tier `RadioSet`, blanking the `#tier-error` composition-summary line the moment the screen mounts (confirmed by reproducing this exact regression before adding the fix). Tests reaching `#continue`/`#back`/`#customize` now `scroll_visible(animate=False)` before clicking, the same established pattern `ReviewScreen`'s own remap tests already use — a real user would need to scroll to reach the same off-screen content too.

**Verified via `docker compose config` against a real generated stack (Homepage + Dashy both enabled) — valid syntax, correct ports (3000/4000), correct Traefik labels when routed, no spurious `HOMEPAGE_ALLOWED_HOSTS`-style env var on Dashy's block.** Pulling and starting the real `lissy93/dashy:latest` image wasn't reachable in this environment (no live Docker daemon here) — stated honestly rather than claimed, the same limitation this project already notes for NVIDIA/AMD/Intel ComfyUI hardware in the sibling Anvil project.

## Testing conventions

- Mock at the **importing module's namespace**, not the source (`patch("installer.cli.detect_system", ...)`, not `patch("installer.detect.detect_system", ...)`) — standard `unittest.mock` behavior, but easy to get backwards.
- `tmp_path` (pytest fixture) for anything touching the real filesystem — never the real `stack/`/`backups/` directories relative to repo root, except inside the handful of deliberate real-infrastructure checks described below, which always clean up in a `finally`/explicit teardown.
- TUI tests (`test_tui.py`) use Textual's own `App.run_test()` (async context manager yielding a `Pilot`) — the documented, correct way to test a Textual app headlessly, not a custom harness. `pytest-asyncio` with `asyncio_mode = "auto"` (set in `pyproject.toml`) means `async def test_...` needs no per-test decorator. Each screen has a `_launch_at_<screen>_screen(...)` helper mirroring the real navigation path (or, where establishing that path is itself under test, a direct `app.push_screen(...)` shortcut) — **a real, non-obvious hazard already hit twice**: `VulcanApp.on_mount()` always pushes `WelcomeScreen` first, whose own background detection worker keeps running — a test that manually overrides `app.system_info` without first awaiting `app.workers.wait_for_complete()` loses the race and gets silently overwritten by real detected values moments later. Every `_launch_at_*` helper either awaits that completion or mocks `WelcomeScreen`'s own `detect_system`/`load_previous_state` before proceeding.
- **Real-infrastructure verification is load-bearing in this project's history, not optional polish.** Nearly every slice includes at least one check against this actual machine's real Docker, not just mocks: real containers started/stopped, real GPU passthrough confirmed via `docker exec` + `/dev/dri`, real generated compose files validated with `docker compose config`, a real `vulcan backup` archive inspected with `tarfile`. When adding a feature that touches Docker/the filesystem/real subprocess calls, a mocked test suite passing is necessary but not sufficient — look for what a real check would look like before considering the work done, and always clean up (`docker compose down`, `rm -rf` the scratch stack) immediately after.

## Code style

Heavy vertical spacing, matching the style established from the very first commit: each function argument on its own line in a multi-arg call, a blank line after `def ...():` before the body, blank lines between most statements. Very few docstrings (module-level explaining *why*, not function-level explaining *what*). New code should match whatever file it's editing.
