## Commands

```bash
# Setup
python -m venv .venv
source .venv/bin/activate

# Run the CLI

# Tests (pytest, config lives in [tool.pytest.ini_options] in pyproject.toml - no separate ini file)

python -m pytest tests/ --cov=installer --cov-report=term-missing   # 213 tests, ~98% coverage as of this writing

# scripts/update.sh and scripts/backup.sh are thin wrappers, not separate logic:
#   exec .venv/bin/python -m installer update / backup "$@"
```

No linter/formatter is configured - nothing enforces style automatically; see "Code style" below for the convention to match by hand. `.github/workflows/ci.yml` exists (mirrors `atlas`'s own CI structure - checkout, a 3.11/3.12 matrix, `pip install -e ".[dev]"`, then the full test suite) but **has never actually run** - there's still no GitHub remote configured for this repo (local-only development so far; **do not push** unless explicitly asked - see the git-push note under Project status). GitHub-hosted `ubuntu-latest` runners ship Docker + Compose v2 pre-installed with the runner user already in the `docker` group, which is why the workflow needs no extra setup for `test_real_detection_and_docker_ready_end_to_end` (the one deliberately-unmocked, real-Docker-dependent test) - but that expectation is unconfirmed against a real execution until this workflow's first run post-push.

## Architecture

**Two interfaces, one engine.** `installer/detect.py`, `installer/docker_setup.py`, `installer/tiers.py`, `installer/services.py`, `installer/generate.py`, and `installer/post_install.py` are the engine: pure or near-pure functions that never prompt, confirm, or catch their own mistakes silently - they return plain result dicts (`{"success": bool, "error": str | None, ...}`) and let the caller decide what to do. `installer/cli.py` (Typer, Rich console output, plain prompts) and `installer/tui/` (Textual) are two independent front ends over that same engine - neither owns any business logic the other doesn't also have access to. When adding a capability, it belongs in the engine layer; a front end's job is only to gather input and call it.

**Entry points.** `./install` (bash) bootstraps `.venv` on first run and always `exec`s into `python -m installer "$@"` - no logic of its own beyond that bootstrap, mirrored exactly by `scripts/update.sh`/`scripts/backup.sh` (`exec .venv/bin/python -m installer update/backup "$@"`, no bootstrap duplicated there since a stack can't exist without `./install` having already run at least once). `installer/__main__.py` and the `vulcan` console script (`pyproject.toml`'s `[project.scripts]`) both point at `installer.cli:app`. `installer/cli.py`'s `main()` is a `@app.callback(invoke_without_command=True)`, not a lone `@app.command()` - required because both `./install` (zero args) and `./install --tier medium --non-interactive --yes` need to work with no subcommand name, while `vulcan version`/`vulcan update`/`vulcan backup` still need to work as real subcommands alongside it. `main()` decides interactive vs. scripted vs. TUI: `--non-interactive` always goes to `run_install()`; otherwise `--plain` goes to `run_install()` too, and the default (no flags) launches the TUI (`from installer.tui import run_tui` - imported lazily inside the branch, not at module top, so `vulcan version`/`--non-interactive` runs don't pay Textual's import cost).

**Detection (`detect.py`).** `detect_system(disk_path="/")` assembles a `SystemInfo` dataclass from `detect_cpu()`/`detect_memory()`/`detect_disk()`/`detect_gpu()`/`detect_docker()`/`detect_os()` - all read-only, all catching their own failure modes (missing tool, unreadable file) and returning `None`/`False`/a zero value rather than raising, since "not present" isn't an error here. **The disk-timing problem**: `detect_system()`'s default `disk_path="/"` only exists to drive an initial, approximate tier recommendation before the user's real media path is known: every real call site (`cli.py`'s `_gather_generation_config()`, the TUI's `MediaPathScreen`) re-runs `detect_disk(media_path)` against the *real* chosen path once it exists and overwrites `SystemInfo.disk_free_gb`/`disk_path_checked` before computing a recommendation that actually means something. `detect_render_group_gid()` (gid of the host's `render` group, `video` as fallback) exists specifically for AMD/Intel GPU passthrough - see Generation below.

**Docker bootstrap (`docker_setup.py` + `shell.py`).** `install_plan_for(os_id)` maps a distro to an install method - `get.docker.com` (ubuntu/debian/raspbian/fedora) or `pacman` (arch), `None` for anything else (caller shows manual-install instructions and stops). `run_ok()` (quiet, `capture_output=True`) is for status checks; `run_privileged()` (no output capture - sudo prompts and install-script progress need the real terminal) prefixes `sudo` only when not already root. **The group-membership gotcha**: a process's group list doesn't refresh mid-run after `usermod -aG docker <user>` - `run_docker_command(..., use_group_workaround=True)` routes through `sg docker -c "<cmd>"` (reads group membership fresh from the system, no relogin needed) for exactly the run that just added the group, falling back to `sudo` if `sg` isn't present. Both `cli.py` and the TUI track a `group_just_added` flag through the whole session for this reason.

**Tier scoring (`tiers.py`).** `TIERS: dict[str, TierDefinition]` (light/medium/heavy) is the single source of truth for both scoring and service composition - `_MEDIUM_SERVICES = _LIGHT_SERVICES + [...]`, `_HEAVY_SERVICES = _MEDIUM_SERVICES + [...]`, so `TIERS["heavy"].services` is already the flat union of all three tiers' services (14 total) - exposed as `ALL_SERVICES` for anything that needs "every known service" (custom mode's picker) without re-deriving that union itself. `recommend_tier(system_info)` checks heavy→medium→light and returns the *first* tier where cores **and** RAM **and** disk all clear the threshold - deliberately no partial credit or averaging; a single weak resource caps the whole recommendation, matching "sized to what the machine can actually handle" literally. Below even Light's minimums, it still recommends Light (`meets_minimum=False` flags it) rather than nothing - blocking outright would fight the fact that every recommendation is overridable anyway. `Recommendation.explanation` lists every resource actually short of the next tier up (not a single guessed bottleneck), computed via `_shortfalls()`.

**Resource limits (`services.py`).** A 3x3 matrix, not per-service-per-tier hand-tuning: each of the 16 services declares one `RESOURCE_PROFILES[key]` ("light"/"standard"/"heavy" - its own typical footprint, independent of tier), and `RESOURCE_LIMITS[tier][profile] -> (cpus, memory)` scales all profiles together per tier. `resource_limits_for(tier_name)` returns `{key: {"cpus", "memory"}}` for every service. **Verified against real Docker Compose v2 (v5.3.1)**: `deploy.resources.limits` genuinely applies outside Swarm mode - confirmed via a throwaway container and `docker inspect` showing the exact `NanoCpus`/`Memory` requested.

**Generation (`generate.py`).** `GenerationConfig` (tier, media_path, puid, pgid, timezone, enabled_optional, gpu_vendor, custom_services) is what every front end eventually builds and hands to `write_stack()`. `enabled_service_keys(config)` returns `config.custom_services` verbatim when set (custom mode - see below), else the tier's non-optional services plus whatever's in `enabled_optional`. Templates (`templates/docker-compose.yml.j2`, `templates/env.j2`) are one literal, Jinja-guarded block per known service - not a fully generic data-driven renderer, deliberately: with 16 known services each carrying small real quirks, this reads like a normal hand-written compose file instead of an abstraction built for services that don't exist yet.

- **Hardlink-safe volumes** (TRaSH Guides convention): services that both download and import media (qBittorrent, SABnzbd, Radarr, Sonarr, Lidarr) mount the *entire* `${MEDIA_PATH}` at `/data` read-write, not separate `downloads`/`media` mounts - so a hardlink from `/data/downloads/...` to `/data/media/...` stays on one filesystem. Jellyfin/Bazarr only need `${MEDIA_PATH}/media`, read-only.
- **GPU passthrough**: AMD/Intel share one path - `/dev/dri` device mapping plus `group_add` with the host's real `render` group gid (**PUID/PGID alone doesn't grant device access** - confirmed by starting a real container and checking `/dev/dri` visibility and group membership inside it). NVIDIA uses the standard `deploy.resources.reservations.devices` block, nested as a **sibling of `limits` under the same `deploy.resources` key**, not a second top-level `deploy:` block (a real duplicate-key conflict caught by reasoning about the YAML shape before writing it, not by trial and error) - flagged as not hardware-verified in this session (no NVIDIA GPU on the dev machine), schema-validity only.
- **Gluetun**: qBittorrent reroutes via `network_mode: "service:gluetun"` instead of its own ports when enabled. `write_stack()` never invents real VPN credentials - placeholders (`changeme`) with `# TODO` comments, flagged via a returned warning.
- **SABnzbd**: `optional=True` in `_LIGHT_SERVICES` (available - and its own tier-agnostic confirm question shown - starting at Light, unlike Gluetun's Medium-only gating or GPU's Heavy/Jellyfin gating), purely additive alongside qBittorrent rather than a replacement for it. Its LSIO image's web UI listens on container port 8080, the same internal port qBittorrent uses - mapped to host `8081` instead of `8080` to avoid the collision, confirmed against LinuxServer's real documented image (`lscr.io/linuxserver/sabnzbd:latest`) before designing around it. Deliberately not routed through Gluetun - Usenet is a direct SSL connection to a paid provider, not peer-to-peer, so it doesn't carry BitTorrent's IP-exposure motivation for VPN-routing. `write_stack()` returns a warning that real Usenet provider credentials still need to be entered through SABnzbd's own first-run setup wizard, the same "never invent a secret, just flag it" treatment Gluetun's VPN credentials get. **Verified against a real container**: generated a real Light-tier stack with SABnzbd enabled into a scratch directory, confirmed via `docker compose config` that qBittorrent and SABnzbd's ports don't collide (`8080` vs `8081`), then actually pulled and started the real `lscr.io/linuxserver/sabnzbd:latest` image - it came up clean (SABnzbd 5.0.4, no errors in its logs) and answered on host port 8081.
- **Recyclarr**: `optional=True` in `_LIGHT_SERVICES`, tier-agnostic like SABnzbd - it always has something real to sync against, since Radarr/Sonarr are non-optional in every tier. Two real deviations from every other service block, both confirmed against recyclarr.dev's real docs rather than assumed: (1) `ghcr.io/recyclarr/recyclarr:8` (major-version pin) - the upstream `:latest` tag **is no longer published**, so this is the one service block in the whole template that isn't `:latest`. (2) the container is rootless and takes a Compose-level `user: "${PUID}:${PGID}"` field instead of `PUID`/`PGID` environment variables the way every LSIO-family service does - no `PUID=`/`PGID=` lines in its `environment:` block at all. **Deliberately no Vulcan-authored `recyclarr.yml`**: the alternative (generating a config with hardcoded TRaSH Guides `trash_id` quality-profile references) was considered and rejected - those IDs are curated externally and can be restructured upstream, and Recyclarr's own `RECYCLARR_CREATE_CONFIG=true` env var already scaffolds a real starter config on first container start, which is a better answer than Vulcan hand-maintaining YAML sync content. `write_stack()`'s warning tells the user to edit the scaffolded `stack/config/recyclarr/recyclarr.yml` with real Radarr/Sonarr API keys afterward, pointing `base_url` at the exact container names/ports this stack already uses (`http://radarr:7878`, `http://sonarr:8989`) - the same "never invent a secret, flag it" treatment Gluetun/SABnzbd get, but for a credential embedded in a YAML file rather than `.env`. **Verified against a real container, and a real finding the warning text was rewritten around**: generated a real stack with Recyclarr enabled, confirmed via `docker compose config` that the `user:` field and pinned image tag render correctly, then actually pulled and started the real image and confirmed `RECYCLARR_CREATE_CONFIG=true` genuinely created a real `recyclarr.yml` under `stack/config/recyclarr/` on first start (not just per docs) - but its content was a `sonarr:` section only, with generic placeholders (`http://localhost:8989`, `YOUR_KEY_HERE`), not a `radarr:` section too and not Vulcan's actual container names. The warning explicitly says to add a `radarr:` section alongside the scaffolded `sonarr:` one, not just "edit the values" - confirmed necessary by reading the real generated file, not assumed from docs. Lidarr integration was checked and confirmed unsupported by Recyclarr (Radarr/Sonarr only) - not a gap, a real upstream limitation.
- **State persistence**: `write_stack()` always also writes `stack/.vulcan-state.json` (tier, media_path, puid/pgid/timezone, enabled_optional, gpu_vendor, custom_services, generated_at) - `load_previous_state()` reads it back, tolerating a missing/corrupt file or unrecognized tier by returning `None` rather than raising. This is what makes re-running `./install` against an existing stack safe: every front end sources its prompt *defaults* from here (falling back to fresh detection only when there's no previous state), following the same precedence everywhere - **explicit flag/input > previous state > freshly-computed default**.
- **Secret preservation on regenerate**: `write_stack()` reads any existing `.env` *before* overwriting it and carries forward each of `VPN_SERVICE_PROVIDER`/`VPN_TYPE`/`WIREGUARD_PRIVATE_KEY` individually if it's not still the literal `"changeme"` placeholder - per-key, not all-or-nothing, so a user who's only filled in one of the three doesn't lose that partial progress on the next regenerate.
- **Custom mode**: `custom_services: set[str] | None` is a free pick across all 16 `ALL_SERVICES` regardless of which tier they're normally catalogued under - resource limits still scale from whichever tier is chosen (`config.tier`), not from each service's native tier. `enabled_optional` (Gluetun/SABnzbd/Recyclarr/Lidarr/Traefik) becomes meaningless once `custom_services` is set - those are just regular entries in the free-form list, no separate toggle.

**Post-install (`post_install.py`).** `update_stack(compose_path, env_path)` runs `docker compose pull` then `up -d` as two distinct steps (not `up -d --pull always`), so a pull failure reports distinctly from a recreate failure - the on-demand alternative to Heavy tier's Watchtower (which updates continuously on its own). `backup_stack(stack_dir, backup_dir)` tars `config/` + `docker-compose.yml` + `.env` into a timestamped `backups/<ts>.tar.gz` - **never** the media library itself, exactly the config/data separation the volume layout already exists to make possible - and always returns a warning that the archive may contain real credentials (`.env`), unconditionally, not conditional on Gluetun actually being configured.

**CLI wiring (`cli.py`).** `run_install()` → `_ensure_docker_ready()` (mirrors `docker_setup.py`'s three readiness gaps: not-installed / not-running / no-compose-v2, each behind its own `typer.confirm()`) → `_gather_generation_config()` (media path → real `detect_disk()` → `recommend_tier()` display → tier choice → custom-mode question → Gluetun (Medium only) / SABnzbd (every tier) / Recyclarr (every tier) / GPU questions → PUID/PGID/timezone) → `_generate_and_maybe_start()` (review screen, `write_stack()` behind a `try/except OSError` boundary, optional `docker compose up -d`). Every mutating action (Docker install, container start, `vulcan update`) sits behind `typer.confirm()` with no bypass beyond an explicit `--yes` - matching Atlas's precedent that infrastructure-mutating actions need explicit opt-in, never an assumed default. Non-mutating actions (`vulcan backup`) need no confirmation at all.

**The TUI (`installer/tui/`).** Five screens, forward-only (no back-navigation anywhere, deliberately, matching the CLI's own forward-only prompt sequence): `WelcomeScreen` (detection) → `DockerReadyScreen` (bootstrap) → `MediaPathScreen` → `TierConfigScreen` (tier + Gluetun/SABnzbd/Recyclarr/GPU checkboxes + PUID/PGID/timezone, **or** a "Customize Services" button leading to `ServiceSelectionScreen` instead of `ReviewScreen`) → `ReviewScreen` (generate, then Start Stack Now / Finish Without Starting). `VulcanApp` (`app.py`) holds all session state as plain instance attributes (`system_info`, `previous_state`, `tier_name`, `puid`, `custom_services`, etc.) rather than threading it through screen constructors - each screen reads/writes `self.app.*` directly, the same role `GenerationConfig` plays by the end of the CLI flow. Any subprocess-backed operation (Docker install/start, `docker compose up -d`) runs in a `@work(thread=True)` worker with results delivered back via `self.app.call_from_thread(callback, ...)` - never called directly from a message handler, which would block the event loop. `ServiceSelectionScreen` uses a real `SelectionList` (verified live against Textual 8.2.8: `Selection(prompt, value, initial_state)` for pre-checking, `.toggle(value)` by value not index, `.selected` returns the current list, `SelectionList.SelectedChanged` fires on every toggle) with GPU-checkbox visibility reacting to whether Jellyfin is currently selected. **A real layout gotcha, caught by `Pilot.click()` refusing an out-of-bounds target, not by reading the code**: stacking too many widgets vertically pushes later ones below a standard 80x24 terminal's visible viewport - `TierConfigScreen`'s two buttons live in a `Horizontal` container side by side for exactly this reason, not just stacked `Vertical` like everything above them.

## Testing conventions

- Mock at the **importing module's namespace**, not the source (`patch("installer.cli.detect_system", ...)`, not `patch("installer.detect.detect_system", ...)`) - standard `unittest.mock` behavior, but easy to get backwards.
- `tmp_path` (pytest fixture) for anything touching the real filesystem - never the real `stack/`/`backups/` directories relative to repo root, except inside the handful of deliberate real-infrastructure checks described below, which always clean up in a `finally`/explicit teardown.
- TUI tests (`test_tui.py`) use Textual's own `App.run_test()` (async context manager yielding a `Pilot`) - the documented, correct way to test a Textual app headlessly, not a custom harness. `pytest-asyncio` with `asyncio_mode = "auto"` (set in `pyproject.toml`) means `async def test_...` needs no per-test decorator. Each screen has a `_launch_at_<screen>_screen(...)` helper mirroring the real navigation path (or, where establishing that path is itself under test, a direct `app.push_screen(...)` shortcut) - **a real, non-obvious hazard already hit twice**: `VulcanApp.on_mount()` always pushes `WelcomeScreen` first, whose own background detection worker keeps running - a test that manually overrides `app.system_info` without first awaiting `app.workers.wait_for_complete()` loses the race and gets silently overwritten by real detected values moments later. Every `_launch_at_*` helper either awaits that completion or mocks `WelcomeScreen`'s own `detect_system`/`load_previous_state` before proceeding.
- **Real-infrastructure verification is load-bearing in this project's history, not optional polish.** Nearly every slice includes at least one check against this actual machine's real Docker, not just mocks: real containers started/stopped, real GPU passthrough confirmed via `docker exec` + `/dev/dri`, real generated compose files validated with `docker compose config`, a real `vulcan backup` archive inspected with `tarfile`. When adding a feature that touches Docker/the filesystem/real subprocess calls, a mocked test suite passing is necessary but not sufficient - look for what a real check would look like before considering the work done, and always clean up (`docker compose down`, `rm -rf` the scratch stack) immediately after.

## Code style

Heavy vertical spacing, matching the style established from the very first commit: each function argument on its own line in a multi-arg call, a blank line after `def ...():` before the body, blank lines between most statements. Very few docstrings (module-level explaining *why*, not function-level explaining *what*). New code should match whatever file it's editing.
