## Commands

```bash
# Setup
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

# Run the CLI
./install                      # bootstraps .venv on first run, then execs into the TUI by default
vulcan --plain                 # plain Typer prompts instead of the TUI (installed console script)
python -m installer --plain    # equivalent, for running from source without reinstalling

# Tests (pytest, config lives in [tool.pytest.ini_options] in pyproject.toml - no separate ini file)
python -m pytest tests/
python -m pytest tests/test_generate.py -v
python -m pytest tests/test_tui.py::test_review_screen_shows_correct_summary
python -m pytest tests/ --cov=installer --cov-report=term-missing   # 265 tests, ~98% coverage as of this writing

# scripts/update.sh, scripts/backup.sh, and scripts/restore.sh are thin
# wrappers, not separate logic:
#   exec .venv/bin/python -m installer update / backup / restore "$@"
```

No linter/formatter is configured - nothing enforces style automatically; see "Code style" below for the convention to match by hand. `.github/workflows/ci.yml` exists (mirrors `atlas`'s own CI structure - checkout, a 3.11/3.12 matrix, `pip install -e ".[dev]"`, then the full test suite) but **has never actually run** - there's still no GitHub remote configured for this repo (local-only development so far; **do not push** unless explicitly asked - see the git-push note under Project status). GitHub-hosted `ubuntu-latest` runners ship Docker + Compose v2 pre-installed with the runner user already in the `docker` group, which is why the workflow needs no extra setup for `test_real_detection_and_docker_ready_end_to_end` (the one deliberately-unmocked, real-Docker-dependent test) - but that expectation is unconfirmed against a real execution until this workflow's first run post-push.

## Architecture

**Two interfaces, one engine.** `installer/detect.py`, `installer/docker_setup.py`, `installer/tiers.py`, `installer/services.py`, `installer/generate.py`, and `installer/post_install.py` are the engine: pure or near-pure functions that never prompt, confirm, or catch their own mistakes silently - they return plain result dicts (`{"success": bool, "error": str | None, ...}`) and let the caller decide what to do. `installer/cli.py` (Typer, Rich console output, plain prompts) and `installer/tui/` (Textual) are two independent front ends over that same engine - neither owns any business logic the other doesn't also have access to. When adding a capability, it belongs in the engine layer; a front end's job is only to gather input and call it.

**Entry points.** `./install` (bash) bootstraps `.venv` on first run and always `exec`s into `python -m installer "$@"` - no logic of its own beyond that bootstrap, mirrored exactly by `scripts/update.sh`/`scripts/backup.sh`/`scripts/restore.sh` (`exec .venv/bin/python -m installer update/backup/restore "$@"`, no bootstrap duplicated there since a stack can't exist without `./install` having already run at least once). `installer/__main__.py` and the `vulcan` console script (`pyproject.toml`'s `[project.scripts]`) both point at `installer.cli:app`. `installer/cli.py`'s `main()` is a `@app.callback(invoke_without_command=True)`, not a lone `@app.command()` - required because both `./install` (zero args) and `./install --tier medium --non-interactive --yes` need to work with no subcommand name, while `vulcan version`/`vulcan update`/`vulcan backup`/`vulcan restore` still need to work as real subcommands alongside it. `main()` decides interactive vs. scripted vs. TUI: `--non-interactive` always goes to `run_install()`; otherwise `--plain` goes to `run_install()` too, and the default (no flags) launches the TUI (`from installer.tui import run_tui` - imported lazily inside the branch, not at module top, so `vulcan version`/`--non-interactive` runs don't pay Textual's import cost).

**Detection (`detect.py`).** `detect_system(disk_path="/")` assembles a `SystemInfo` dataclass from `detect_cpu()`/`detect_memory()`/`detect_disk()`/`detect_gpu()`/`detect_docker()`/`detect_os()` - all read-only, all catching their own failure modes (missing tool, unreadable file) and returning `None`/`False`/a zero value rather than raising, since "not present" isn't an error here. **The disk-timing problem**: `detect_system()`'s default `disk_path="/"` only exists to drive an initial, approximate tier recommendation before the user's real media path is known: every real call site (`cli.py`'s `_gather_generation_config()`, the TUI's `MediaPathScreen`) re-runs `detect_disk(media_path)` against the *real* chosen path once it exists and overwrites `SystemInfo.disk_free_gb`/`disk_path_checked` before computing a recommendation that actually means something. `detect_render_group_gid()` (gid of the host's `render` group, `video` as fallback) exists specifically for AMD/Intel GPU passthrough - see Generation below.

**Docker bootstrap (`docker_setup.py` + `shell.py`).** `install_plan_for(os_id)` maps a distro to an install method - `get.docker.com` (ubuntu/debian/raspbian/fedora) or `pacman` (arch), `None` for anything else (caller shows manual-install instructions and stops). `run_ok()` (quiet, `capture_output=True`) is for status checks; `run_privileged()` (no output capture - sudo prompts and install-script progress need the real terminal) prefixes `sudo` only when not already root. **The group-membership gotcha**: a process's group list doesn't refresh mid-run after `usermod -aG docker <user>` - `run_docker_command(..., use_group_workaround=True)` routes through `sg docker -c "<cmd>"` (reads group membership fresh from the system, no relogin needed) for exactly the run that just added the group, falling back to `sudo` if `sg` isn't present. Both `cli.py` and the TUI track a `group_just_added` flag through the whole session for this reason.

**aarch64/ARM readiness audit - a static audit, explicitly not real-hardware verification, and this project is deliberately honest about that distinction rather than quietly upgrading its own confidence.** No ARM hardware exists in this environment, so this was scoped (with the user's explicit sign-off on the approach) to what can be genuinely checked without it, rather than pretending a manifest check is the same as a real run. What was actually confirmed, not assumed: (1) every one of the 16 Docker images `docker-compose.yml.j2` can reference has a real, published `linux/arm64` manifest - checked with `docker manifest inspect <image>` against the real registries (Docker Hub, `lscr.io`, `ghcr.io`), not read off each project's README. (2) `docker_setup.py`'s `DOCKER_SCRIPT_DISTROS` already included `"raspbian"` - the most common ARM homelab distro - before any of this ARM-specific work started; the `get.docker.com` script and Arch's `pacman -S docker` both auto-detect the host's real architecture internally, so neither of Vulcan's two install paths needed a code change to support aarch64. (3) `psutil` (the only compiled/native dependency in `pyproject.toml`) ships `manylinux_aarch64` wheels - no dependency blocks an aarch64 install. Two real, honest gaps found by reading the code, left as genuine open gaps rather than papered over: `detect_cpu()`'s `cpu_model` parsing looks for a `"model name"` line in `/proc/cpuinfo`, the x86 convention - real ARM64 Linux typically exposes `CPU implementer`/`CPU part` fields instead, so `cpu_model` will likely come back `None` ("unknown" in the CLI's own summary) on real ARM hardware; not a crash, since the function already treats a missing field as "not present" by design, but a real display gap worth knowing about going in. `detect_gpu()` only recognizes NVIDIA/AMD/Intel-branded GPUs (`nvidia-smi`/`rocm-smi`/an `lspci` string match) - hardware transcoding was designed around x86-style discrete/integrated GPUs, and typical ARM SBC hardware (e.g. a Raspberry Pi's VideoCore/V4L2 stack) was never in that scope; `detect_gpu()` returns `None` there through the same graceful "not present" path any undetected GPU already takes, so Jellyfin just runs software-only transcoding, not a crash or a silently wrong claim. **What this audit does not claim**: that Vulcan's install flow, the pulled images, or a generated stack actually run correctly end-to-end on real ARM hardware - that remains the one genuinely open, unverified gap, since a manifest existing and an install script detecting the right architecture are real, checkable facts, but neither is the same thing as a real run.

**Tier scoring (`tiers.py`).** `TIERS: dict[str, TierDefinition]` (light/medium/heavy) is the single source of truth for both scoring and service composition - `_MEDIUM_SERVICES = _LIGHT_SERVICES + [...]`, `_HEAVY_SERVICES = _MEDIUM_SERVICES + [...]`, so `TIERS["heavy"].services` is already the flat union of all three tiers' services (16 total) - exposed as `ALL_SERVICES` for anything that needs "every known service" (custom mode's picker) without re-deriving that union itself. `recommend_tier(system_info)` checks heavy→medium→light and returns the *first* tier where cores **and** RAM **and** disk all clear the threshold - deliberately no partial credit or averaging; a single weak resource caps the whole recommendation, matching "sized to what the machine can actually handle" literally. Below even Light's minimums, it still recommends Light (`meets_minimum=False` flags it) rather than nothing - blocking outright would fight the fact that every recommendation is overridable anyway. `Recommendation.explanation` lists every resource actually short of the next tier up (not a single guessed bottleneck), computed via `_shortfalls()`.

**Resource limits (`services.py`).** A 3x3 matrix, not per-service-per-tier hand-tuning: each of the 16 services declares one `RESOURCE_PROFILES[key]` ("light"/"standard"/"heavy" - its own typical footprint, independent of tier), and `RESOURCE_LIMITS[tier][profile] -> (cpus, memory)` scales all profiles together per tier. `resource_limits_for(tier_name)` returns `{key: {"cpus", "memory"}}` for every service. **Verified against real Docker Compose v2 (v5.3.1)**: `deploy.resources.limits` genuinely applies outside Swarm mode - confirmed via a throwaway container and `docker inspect` showing the exact `NanoCpus`/`Memory` requested.

**Generation (`generate.py`).** `GenerationConfig` (tier, media_path, puid, pgid, timezone, enabled_optional, gpu_vendor, custom_services, domain) is what every front end eventually builds and hands to `write_stack()`. `enabled_service_keys(config)` returns `config.custom_services` verbatim when set (custom mode - see below), else the tier's non-optional services plus whatever's in `enabled_optional`. Templates (`templates/docker-compose.yml.j2`, `templates/env.j2`) are one literal, Jinja-guarded block per known service - not a fully generic data-driven renderer, deliberately: with 16 known services each carrying small real quirks, this reads like a normal hand-written compose file instead of an abstraction built for services that don't exist yet.

- **Hardlink-safe volumes** (TRaSH Guides convention): services that both download and import media (qBittorrent, SABnzbd, Radarr, Sonarr, Lidarr) mount the *entire* `${MEDIA_PATH}` at `/data` read-write, not separate `downloads`/`media` mounts - so a hardlink from `/data/downloads/...` to `/data/media/...` stays on one filesystem. Jellyfin/Bazarr only need `${MEDIA_PATH}/media`, read-only.
- **GPU passthrough**: AMD/Intel share one path - `/dev/dri` device mapping plus `group_add` with the host's real `render` group gid (**PUID/PGID alone doesn't grant device access** - confirmed by starting a real container and checking `/dev/dri` visibility and group membership inside it). NVIDIA uses the standard `deploy.resources.reservations.devices` block, nested as a **sibling of `limits` under the same `deploy.resources` key**, not a second top-level `deploy:` block (a real duplicate-key conflict caught by reasoning about the YAML shape before writing it, not by trial and error) - flagged as not hardware-verified in this session (no NVIDIA GPU on the dev machine), schema-validity only.
- **Gluetun**: qBittorrent reroutes via `network_mode: "service:gluetun"` instead of its own ports when enabled. `write_stack()` never invents real VPN credentials - placeholders (`changeme`) with `# TODO` comments, flagged via a returned warning.
- **SABnzbd**: `optional=True` in `_LIGHT_SERVICES` (available - and its own tier-agnostic confirm question shown - starting at Light, unlike Gluetun's Medium-only gating or GPU's Heavy/Jellyfin gating), purely additive alongside qBittorrent rather than a replacement for it. Its LSIO image's web UI listens on container port 8080, the same internal port qBittorrent uses - mapped to host `8081` instead of `8080` to avoid the collision, confirmed against LinuxServer's real documented image (`lscr.io/linuxserver/sabnzbd:latest`) before designing around it. Deliberately not routed through Gluetun - Usenet is a direct SSL connection to a paid provider, not peer-to-peer, so it doesn't carry BitTorrent's IP-exposure motivation for VPN-routing. `write_stack()` returns a warning that real Usenet provider credentials still need to be entered through SABnzbd's own first-run setup wizard, the same "never invent a secret, just flag it" treatment Gluetun's VPN credentials get. **Verified against a real container**: generated a real Light-tier stack with SABnzbd enabled into a scratch directory, confirmed via `docker compose config` that qBittorrent and SABnzbd's ports don't collide (`8080` vs `8081`), then actually pulled and started the real `lscr.io/linuxserver/sabnzbd:latest` image - it came up clean (SABnzbd 5.0.4, no errors in its logs) and answered on host port 8081.
- **Recyclarr**: `optional=True` in `_LIGHT_SERVICES`, tier-agnostic like SABnzbd - it always has something real to sync against, since Radarr/Sonarr are non-optional in every tier. Two real deviations from every other service block, both confirmed against recyclarr.dev's real docs rather than assumed: (1) `ghcr.io/recyclarr/recyclarr:8` (major-version pin) - the upstream `:latest` tag **is no longer published**, so this is the one service block in the whole template that isn't `:latest`. (2) the container is rootless and takes a Compose-level `user: "${PUID}:${PGID}"` field instead of `PUID`/`PGID` environment variables the way every LSIO-family service does - no `PUID=`/`PGID=` lines in its `environment:` block at all. **Deliberately no Vulcan-authored `recyclarr.yml`**: the alternative (generating a config with hardcoded TRaSH Guides `trash_id` quality-profile references) was considered and rejected - those IDs are curated externally and can be restructured upstream, and Recyclarr's own `RECYCLARR_CREATE_CONFIG=true` env var already scaffolds a real starter config on first container start, which is a better answer than Vulcan hand-maintaining YAML sync content. `write_stack()`'s warning tells the user to edit the scaffolded `stack/config/recyclarr/recyclarr.yml` with real Radarr/Sonarr API keys afterward, pointing `base_url` at the exact container names/ports this stack already uses (`http://radarr:7878`, `http://sonarr:8989`) - the same "never invent a secret, flag it" treatment Gluetun/SABnzbd get, but for a credential embedded in a YAML file rather than `.env`. **Verified against a real container, and a real finding the warning text was rewritten around**: generated a real stack with Recyclarr enabled, confirmed via `docker compose config` that the `user:` field and pinned image tag render correctly, then actually pulled and started the real image and confirmed `RECYCLARR_CREATE_CONFIG=true` genuinely created a real `recyclarr.yml` under `stack/config/recyclarr/` on first start (not just per docs) - but its content was a `sonarr:` section only, with generic placeholders (`http://localhost:8989`, `YOUR_KEY_HERE`), not a `radarr:` section too and not Vulcan's actual container names. The warning explicitly says to add a `radarr:` section alongside the scaffolded `sonarr:` one, not just "edit the values" - confirmed necessary by reading the real generated file, not assumed from docs. Lidarr integration was checked and confirmed unsupported by Recyclarr (Radarr/Sonarr only) - not a gap, a real upstream limitation.
- **State persistence**: `write_stack()` always also writes `stack/.vulcan-state.json` (tier, media_path, puid/pgid/timezone, enabled_optional, gpu_vendor, custom_services, generated_at) - `load_previous_state()` reads it back, tolerating a missing/corrupt file or unrecognized tier by returning `None` rather than raising. This is what makes re-running `./install` against an existing stack safe: every front end sources its prompt *defaults* from here (falling back to fresh detection only when there's no previous state), following the same precedence everywhere - **explicit flag/input > previous state > freshly-computed default**.
- **Secret preservation on regenerate**: `write_stack()` reads any existing `.env` *before* overwriting it and carries forward each of `VPN_SERVICE_PROVIDER`/`VPN_TYPE`/`WIREGUARD_PRIVATE_KEY` individually if it's not still the literal `"changeme"` placeholder - per-key, not all-or-nothing, so a user who's only filled in one of the three doesn't lose that partial progress on the next regenerate.
- **Custom mode**: `custom_services: set[str] | None` is a free pick across all 16 `ALL_SERVICES` regardless of which tier they're normally catalogued under - resource limits still scale from whichever tier is chosen (`config.tier`), not from each service's native tier. `enabled_optional` (Gluetun/SABnzbd/Recyclarr/Lidarr/Traefik) becomes meaningless once `custom_services` is set - those are just regular entries in the free-form list, no separate toggle.
- **Real Traefik routing**: closes the long-tracked "bare skeleton, no routing labels, no domain input" gap. `domain: str | None` is only ever gathered when `"traefik"` is in `custom_services_selected` - a real, load-bearing fact found by reading the code, not assumed: **Traefik (and Lidarr) have no enable question anywhere in the normal tier flow at all**, `enabled_optional` never contains `"traefik"` outside custom mode, so custom mode's `ServiceSelectionScreen` (TUI) and the `--domain` flag/interactive prompt (CLI, right after the custom-services block resolves) are the only places a domain needs to exist. Every user-facing service (`jellyfin`, `radarr`, `sonarr`, `prowlarr`, `qbittorrent`, `sabnzbd`, `jellyseerr`, `bazarr`, `lidarr`, `homepage`, `uptime-kuma`) gets a `{% if 'traefik' in enabled and domain %}` guarded `labels:` block routing `<service>.<domain>` to its own **internal** container port (not the host-published one - matters for SABnzbd, whose host port is remapped to `8081` but Traefik talks to the container directly on its real `8080`). Deliberately skipped: `flaresolverr` (internal-only API), `gluetun` (not user-facing), `recyclarr`/`watchtower` (no web UI). TLS uses `tls=true` with no `certresolver` - **a real, documented Traefik behavior, not assumed**: this genuinely triggers Traefik's own auto-generated self-signed default certificate, zero external dependency, confirmed via research and then via a real `curl` showing `issuer: CN=TRAEFIK DEFAULT CERT`. Let's Encrypt/ACME is deliberately out of scope - HTTP-01 needs a port-forwarded public domain and DNS-01 needs picking one specific DNS provider's API out of dozens of legitimate choices, the same "don't hardcode one external assumption" reasoning already applied to Recyclarr's config and Gluetun/SABnzbd's credentials. `qbittorrent`'s labels are skipped whenever `gluetun` is enabled - confirmed via real research that a container using `network_mode: "service:gluetun"` has no network identity of its own for Traefik's Docker provider to discover, not solved (a real VPN-provider-dependent rabbit hole this environment can't verify), just correctly explained via a `write_stack()` warning instead of generating labels that would silently never route. Traefik's own command gains an HTTP→HTTPS redirect gated on `domain` alone, so its output is byte-identical to before this slice whenever no domain is configured. **Verified against real containers, not just `docker compose config`**: started a real Traefik + Radarr pair with a real domain, confirmed via `curl -k -H "Host: radarr.<domain>" https://localhost/` that Traefik genuinely discovered the label-based router and proxied a real `200` from Radarr, that an unmatched Host header correctly got a `404` (rule matching actually works, not just present), that plain HTTP redirected `301` to HTTPS, and separately confirmed via `docker compose config` that a Gluetun+qBittorrent+Traefik+domain combination renders qBittorrent with zero `labels:` while every other enabled service still gets them.

**Post-install (`post_install.py`).** `update_stack(compose_path, env_path)` runs `docker compose pull` then `up -d` as two distinct steps (not `up -d --pull always`), so a pull failure reports distinctly from a recreate failure - the on-demand alternative to Heavy tier's Watchtower (which updates continuously on its own). `backup_stack(stack_dir, backup_dir)` tars `config/` + `docker-compose.yml` + `.env` into a timestamped `backups/<ts>.tar.gz` - **never** the media library itself, exactly the config/data separation the volume layout already exists to make possible - and always returns a warning that the archive may contain real credentials (`.env`), unconditionally, not conditional on Gluetun actually being configured.

**`restore_stack(backup_path, compose_path, env_path, stack_dir)` is the reverse of `backup_stack()` - and the first genuinely destructive local-file operation in the project.** `latest_backup(backup_dir)` finds the most recent `vulcan-backup-*.tar.gz` by a plain lexicographic sort - safe only because `backup_stack()`'s own timestamp format (`%Y%m%dT%H%M%SZ`) already sorts correctly as a string, no datetime parsing needed. Two real details, not assumed: (1) extraction always passes `filter="data"` to `tarfile.extractall()` - the path-traversal-safe mode from PEP 706, confirmed via real research to be backported to every Python version this project supports (3.11/3.12), not just 3.12+, so no version branching was needed to use it unconditionally. (2) if a compose file already exists at the target, `restore_stack()` runs `docker compose down` against **that pre-restore file** before extracting anything - deliberately that ordering and not the reverse, since after extraction the compose file becomes the restored version, which might not even reference the same services the old one had running; stopping first avoids a container racing with its own config directory being overwritten out from under it. `restore_stack()` never touches `stack/.vulcan-state.json` - `backup_stack()` never archived it either, so there's nothing to restore there; symmetric by construction, not an oversight. **A real bug caught only by testing against a real drifted stack, not by the mocked test suite**: `tarfile.extractall()` only ever adds or overwrites members present in the archive - it never deletes files already on disk that the archive doesn't mention. The first real verification pass restored an old `docker-compose.yml`/`.env` correctly but left a stray file (added to `config/prowlarr/` after the backup was taken) sitting there untouched, silently defeating what "restore" is supposed to mean. Fixed by having `restore_stack()` `shutil.rmtree()` the existing `config/` directory before extracting - re-verified against the same real scenario (a real container running, a real backup, a real stray file added afterward) and confirmed the stray file is now genuinely gone post-restore, not just that extraction "succeeded."

**Both the down-before-extract ordering and the stray-file cleanup have been verified against a real running container**, not just mocked: started a real `prowlarr` container from a real generated stack, took a real backup, drifted both the compose file and a config file (including adding a file with no archive counterpart), then ran `restore_stack()` for real - confirmed via `docker ps` that the container was genuinely stopped/removed by the `down` step before any file touched disk, confirmed the restored `docker-compose.yml`/`config/prowlarr/settings` matched the backup exactly, confirmed the stray file was gone, and confirmed `docker compose up -d` against the restored stack came back up cleanly afterward.

**CLI wiring (`cli.py`).** `run_install()` → `_ensure_docker_ready()` (mirrors `docker_setup.py`'s three readiness gaps: not-installed / not-running / no-compose-v2, each behind its own `typer.confirm()`) → `_gather_generation_config()` (media path → real `detect_disk()` → `recommend_tier()` display → tier choice → custom-mode question → Gluetun (Medium only) / SABnzbd (every tier) / Recyclarr (every tier) / GPU questions → PUID/PGID/timezone) → `_generate_and_maybe_start()` (review screen, `write_stack()` behind a `try/except OSError` boundary, optional `docker compose up -d`). Every mutating action (Docker install, container start, `vulcan update`, `vulcan restore`) sits behind `typer.confirm()` with no bypass beyond an explicit `--yes` - matching Atlas's precedent that infrastructure-mutating actions need explicit opt-in, never an assumed default. Non-mutating actions (`vulcan backup`) need no confirmation at all.

**The TUI (`installer/tui/`).** Six screens: `WelcomeScreen` (detection) → `DockerReadyScreen` (bootstrap) → `MediaPathScreen` → `TierConfigScreen` (tier + Gluetun/SABnzbd/Recyclarr/GPU checkboxes + PUID/PGID/timezone) → `ReviewScreen` (generate, then Start Stack Now / Finish Without Starting) is the primary five-screen path; `TierConfigScreen`'s "Customize Services" button is the one branch off it, leading to the sixth screen, `ServiceSelectionScreen`, instead of straight to `ReviewScreen`. `VulcanApp` (`app.py`) holds all session state as plain instance attributes (`system_info`, `previous_state`, `tier_name`, `puid`, `custom_services`, etc.) rather than threading it through screen constructors - each screen reads/writes `self.app.*` directly, the same role `GenerationConfig` plays by the end of the CLI flow. Any subprocess-backed operation (Docker install/start, `docker compose up -d`) runs in a `@work(thread=True)` worker with results delivered back via `self.app.call_from_thread(callback, ...)` - never called directly from a message handler, which would block the event loop. `ServiceSelectionScreen` uses a real `SelectionList` (verified live against Textual 8.2.8: `Selection(prompt, value, initial_state)` for pre-checking, `.toggle(value)` by value not index, `.selected` returns the current list, `SelectionList.SelectedChanged` fires on every toggle) with GPU-checkbox visibility reacting to whether Jellyfin is currently selected. **A real layout gotcha, caught by `Pilot.click()` refusing an out-of-bounds target, not by reading the code**: stacking too many widgets vertically pushes later ones below a standard 80x24 terminal's visible viewport - `TierConfigScreen`'s buttons live in a `Horizontal` container side by side for exactly this reason, not just stacked `Vertical` like everything above them; every screen's "Back" button added later follows the same rule, folded into an existing button row rather than added as a new one.

**Back navigation.** Every screen except `WelcomeScreen` (nothing before it) has a `Button("Back", id="back")` calling `self.app.pop_screen()` - genuinely just `pop_screen()`, no manual "go to screen X" logic anywhere, confirmed correct by reading Textual 8.2.8's actual `App.pop_screen()`/`_replace_screen()` source rather than assumed: popping reveals whatever is *really* beneath on the stack (so `ReviewScreen`'s "Back" correctly lands on `TierConfigScreen` or `ServiceSelectionScreen` depending on which one actually pushed it, no special-casing needed), the screen being left is genuinely unmounted, and the screen being revealed is **not** remounted - it gets `ScreenResume`, not `Mount`, so `on_mount()` never re-fires and every widget's value is exactly what the user left it as. Since every "Continue"/"Customize" handler already pushes a *fresh* screen instance rather than a cached one, there's never a stale-forward-screen problem: going back destroys the screen being left, and going forward again from any revealed screen always builds a new next screen from current app state. "Back" navigates the UI stack only - it does not undo a real mutation that already happened (Docker actually installed, `stack/docker-compose.yml` actually written, a container actually started), the same principle a browser back button already follows after a submitted form; going back and regenerating is exactly the same supported "re-run is safe" operation as running `./install` again against an existing stack. Two screens run a background `@work(thread=True)` worker whose completion callback touches `self.query_one(...)` - `DockerReadyScreen.run_fix()` and `ReviewScreen._run_start()` - popping mid-worker would let that callback fire against an already-removed screen, so Back is explicitly disabled for the duration of each (re-enabled after `DockerReadyScreen.fix_complete()`; no re-enable needed after `ReviewScreen`'s start, since it always ends in `self.app.exit(...)` either way). The CLI's `--plain` prompt flow stays forward-only - a separate, much bigger kind of feature (re-prompting logic), not attempted here.

## Testing conventions

- Mock at the **importing module's namespace**, not the source (`patch("installer.cli.detect_system", ...)`, not `patch("installer.detect.detect_system", ...)`) - standard `unittest.mock` behavior, but easy to get backwards.
- `tmp_path` (pytest fixture) for anything touching the real filesystem - never the real `stack/`/`backups/` directories relative to repo root, except inside the handful of deliberate real-infrastructure checks described below, which always clean up in a `finally`/explicit teardown.
- TUI tests (`test_tui.py`) use Textual's own `App.run_test()` (async context manager yielding a `Pilot`) - the documented, correct way to test a Textual app headlessly, not a custom harness. `pytest-asyncio` with `asyncio_mode = "auto"` (set in `pyproject.toml`) means `async def test_...` needs no per-test decorator. Each screen has a `_launch_at_<screen>_screen(...)` helper mirroring the real navigation path (or, where establishing that path is itself under test, a direct `app.push_screen(...)` shortcut) - **a real, non-obvious hazard already hit twice**: `VulcanApp.on_mount()` always pushes `WelcomeScreen` first, whose own background detection worker keeps running - a test that manually overrides `app.system_info` without first awaiting `app.workers.wait_for_complete()` loses the race and gets silently overwritten by real detected values moments later. Every `_launch_at_*` helper either awaits that completion or mocks `WelcomeScreen`'s own `detect_system`/`load_previous_state` before proceeding.
- **Real-infrastructure verification is load-bearing in this project's history, not optional polish.** Nearly every slice includes at least one check against this actual machine's real Docker, not just mocks: real containers started/stopped, real GPU passthrough confirmed via `docker exec` + `/dev/dri`, real generated compose files validated with `docker compose config`, a real `vulcan backup` archive inspected with `tarfile`. When adding a feature that touches Docker/the filesystem/real subprocess calls, a mocked test suite passing is necessary but not sufficient - look for what a real check would look like before considering the work done, and always clean up (`docker compose down`, `rm -rf` the scratch stack) immediately after.
