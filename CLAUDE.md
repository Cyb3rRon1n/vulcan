No formatter is configured, and deliberately so — this codebase has a real, documented style (heavy vertical spacing, see "Code style" below) that a default Black/ruff-format pass would fight; new code matches the file it's editing by hand, not an automated tool. CI does run `ruff check .` (pyflakes-only, `[tool.ruff.lint] select = ["F"]` in `pyproject.toml`) — real correctness signal (unused imports/locals, undefined names) confirmed clean against the existing codebase before adding it (3 genuine dead-code hits found and fixed, zero false positives from broader style rules, which is why the rule set stays narrow rather than ruff's fuller default). `.github/workflows/ci.yml` (mirrors `atlas`'s own CI structure — checkout, a 3.11/3.12 matrix, `pip install -e ".[dev]"`, lint, then the full test suite) **has now genuinely run on real GitHub Actions `ubuntu-latest` runners and passed** — both matrix jobs (3.11 and 3.12), confirmed via `gh run view` after the repo's first push, not just expected to work. GitHub-hosted `ubuntu-latest` runners do ship Docker + Compose v2 pre-installed with the runner user already in the `docker` group, exactly as assumed before this was confirmable — `test_real_detection_and_docker_ready_end_to_end` (the one deliberately-unmocked, real-Docker-dependent test) needed no extra CI setup and passed for real alongside everything else.

## Architecture

**Two interfaces, one engine.** `installer/detect.py`, `installer/docker_setup.py`, `installer/tiers.py`, `installer/services.py`, `installer/generate.py`, and `installer/post_install.py` are the engine: pure or near-pure functions that never prompt, confirm, or catch their own mistakes silently — they return plain result dicts (`{"success": bool, "error": str | None, ...}`) and let the caller decide what to do. `installer/cli.py` (Typer, Rich console output, plain prompts) and `installer/menu.sh` (bash + real `whiptail`) are two independent front ends over that same engine — neither owns any business logic the other doesn't also have access to. When adding a capability, it belongs in the engine layer; a front end's job is only to gather input and call it. **`installer/menu.sh` replaced the earlier Python/Textual TUI (`installer/tui/`) — see "The bash + whiptail installer front end" below for why and how; every `installer/tui/`-era section further down this file is kept for the reasoning it carries, not as a claim it's still the current implementation.**

**Entry points.** `./install` (bash) bootstraps `.venv` on first run and always `exec`s into `python -m installer "$@"` — no logic of its own beyond that bootstrap, mirrored exactly by `scripts/update.sh`/`scripts/backup.sh`/`scripts/restore.sh` (`exec .venv/bin/python -m installer update/backup/restore "$@"`, no bootstrap duplicated there since a stack can't exist without `./install` having already run at least once). `installer/__main__.py` and the `vulcan` console script (`pyproject.toml`'s `[project.scripts]`) both point at `installer.cli:app`. `installer/cli.py`'s `main()` is a `@app.callback(invoke_without_command=True)`, not a lone `@app.command()` — required because both `./install` (zero args) and `./install --tier medium --non-interactive --yes` need to work with no subcommand name, while `vulcan version`/`vulcan update`/`vulcan backup`/`vulcan restore` still need to work as real subcommands alongside it. `main()` decides interactive vs. scripted vs. menu: `--non-interactive` always goes to `run_install()`; otherwise `--plain` goes to `run_install()` too, and the default (no flags) launches `installer/menu.sh` via `_launch_menu()` (a real `subprocess.run(["bash", ...])`, not an import — it's bash, not Python — with the script's exit code propagated via `typer.Exit`).

**Detection (`detect.py`).** `detect_system(disk_path="/")` assembles a `SystemInfo` dataclass from `detect_cpu()`/`detect_memory()`/`detect_disk()`/`detect_gpu()`/`detect_docker()`/`detect_os()` — all read-only, all catching their own failure modes (missing tool, unreadable file) and returning `None`/`False`/a zero value rather than raising, since "not present" isn't an error here. **The disk-timing problem**: `detect_system()`'s default `disk_path="/"` only exists to drive an initial, approximate tier recommendation before the user's real media path is known: every real call site (`cli.py`'s `_gather_generation_config()`, the TUI's `MediaPathScreen`) re-runs `detect_disk(media_path)` against the *real* chosen path once it exists and overwrites `SystemInfo.disk_free_gb`/`disk_path_checked` before computing a recommendation that actually means something. `detect_render_group_gid()` (gid of the host's `render` group, `video` as fallback) exists specifically for AMD/Intel GPU passthrough — see Generation below.

**Docker bootstrap (`docker_setup.py` + `shell.py`).** `install_plan_for(os_id, os_is_atomic)` maps a distro to an install method — `get.docker.com` (ubuntu/debian/raspbian/fedora) or `pacman` (arch), `rpm-ostree` for atomic hosts (checked *before* `os_id`, see below), `None` for anything else (caller shows manual-install instructions and stops). `run_ok()` (quiet, `capture_output=True`) is for status checks; `run_privileged()` (no output capture — sudo prompts and install-script progress need the real terminal) prefixes `sudo` only when not already root. **The group-membership gotcha**: a process's group list doesn't refresh mid-run after `usermod -aG docker <user>` — `run_docker_command(..., use_group_workaround=True)` routes through `sg docker -c "<cmd>"` (reads group membership fresh from the system, no relogin needed) for exactly the run that just added the group, falling back to `sudo` if `sg` isn't present. Both `cli.py` and the TUI track a `group_just_added` flag through the whole session for this reason. `check_docker_ready(use_group_workaround)` applies the same `sg` fix to the readiness *re-check* right after `add_user_to_docker_group()`, not just the final start — a plain `detect_docker()` call there still sees this process's own stale group list.

**Atomic/immutable-OS support (`os_is_atomic`) — ported from the sibling Anvil project, which built and live-verified all of it against a real Bazzite GPU host, not invented here from first principles.** `detect.py`'s `detect_os_is_atomic()` checks `/run/ostree-booted` (ostree's real boot-time marker) before falling back to `shutil.which("rpm-ostree")`. `install_plan_for` checks it *before* `os_id` — Bazzite/Kinoite both report `os_id="fedora"` (`ID_LIKE=fedora`), which would otherwise wrongly route through the plain `get.docker.com` script against a read-only base image. The atomic path adds Docker's real repo file then runs `rpm-ostree install docker-ce docker-ce-cli containerd.io docker-compose-plugin docker-buildx-plugin` — layered, not live, so a successful install reports `needs_reboot: True` and both front ends stop cleanly with real reboot instructions instead of pretending Docker is ready.

**Two real bugs, found and fixed live by Anvil against a real Bazzite host, ported here unchanged rather than re-derived:**
1. **`usermod -aG docker <user>` reports real success and silently writes nothing** when the docker group was created by `systemd-sysusers` for a layered package and its canonical record lives only in `/usr/lib/group` (the `altfiles` NSS source, never present in `/etc/group` at all — confirmed live: `getent group docker`/`id <user>` showed no membership change after a "successful" `usermod`). `gpasswd -a` fails the same way, more honestly (`group 'docker' does not exist in /etc/group`) — both tools only ever look at the literal file. **The real, live-verified fix**: a local `/etc/group` entry with the same name+gid merges cleanly with the vendor entry (`nsswitch.conf`'s own `group: files [SUCCESS=merge] altfiles ...`), after which `gpasswd` manages membership on it normally. `add_user_to_docker_group()` now tries plain `usermod` first (unchanged, still correct on every non-atomic host) and only falls back to the merge-entry trick when a real functional check (`_user_in_docker_group()`, `id -nG <user>` — never trust the tool's own claimed exit code) shows the plain path didn't actually work.
2. **A plain `detect_docker()` re-check right after fixing group membership in the same process still fails**, since that process's own supplementary group list was fixed at login time and doesn't re-read `/etc/group`. `check_docker_ready(use_group_workaround=True)` (above) closes this.

Also closed while porting: `add_user_to_docker_group()`'s result was never checked in either front end before this - both `_ensure_docker_ready()` and `DockerReadyScreen` now check it and report a clear error rather than silently proceeding into a readiness check that would just fail unexplained. Full live-verification narrative (the actual Bazzite host, the exact commands run, the exact failures hit) lives in Anvil's own `CLAUDE.md`/`ROADMAP.md` "v0.9" entries, not duplicated here — this port carries the same code, not independently re-verified against real atomic hardware from this project.

## MeTube, Downtify, Netdata, and Homepage-private routing

A direct owner request to replicate and improve on a previous CasaOS-based homelab (Jellyfin/Radarr/Sonarr/Prowlarr/Gluetun/FlareSolverr/qBittorrent/Lidarr/Bazarr all already covered 1:1; Dashy → Homepage) - three genuinely new services plus one new routing exception, not a mechanical extension of the existing pattern in every dimension.

**MeTube and Downtify are the "automated downloader" replacement for what the owner's old CasaOS Windows VM did**, deliberately kept container-native rather than adding VM/hypervisor support Vulcan has never had (a Docker Compose generator was never the right place for that - a real Proxmox/libvirt host alongside Vulcan, not through it, was the answer given). Both are tier-agnostic optional, same `_LIGHT_SERVICES` placement as SABnzbd/Recyclarr/Decluttarr/Maintainerr.

**Downtify was picked over `pjmeca/spotify-downloader` for one real, deciding reason, not a coin flip**: the owner was explicit about not wanting to need Spotify Premium. `pjmeca/spotify-downloader` supports real scheduled artist-tracking (closer to Lidarr's own "monitor and auto-grab" model) but needs real Spotify API credentials, and Spotify's own current developer policy requires the API app's owner to have an active Premium subscription to use it at all - a real, live blocker for exactly the "don't need premium" requirement. Downtify needs zero credentials (confirmed via its own docs: it resolves track/playlist metadata by scraping Spotify's public `open.spotify.com/embed` pages, then finds and downloads matching audio via YouTube Music - never touches Spotify's real API), at the cost of losing the automatic-tracking feature - a real tradeoff, decided in the direction the owner's stated constraint pointed.

**A real, found-live gap, not hidden**: Downtify's official image has no documented PUID/PGID support at all (every other service in this stack, including MeTube, does) - confirmed live by starting a real container and finding its own SQLite monitor file landed `root:root`-owned, not `PUID:PGID`-owned like everything else. `write_stack()`'s warning names this outright rather than silently matching the PUID/PGID pattern and hoping it works.

**Netdata is the real system-monitoring replacement for CasaOS's own built-in widget** - and genuinely, deliberately more invasive than any other service in this stack, matched exactly to its own official recommended `docker-compose.yml` (fetched and used directly, not trimmed down): `network_mode: host`, `pid: host`, `SYS_PTRACE`/`SYS_ADMIN` capabilities, `apparmor:unconfined`, read-only mounts of `/`, `/proc`, `/sys`, `/etc/passwd`, `/etc/group`, `/var/log`, and `/var/run/docker.sock`. This is what real-time CPU/RAM/disk/network/temperature monitoring (plus real Docker container awareness, confirmed live - see below) actually needs, not scope creep - but it's treated as a real tradeoff to weigh, not glossed over: unlike Gluetun's opt-out (defaults-on) pattern, Netdata has no default-on path anywhere, and the exact host-access list is named in both the CLI confirm prompt and the TUI checkbox's own tooltip, not just a post-generate warning nobody reads before enabling it.

**Never routed through Traefik, a deliberate exclusion from `WEB_FACING_SERVICES`, not an oversight.** `network_mode: host` means the container shares the host's own network namespace - it has no separate Docker-network IP for Traefik's Docker provider to discover, the identical real limitation qBittorrent already has when sharing Gluetun's namespace (`network_mode: service:gluetun`). Since `WEB_FACING_SERVICES` specifically means "gets a Homepage tile *and* Traefik routing" (enforced by `tests/test_generate.py`'s own cross-check test against the real template), and Netdata can only ever have the first half, it's deliberately left out of that set - `_service_href()` gained a hand-written, unconditional exception for `key == "netdata"` that always returns a direct `http://<host>:19999` link, bypassing the routed-vs-host-port branching every other service goes through. `_HOMEPAGE_GROUPS` gained a new `"System"` group carrying it, with the exclusion's exact reasoning documented in a comment there so it isn't mistaken for a forgotten `WEB_FACING_SERVICES` entry later.

**Homepage-private closes the other half of the same owner request**: "anyone who reaches my domain should land on Jellyfin, not a dashboard listing every other service." New `GenerationConfig.homepage_private: bool`, only ever asked about when Homepage and Traefik+domain are all active (meaningless otherwise) - the CLI prompt and the TUI's `ServiceSelectionScreen` checkbox both default `True` (recommended, opt-out not opt-in, matching Gluetun's own "safe by default" precedent). When set, `_service_href()` gained one more exception alongside the pre-existing qBittorrent+Gluetun one (`homepage_kept_private = key == "homepage" and config.homepage_private`), and `_homepage_allowed_hosts()` stops adding the routed hostname to `HOMEPAGE_ALLOWED_HOSTS` - the compose template's own Homepage block already had a `{% if 'traefik' in enabled and domain %}` guard around its Traefik labels, which now also checks `not homepage_private`. Every other routed service is completely unaffected - this is a Homepage-only exception, the same narrow-scope precedent qBittorrent's own Gluetun exception already established, not a general "opt any service out of Traefik" mechanism.

**A real layout regression, found live and fixed at the root cause, not patched around.** The first version of this work added three new *unconditional* "MeTube/Downtree/Netdata: enabled/disabled" lines to `ReviewScreen`'s summary text, mirroring how SABnzbd/Recyclarr/Homepage are already always shown - which made every single `ReviewScreen` render three lines taller by default, even for a stack that never touches any of the three, silently pushing the dynamically-mounted port-remap fields below the 80x24 test viewport and breaking three previously-passing remap tests (confirmed via `git stash` that they passed on `main` before this work, ruling out a pre-existing flake). Fixed by making the three new lines conditional - only shown when actually enabled - matching the *existing* "Homepage: private" line's own precedent rather than the four pre-existing unconditional service lines; a deliberate, reasoned divergence from that older precedent given this screen's own already-documented tight vertical budget, not an inconsistency introduced by accident.

**A second, independent layout consequence, same root class of problem**: adding the MeTube/Downtify/Netdata checkboxes to `TierConfigScreen` made *that* screen taller too, requiring the identical `VerticalScroll`-root fix `ReviewScreen` already established (dropping `align: center middle`, which fights a scrollable root) to keep `#continue`/`#back`/`#customize` reachable. That surfaced a real, confirmed Textual `Pilot` mouse-hit-testing quirk against the new nested-`Horizontal`-inside-`VerticalScroll` layout - clicking one checkbox by selector could toggle a *different* checkbox instead, non-deterministically. Root-caused rather than assumed: the identical toggle done via real keyboard interaction (`checkbox.focus()` then `pilot.press("space")`) landed on the correct widget every single time, proving the application's own click-handling code was never the bug - it's specifically `Pilot.click()`'s coordinate resolution against this layout shape. Worked around in tests by setting `Checkbox.value` directly in test setup instead of simulating a click for the affected checkboxes (these particular checkboxes have no `on_checkbox_changed` side effects of their own worth click-testing - only their final value, read when Continue is pressed, matters), not by chasing the Textual-level bug itself.

**Verified against real Docker, all three services, not just `docker compose config`** (though a full Heavy-tier stack with all three plus Homepage-private plus Traefik+a real domain also validated clean via `docker compose config`, exit 0). Pulled and started all three for real: MeTube answered a real `curl` with `200` and reported `healthy`; Downtify answered `200` and its root-owned data file was confirmed exactly as documented; Netdata answered `200`, correctly recognized the real host (`fedora`) through its `/host/etc/os-release` mount, and - genuinely proving the `docker.sock` mount does what it's there for, not just present in the rendered YAML - its own logs showed it discovering and correctly naming its own running container via a real `docker.sock` API call. All three containers and their pulled images were removed afterward; nothing left running.

**aarch64/ARM readiness audit — a static audit, explicitly not real-hardware verification, and this project is deliberately honest about that distinction rather than quietly upgrading its own confidence.** No ARM hardware exists in this environment, so this was scoped (with the user's explicit sign-off on the approach) to what can be genuinely checked without it, rather than pretending a manifest check is the same as a real run. What was actually confirmed, not assumed: (1) every one of the 16 Docker images `docker-compose.yml.j2` can reference has a real, published `linux/arm64` manifest — checked with `docker manifest inspect <image>` against the real registries (Docker Hub, `lscr.io`, `ghcr.io`), not read off each project's README. (2) `docker_setup.py`'s `DOCKER_SCRIPT_DISTROS` already included `"raspbian"` — the most common ARM homelab distro — before any of this ARM-specific work started; the `get.docker.com` script and Arch's `pacman -S docker` both auto-detect the host's real architecture internally, so neither of Vulcan's two install paths needed a code change to support aarch64. (3) `psutil` (the only compiled/native dependency in `pyproject.toml`) ships `manylinux_aarch64` wheels — no dependency blocks an aarch64 install. Two real, honest gaps found by reading the code, left as genuine open gaps rather than papered over: `detect_cpu()`'s `cpu_model` parsing looks for a `"model name"` line in `/proc/cpuinfo`, the x86 convention — real ARM64 Linux typically exposes `CPU implementer`/`CPU part` fields instead, so `cpu_model` will likely come back `None` ("unknown" in the CLI's own summary) on real ARM hardware; not a crash, since the function already treats a missing field as "not present" by design, but a real display gap worth knowing about going in. `detect_gpu()` only recognizes NVIDIA/AMD/Intel-branded GPUs (`nvidia-smi`/`rocm-smi`/an `lspci` string match) — hardware transcoding was designed around x86-style discrete/integrated GPUs, and typical ARM SBC hardware (e.g. a Raspberry Pi's VideoCore/V4L2 stack) was never in that scope; `detect_gpu()` returns `None` there through the same graceful "not present" path any undetected GPU already takes, so Jellyfin just runs software-only transcoding, not a crash or a silently wrong claim. **What this audit does not claim**: that Vulcan's install flow, the pulled images, or a generated stack actually run correctly end-to-end on real ARM hardware — that remains the one genuinely open, unverified gap, since a manifest existing and an install script detecting the right architecture are real, checkable facts, but neither is the same thing as a real run.

**Tier scoring (`tiers.py`).** `TIERS: dict[str, TierDefinition]` (light/medium/heavy) is the single source of truth for both scoring and service composition — `_MEDIUM_SERVICES = _LIGHT_SERVICES + [...]`, `_HEAVY_SERVICES = _MEDIUM_SERVICES + [...]`, so `TIERS["heavy"].services` is already the flat union of all three tiers' services (17 total) — exposed as `ALL_SERVICES` for anything that needs "every known service" (custom mode's picker) without re-deriving that union itself. `recommend_tier(system_info)` checks heavy→medium→light and returns the *first* tier where cores **and** RAM **and** disk all clear the threshold — deliberately no partial credit or averaging; a single weak resource caps the whole recommendation, matching "sized to what the machine can actually handle" literally. Below even Light's minimums, it still recommends Light (`meets_minimum=False` flags it) rather than nothing — blocking outright would fight the fact that every recommendation is overridable anyway. `Recommendation.explanation` lists every resource actually short of the next tier up (not a single guessed bottleneck), computed via `_shortfalls()`.

**Resource limits (`services.py`).** A 3x3 matrix, not per-service-per-tier hand-tuning: each of the 19 services declares one `RESOURCE_PROFILES[key]` ("light"/"standard"/"heavy" — its own typical footprint, independent of tier), and `RESOURCE_LIMITS[tier][profile] -> (cpus, memory)` scales all profiles together per tier. `resource_limits_for(tier_name)` returns `{key: {"cpus", "memory"}}` for every service. **Verified against real Docker Compose v2 (v5.3.1)**: `deploy.resources.limits` genuinely applies outside Swarm mode — confirmed via a throwaway container and `docker inspect` showing the exact `NanoCpus`/`Memory` requested.

**Generation (`generate.py`).** `GenerationConfig` (tier, media_path, puid, pgid, timezone, enabled_optional, gpu_vendor, custom_services, domain) is what every front end eventually builds and hands to `write_stack()`. `enabled_service_keys(config)` returns `config.custom_services` verbatim when set (custom mode — see below), else the tier's non-optional services plus whatever's in `enabled_optional`. Templates (`templates/docker-compose.yml.j2`, `templates/env.j2`) are one literal, Jinja-guarded block per known service — not a fully generic data-driven renderer, deliberately: with 17 known services each carrying small real quirks, this reads like a normal hand-written compose file instead of an abstraction built for services that don't exist yet.

- **Hardlink-safe volumes** (TRaSH Guides convention): services that both download and import media (qBittorrent, SABnzbd, Radarr, Sonarr, Lidarr) mount the *entire* `${MEDIA_PATH}` at `/data` read-write, not separate `downloads`/`media` mounts — so a hardlink from `/data/downloads/...` to `/data/media/...` stays on one filesystem. Jellyfin/Bazarr only need `${MEDIA_PATH}/media`, read-only.
- **GPU passthrough**: AMD/Intel share one path — `/dev/dri` device mapping plus `group_add` with the host's real `render` group gid (**PUID/PGID alone doesn't grant device access** — confirmed by starting a real container and checking `/dev/dri` visibility and group membership inside it). NVIDIA uses the standard `deploy.resources.reservations.devices` block, nested as a **sibling of `limits` under the same `deploy.resources` key**, not a second top-level `deploy:` block (a real duplicate-key conflict caught by reasoning about the YAML shape before writing it, not by trial and error) — flagged as not hardware-verified in this session (no NVIDIA GPU on the dev machine), schema-validity only.
- **Gluetun**: qBittorrent reroutes via `network_mode: "service:gluetun"` instead of its own ports when enabled. `write_stack()` never invents real VPN credentials — placeholders (`changeme`) with `# TODO` comments, flagged via a returned warning. `optional=True` in `_LIGHT_SERVICES` (moved up from `_MEDIUM_SERVICES` — see the default-on entry below), tier-agnostic like SABnzbd/Recyclarr/Decluttarr.
- **SABnzbd**: `optional=True` in `_LIGHT_SERVICES` (available — and its own tier-agnostic confirm question shown — starting at Light, unlike Gluetun's Medium-only gating or GPU's Heavy/Jellyfin gating), purely additive alongside qBittorrent rather than a replacement for it. Its LSIO image's web UI listens on container port 8080, the same internal port qBittorrent uses — mapped to host `8081` instead of `8080` to avoid the collision, confirmed against LinuxServer's real documented image (`lscr.io/linuxserver/sabnzbd:latest`) before designing around it. Deliberately not routed through Gluetun — Usenet is a direct SSL connection to a paid provider, not peer-to-peer, so it doesn't carry BitTorrent's IP-exposure motivation for VPN-routing. `write_stack()` returns a warning that real Usenet provider credentials still need to be entered through SABnzbd's own first-run setup wizard, the same "never invent a secret, just flag it" treatment Gluetun's VPN credentials get. **Verified against a real container**: generated a real Light-tier stack with SABnzbd enabled into a scratch directory, confirmed via `docker compose config` that qBittorrent and SABnzbd's ports don't collide (`8080` vs `8081`), then actually pulled and started the real `lscr.io/linuxserver/sabnzbd:latest` image — it came up clean (SABnzbd 5.0.4, no errors in its logs) and answered on host port 8081.
- **Recyclarr**: `optional=True` in `_LIGHT_SERVICES`, tier-agnostic like SABnzbd — it always has something real to sync against, since Radarr/Sonarr are non-optional in every tier. Two real deviations from every other service block, both confirmed against recyclarr.dev's real docs rather than assumed: (1) `ghcr.io/recyclarr/recyclarr:8` (major-version pin) — the upstream `:latest` tag **is no longer published**, so this is the one service block in the whole template that isn't `:latest`. (2) the container is rootless and takes a Compose-level `user: "${PUID}:${PGID}"` field instead of `PUID`/`PGID` environment variables the way every LSIO-family service does — no `PUID=`/`PGID=` lines in its `environment:` block at all. **Deliberately no Vulcan-authored `recyclarr.yml`**: the alternative (generating a config with hardcoded TRaSH Guides `trash_id` quality-profile references) was considered and rejected — those IDs are curated externally and can be restructured upstream, and Recyclarr's own `RECYCLARR_CREATE_CONFIG=true` env var already scaffolds a real starter config on first container start, which is a better answer than Vulcan hand-maintaining YAML sync content. `write_stack()`'s warning tells the user to edit the scaffolded `stack/config/recyclarr/recyclarr.yml` with real Radarr/Sonarr API keys afterward, pointing `base_url` at the exact container names/ports this stack already uses (`http://radarr:7878`, `http://sonarr:8989`) — the same "never invent a secret, flag it" treatment Gluetun/SABnzbd get, but for a credential embedded in a YAML file rather than `.env`. **Verified against a real container, and a real finding the warning text was rewritten around**: generated a real stack with Recyclarr enabled, confirmed via `docker compose config` that the `user:` field and pinned image tag render correctly, then actually pulled and started the real image and confirmed `RECYCLARR_CREATE_CONFIG=true` genuinely created a real `recyclarr.yml` under `stack/config/recyclarr/` on first start (not just per docs) — but its content was a `sonarr:` section only, with generic placeholders (`http://localhost:8989`, `YOUR_KEY_HERE`), not a `radarr:` section too and not Vulcan's actual container names. The warning explicitly says to add a `radarr:` section alongside the scaffolded `sonarr:` one, not just "edit the values" — confirmed necessary by reading the real generated file, not assumed from docs. Lidarr and Readarr integration were both checked and confirmed unsupported by Recyclarr (Radarr/Sonarr only) — not a gap, a real upstream limitation.

**`backup_stack()` no longer archives live SQLite databases directly.** Follow-up to a "what do other homelab users get bitten by" discussion — every `*arr` app and Jellyfin itself store real state in SQLite, and the original implementation just `tar.add()`'d `config/` as-is with zero coordination with whatever's running, a real (if latent) risk of archiving a torn/mid-write database. `_is_sqlite_file(path)` detects real SQLite files generically by magic header (`b"SQLite format 3\x00"`, the stable file-format signature) rather than a hardcoded per-service filename table — the same "don't maintain a mapping that needs updating every time a service is added" reasoning already applied to Homepage's groups and Traefik's routed-service list. `backup_stack()` now stages `config/` into a `tempfile.TemporaryDirectory()` via `shutil.copytree(..., ignore=<skip real SQLite files>)`, then `_snapshot_sqlite_database()` writes a proper point-in-time copy of each real SQLite file into the staged tree using Python's stdlib `sqlite3.Connection.backup()` (opening the live file read-only via the `file:...?mode=ro` URI form, so this process never takes a write lock or creates a stray `-wal`/`-shm` file) before the staged directory gets tarred exactly as before — **zero new dependencies**, `sqlite3` and `tempfile` are both stdlib. **Read-only media-path redundancy detection (`detect_media_redundancy()`/`describe_media_redundancy()` in `detect.py`).** Follow-up to a discussion on whether Vulcan should manage RAID/partitioning itself — deliberately not: everything else Vulcan does is reversible (regenerate a compose file, restore a backup), while creating/modifying storage is genuinely destructive and belongs to mature, purpose-built tools (mdadm, ZFS, btrfs, TrueNAS/Unraid). This is the safe alternative: **report** whether `media_path` has any drive-level redundancy, the same read-only style as CPU/GPU detection, never suggest or perform a storage change. `findmnt -no SOURCE,FSTYPE,TARGET -T <path>` resolves any arbitrary path (not just a mountpoint) to its backing device/pool, filesystem, and real mountpoint — confirmed real on this machine. Branches by filesystem: an mdadm array (`device` starts with `/dev/md`) reads `/proc/mdstat` for that array's raid level (`raid1`/`4`/`5`/`6`/`10` = redundant, `raid0`/`linear` = not); btrfs runs `btrfs filesystem show <mountpoint>` and checks `Total devices N` (`N > 1` = redundant); ZFS resolves the pool name and runs `zpool status <pool>`, redundant if its config-tree output contains a `mirror`/`raidz` line; anything else (ext4/xfs/vfat directly on a plain device) is single-device, not redundant. A missing `btrfs`/`zpool` binary means "can't determine" (`redundant: None`), never a false "not redundant" — a real bug caught and fixed before shipping, not by testing, but by reading the branch structure: the original `elif filesystem == "btrfs" and shutil.which("btrfs")` combined check silently fell through to the plain-device `else` when the tool was missing, which would have wrongly reported "no redundancy" instead of "unknown." **A second real bug, this one only caught by running against a real filesystem**: `btrfs filesystem show` rejects an arbitrary path underneath its mountpoint (`ERROR: not a valid btrfs filesystem`) even though `findmnt -T` resolves that same path fine — the fix was passing `findmnt`'s own resolved `TARGET` (the real mountpoint) to `btrfs filesystem show`, not the raw `media_path` argument. Surfaced once, right when `detect_disk(media_path)` already runs: the TUI (`MediaPathScreen`) stores it as `self.app.media_redundancy` and `ReviewScreen` renders it in the summary (plus a plain-text warning line when not redundant, since that screen's summary is a single `Static`, not per-line Rich-tagged CLI output); the CLI (`_gather_generation_config()`) computes and prints it immediately, the same way the "Recommended tier" line already is — deliberately not threaded through `GenerationConfig`, since it's purely observational and doesn't affect what gets generated. **Honestly bounded verification**: the plain-device and single-device-btrfs branches are verified against this real machine's actual `/home` (confirmed `redundant: False`, `device_count: 1`) and through a real end-to-end CLI run (a `tmpfs`-backed media path correctly reported as non-redundant). The mdadm-active-array and ZFS-mirror branches are test-suite-verified only, against documented formats — this machine has `mdadm` installed but no spare devices and no passwordless sudo to safely build even a loop-device test array, and no `zfs`/`zpool` tooling at all. Same category of caveat this project already applies to NVIDIA GPU passthrough: shipped, clearly not hardware-verified yet, not claimed as more solid than it is.

**`restore_stack(backup_path, compose_path, env_path, stack_dir)` is the reverse of `backup_stack()` — and the first genuinely destructive local-file operation in the project.** `latest_backup(backup_dir)` finds the most recent `vulcan-backup-*.tar.gz` by a plain lexicographic sort — safe only because `backup_stack()`'s own timestamp format (`%Y%m%dT%H%M%SZ`) already sorts correctly as a string, no datetime parsing needed. Two real details, not assumed: (1) extraction always passes `filter="data"` to `tarfile.extractall()` — the path-traversal-safe mode from PEP 706, confirmed via real research to be backported to every Python version this project supports (3.11/3.12), not just 3.12+, so no version branching was needed to use it unconditionally. (2) if a compose file already exists at the target, `restore_stack()` runs `docker compose down` against **that pre-restore file** before extracting anything — deliberately that ordering and not the reverse, since after extraction the compose file becomes the restored version, which might not even reference the same services the old one had running; stopping first avoids a container racing with its own config directory being overwritten out from under it. `restore_stack()` never touches `stack/.vulcan-state.json` — `backup_stack()` never archived it either, so there's nothing to restore there; symmetric by construction, not an oversight. **A real bug caught only by testing against a real drifted stack, not by the mocked test suite**: `tarfile.extractall()` only ever adds or overwrites members present in the archive — it never deletes files already on disk that the archive doesn't mention. The first real verification pass restored an old `docker-compose.yml`/`.env` correctly but left a stray file (added to `config/prowlarr/` after the backup was taken) sitting there untouched, silently defeating what "restore" is supposed to mean. Fixed by having `restore_stack()` `shutil.rmtree()` the existing `config/` directory before extracting — re-verified against the same real scenario (a real container running, a real backup, a real stray file added afterward) and confirmed the stray file is now genuinely gone post-restore, not just that extraction "succeeded."

**Both the down-before-extract ordering and the stray-file cleanup have been verified against a real running container**, not just mocked: started a real `prowlarr` container from a real generated stack, took a real backup, drifted both the compose file and a config file (including adding a file with no archive counterpart), then ran `restore_stack()` for real — confirmed via `docker ps` that the container was genuinely stopped/removed by the `down` step before any file touched disk, confirmed the restored `docker-compose.yml`/`config/prowlarr/settings` matched the backup exactly, confirmed the stray file was gone, and confirmed `docker compose up -d` against the restored stack came back up cleanly afterward.

**`vulcan uninstall` - the reverse of a plain install.** Added specifically so the CLI/TUI install flow can be repeatedly tested from a genuinely clean slate, without hand-deleting containers and directories between runs. `uninstall_stack()` (`installer/post_install.py`) reuses `restore_stack()`'s exact "stop first, only if a compose file exists" shape (`if Path(compose_path).exists(): run_docker_command([..., "down"])`, a clean error and nothing deleted if that fails) rather than reinventing it, then `shutil.rmtree(stack_dir)`. **Confirmed by reading `templates/docker-compose.yml.j2`, not assumed, that this is a complete wipe**: every service mounts `./config/<key>` as a bind mount into `stack/config/` — no top-level `volumes:` block exists anywhere in the template, so there's no separate named-volume cleanup needed; deleting `stack/` after `down` removes containers, network, and all app state in one pass. `config.media_path` (the actual media library) lives outside `stack/` entirely and is never touched, the same "Vulcan never creates or modifies storage itself" principle already established for read-only redundancy detection. `backups/`/`exports/` are left alone by default too — they're archives the user explicitly asked Vulcan to create, not part of "the install," so uninstalling shouldn't silently take them with it; a `--purge-artifacts` flag opts into deleting those too, for the "wipe genuinely everything, including old test backups" case. Same `--non-interactive`/`--yes` pair and default-deny `typer.confirm()` gate every other mutating lifecycle command already uses, with the confirm text stating explicitly what is and isn't touched. **Verified against real infrastructure, and it surfaced a real, pre-existing mess unrelated to this feature**: several containers from an earlier verification pass (`jellyfin`/`sonarr`/`radarr`/`prowlarr`) were found still running with no `stack/` directory behind them at all — traced to an earlier stray-directory cleanup that deleted `stack/` directly without running `docker compose down` first, never through any code path this project ships; cleared manually before testing, since a real `vulcan uninstall` run is the only path that removes `stack/` at all and it always stops containers first. **`WEB_FACING_SERVICES` — closes a real drift risk flagged (but not fixed) when Homepage pre-seeding shipped: Homepage's tile groups and the Traefik template's per-service label blocks each independently listed which services have a web UI, with nothing keeping the two in sync.** This project has hit exactly this class of staleness before (the "17 known services" count going stale, twice — see `tier_description()`'s entry above), so it was worth closing rather than leaving as a permanent footnote. `WEB_FACING_SERVICES` (`generate.py`) is the full set of services with their own routable web UI, including `traefik` and `homepage` themselves — a deliberate choice over excluding them, since neither routes/tiles itself the *normal* way but each still needs representation somewhere: Traefik gets a Homepage tile (linking to its own dashboard) but no per-service label block; Homepage gets a label block (it's routable like anything else) but no tile of itself. Each existing consumer derives its own view by excluding just itself — `WEB_FACING_SERVICES - {"homepage"}` for `_HOMEPAGE_GROUPS`'s flattened membership, `WEB_FACING_SERVICES - {"traefik"}` for the template's routed set.

**Deliberately not a template rewrite.** The obvious-looking alternative — making `docker-compose.yml.j2` loop over a shared list to generate its per-service Traefik blocks — was considered and rejected, consistent with this project's already-stated principle that the template stays "one literal, Jinja-guarded block per known service... not a fully generic data-driven renderer" (see Generation, above): each service's block carries small real quirks (different container-internal ports, SABnzbd's host/container port mismatch, qBittorrent's Gluetun exception) that a generic loop would have to parameterize around for no real benefit. Instead, `WEB_FACING_SERVICES` only backs two new regression tests (`tests/test_generate.py`) — `test_homepage_groups_match_web_facing_services` (a set-equality check against `_HOMEPAGE_GROUPS`'s flattened values) and `test_traefik_template_routes_match_web_facing_services` (regex-parses the real `docker-compose.yml.j2` for every `traefik.http.routers.<key>.rule=Host` line, excluding Traefik's own special `dashboard` router, and set-compares against the constant) — so a service added to one list and forgotten in the other now fails a real test instead of silently drifting, without touching the hand-written template at all.

**Interactive port remapping in the TUI — closes the roadmap's last non-ARM-blocked open item, replacing "rerun with `vulcan --plain`" with a real inline fix.** `ReviewScreen` gained a `"Remap Ports"` button (shown alongside `"Clean Up & Retry"`, mutually applicable when a conflict has both an own-orphan port and a genuinely-unrelated one) that dynamically mounts one `Horizontal(Static label, Input)` row per remappable conflicting port into `#remap-fields`, plus a fixed `"Apply Remap"`/`"Cancel Remap"` row. `_apply_remap()` mirrors the CLI's `_resolve_port_conflicts()` validation (invalid int, or a typed port colliding with `resolve_ports(config).values()`) plus one real improvement not in the CLI: colliding *within the same submission* (two ports both typed to the same new value) is also caught, via a local `seen_new_ports` set — the CLI's own sequential-prompt loop can't hit this since it revalidates from a state that already includes each prior answer in the same pass, but the TUI collects everything at once, so this check earns its keep rather than being unreachable defensive code. On success: `self._config.port_overrides` is updated in place (already the same dict object as `self.app.port_overrides` — `_build_config()` never copies it — so state persistence to `.vulcan-state.json` keeps working for free), `write_stack()` regenerates, fields hide, and `_start_stack()` retries.

**A real, reproduced layout bug, not just a theoretical risk the roadmap flagged and moved on from.** The roadmap item deferring this named the exact failure mode before it was ever built: "would need dynamically mounted `Input`s per conflicting port inside `ReviewScreen`'s already-tight layout budget." Built the naive version first (fields plus Apply/Cancel all dynamically mounted inside one `VerticalScroll(max-height: 10)`), then deliberately reproduced the predicted failure with a 3-simultaneous-conflict scenario before trusting the single-conflict case was representative — and it broke exactly as predicted: `pilot.click("#apply-remap")` raised a real `textual.pilot.OutOfBounds`, the same failure class `TierConfigScreen` hit before (see its own entry above). Root-caused, not patched around: `ReviewScreen`'s root container was a plain `Vertical` (not scrollable), so content genuinely exceeding the 80x24 viewport wasn't a test artifact — a real user couldn't have scrolled to it either, since there was nothing to scroll. Fixed by making the root a real `VerticalScroll`, which surfaced a second, non-obvious issue along the way: `align: center middle` (present since this screen was first built) fought the new scrollable root, inflating an *unrelated single-conflict* case's layout to a `y=42` offset — traced to `Vertical`'s and `Horizontal`'s own Textual-default `height: 1fr` on the dynamically-mounted per-port rows, which an `auto`-height parent can't size around sanely; fixed with an explicit `.remap-row { height: auto; }` class. `align: center middle` itself was dropped from `ReviewScreen` entirely — centering doesn't make sense once a screen's content can genuinely overflow and scroll.

**Verified past what the automated widget-existence tests alone would have caught.** `tests/test_tui.py` includes a dedicated 3-port scenario (`test_review_screen_remap_reachable_with_many_simultaneous_conflicts`) that scrolls each target into view before clicking — deliberately mirroring what a real user's mouse wheel would have to do to reach off-screen content, not a workaround unique to the test. Regenerated `docs/screenshots/06-review.svg` per this project's own "regenerate after a TUI change" convention (`scripts/generate_screenshots.py`) and confirmed its canvas dimensions are unchanged from before (the default, no-conflict view was never affected) — the other three screenshots the same script touches (`01-welcome`, `04-tier-config`, `05-service-selection`) came back with unrelated Textual-theme-color/random-SVG-id churn from a pre-existing version drift, not from this change, so those three were left unregenerated rather than folded into this diff. Separately hit and worked around, without touching it, a pre-existing environment issue on this dev machine unrelated to this feature: this repo's own `.venv` also has the sibling `anvil` project editable-installed into it (`_editable_impl_anvil_forge.pth` sorts before `_editable_impl_vulcan_forge.pth`), which shadows `installer.tui.app` when running a script directly (though not under `pytest`, which inserts its own rootdir first) — worked around for the one affected command via an explicit `PYTHONPATH`, not fixed at the venv level, since that's outside this slice's scope.

**CLI wiring (`cli.py`).** `run_install()` → `_ensure_docker_ready()` (mirrors `docker_setup.py`'s three readiness gaps: not-installed / not-running / no-compose-v2, each behind its own `typer.confirm()`) → `_gather_generation_config()` (media path → real `detect_disk()` → `recommend_tier()` display → tier choice → custom-mode question → Gluetun / SABnzbd / Recyclarr (all three tier-agnostic, every tier) / GPU questions → PUID/PGID/timezone) → `_generate_and_maybe_start()` (review screen, `write_stack()` behind a `try/except OSError` boundary, optional `docker compose up -d`). Every mutating action (Docker install, container start, `vulcan update`, `vulcan restore`) sits behind `typer.confirm()` with no bypass beyond an explicit `--yes` — matching Atlas's precedent that infrastructure-mutating actions need explicit opt-in, never an assumed default. Non-mutating actions (`vulcan backup`) need no confirmation at all.

**The TUI (`installer/tui/`).** Six screens: `WelcomeScreen` (detection) → `DockerReadyScreen` (bootstrap) → `MediaPathScreen` → `TierConfigScreen` (tier + Gluetun/SABnzbd/Recyclarr/GPU checkboxes + PUID/PGID/timezone) → `ReviewScreen` (generate, then Start Stack Now / Finish Without Starting) is the primary five-screen path; `TierConfigScreen`'s "Customize Services" button is the one branch off it, leading to the sixth screen, `ServiceSelectionScreen`, instead of straight to `ReviewScreen`. `VulcanApp` (`app.py`) holds all session state as plain instance attributes (`system_info`, `previous_state`, `tier_name`, `puid`, `custom_services`, etc.) rather than threading it through screen constructors — each screen reads/writes `self.app.*` directly, the same role `GenerationConfig` plays by the end of the CLI flow. Any subprocess-backed operation (Docker install/start, `docker compose up -d`) runs in a `@work(thread=True)` worker with results delivered back via `self.app.call_from_thread(callback, ...)` — never called directly from a message handler, which would block the event loop. `ServiceSelectionScreen` uses a real `SelectionList` (verified live against Textual 8.2.8: `Selection(prompt, value, initial_state)` for pre-checking, `.toggle(value)` by value not index, `.selected` returns the current list, `SelectionList.SelectedChanged` fires on every toggle) with GPU-checkbox visibility reacting to whether Jellyfin is currently selected. **A real layout gotcha, caught by `Pilot.click()` refusing an out-of-bounds target, not by reading the code**: stacking too many widgets vertically pushes later ones below a standard 80x24 terminal's visible viewport — `TierConfigScreen`'s buttons live in a `Horizontal` container side by side for exactly this reason, not just stacked `Vertical` like everything above them; every screen's "Back" button added later follows the same rule, folded into an existing button row rather than added as a new one.

**README screenshots (`scripts/generate_screenshots.py`, `docs/screenshots/*.svg`).** Real SVG exports via `App.save_screenshot()` — the same real `App.run_test()`/`Pilot` harness the test suite already uses to drive the real app, not a mock or a hand-drawn mockup. Two real gotchas only found by actually running it, not by reading the code: (1) `TierConfigScreen`'s tier-recommendation text is computed once in `compose()` and baked into a `Static` widget — setting `app.system_info.disk_free_gb` *after* that screen is already pushed does nothing, since Textual doesn't remount a screen on reveal (see "Back navigation" above) and there's no reactive binding recomputing the text either; the real fix is patching `detect_disk()` itself (`installer.tui.media_path_screen.detect_disk`) so `MediaPathScreen`'s own genuine `detect_disk()` call — which runs synchronously inside its Continue handler, immediately before pushing `TierConfigScreen` — returns the illustrative value in the first place. (2) That same Continue handler also does a real `mkdir()`, so a nice-looking illustrative path (`/mnt/media`) has to be swapped for a real writable one immediately before the click, then swapped back into `app.media_path` afterward purely for later screens' display — the path shown briefly needs to be real for the click to succeed, but nothing about the *screenshot* needs it to be.

**Back navigation.** Every screen except `WelcomeScreen` (nothing before it) has a `Button("Back", id="back")` calling `self.app.pop_screen()` — genuinely just `pop_screen()`, no manual "go to screen X" logic anywhere, confirmed correct by reading Textual 8.2.8's actual `App.pop_screen()`/`_replace_screen()` source rather than assumed: popping reveals whatever is *really* beneath on the stack (so `ReviewScreen`'s "Back" correctly lands on `TierConfigScreen` or `ServiceSelectionScreen` depending on which one actually pushed it, no special-casing needed), the screen being left is genuinely unmounted, and the screen being revealed is **not** remounted — it gets `ScreenResume`, not `Mount`, so `on_mount()` never re-fires and every widget's value is exactly what the user left it as. Since every "Continue"/"Customize" handler already pushes a *fresh* screen instance rather than a cached one, there's never a stale-forward-screen problem: going back destroys the screen being left, and going forward again from any revealed screen always builds a new next screen from current app state. "Back" navigates the UI stack only — it does not undo a real mutation that already happened (Docker actually installed, `stack/docker-compose.yml` actually written, a container actually started), the same principle a browser back button already follows after a submitted form; going back and regenerating is exactly the same supported "re-run is safe" operation as running `./install` again against an existing stack. Two screens run a background `@work(thread=True)` worker whose completion callback touches `self.query_one(...)` — `DockerReadyScreen.run_fix()` and `ReviewScreen._run_start()` — popping mid-worker would let that callback fire against an already-removed screen, so Back is explicitly disabled for the duration of each (re-enabled after `DockerReadyScreen.fix_complete()`; no re-enable needed after `ReviewScreen`'s start, since it always ends in `self.app.exit(...)` either way). The CLI's `--plain` prompt flow stays forward-only — a separate, much bigger kind of feature (re-prompting logic), not attempted here.

## Vaultwarden, Jellyfin's Authelia exemption explained, and the post-install setup walkthrough

A direct owner request following the MeTube/Downtify/Netdata work above: whether a password manager made sense for the growing pile of per-service credentials this stack generates, and separately, whether Jellyfin's own (pre-existing, silent) exclusion from Authelia was actually the right call - both researched for real rather than assumed, and both landed together with a third piece the owner asked for directly: a real, ordered "what to configure first" walkthrough.

**Vaultwarden was picked after checking what the 2026 self-hosted homelab community actually uses, not by default familiarity** - it's the dominant recommendation for exactly this scale (solo/family homelab): a lightweight Rust reimplementation of the Bitwarden server, well under 50MB RAM, and the *official* Bitwarden apps/browser extensions work against it unmodified (no need for a Vaultwarden-specific client). A 25th real service, tier-agnostic optional like MeTube/Downtify/Netdata.

**Confirmed, not assumed: Vaultwarden has the identical native-app conflict with Authelia that Jellyfin already has.** Real community sources (`jellyfin/jellyfin#16956`, `authelia/authelia#8611`) confirm Authelia's forward-auth login works by redirecting the browser to a login page - which native apps that authenticate directly against an API (Jellyfin's phone/TV apps, and just as much Vaultwarden's own browser extension/mobile/desktop apps) can't complete. Both are deliberately excluded from `authelia@docker` in the compose template, with the reasoning documented inline as a Jinja comment at each exclusion, not just in this file. `write_stack()` now also surfaces this as a real warning on Jellyfin's own entry (previously this was true but silent in the template with no explanation anywhere a user would see it) recommending Jellyfin's own built-in 2FA plugin as the real protection layer for the one service Authelia doesn't cover - the same real protection layer Vaultwarden's own warning recommends for itself.

**A real websocket-aware Traefik setup, not just a copy of Jellyfin's routing pattern.** Vaultwarden's live-sync push notifications need a second path routed to a different container port (`3012`, not the main `80`) - `vaultwarden-ws`, matching `Path(\`/notifications/hub\`)` on the same hostname, alongside the main `vaultwarden` router. Without it the official apps still function correctly, just falling back to periodic polling instead of instant push sync - not a hard requirement, but a real quality difference worth the extra router. `ADMIN_TOKEN` is a genuinely random secret (`secrets.token_hex(32)`) generated into `.env` the same way Authelia's own `JWT_SECRET`/`SESSION_SECRET` already are (`installer/auth.py`) - preserved across a regenerate via the same `_preserved_vpn_value()` helper Gluetun/Tailscale/Cloudflare credentials already use, not reset to a placeholder each time.

**Verified against real Docker**: a full stack with Vaultwarden + Traefik + a real domain + Cloudflare DNS validated clean via `docker compose config` (both routers present, correct ports, no `authelia@docker` label anywhere on either), then a real `vaultwarden/server:latest` container was pulled and started standalone - came up, reported `health: starting` then healthy, and answered its own `/alive` endpoint with a real current timestamp. Removed afterward; nothing left running.

**The setup walkthrough (`docs/WALKTHROUGH.md`, `generate.py`'s `render_setup_order()`) is a direct response to explicit owner feedback that configuration order matters** - not a nice-to-have added speculatively. The doc walks every service in real dependency order (Vaultwarden first so every credential created below has somewhere to go immediately; Prowlarr before the `*arr` apps that query it; a working download client before anything expects one; Jellyfin's libraries before Jellyseerr can request into them; dashboards last since they've nothing to show until everything above is running) and is linked as a raw GitHub blob URL - GitHub renders Markdown blobs in-browser automatically, so this works today with zero new infrastructure; a real mkdocs/GitHub Pages site was considered and deliberately deferred as a separate, larger, not-yet-decided piece of work rather than assumed as part of this request. `render_setup_order()` mirrors the same sequence but trimmed to only the services a given config actually has enabled, with dynamically computed step numbers (not hardcoded "1./2./3.") so skipping a disabled service's step never leaves a visible gap. Wired into both the CLI's post-start output and the TUI's `ReviewScreen._start_complete()`; Homepage's pre-seeded `services.yaml` also gained an always-present "Guides" tile linking to the same doc (unconditional - documentation, not a service with an enabled/disabled state).

**The "TUI text needs to be freely selectable/copyable" requirement was already satisfied by an existing mechanism - checked before assuming a new widget was needed.** Both TUI exit paths that print final instructions (`ReviewScreen._start_complete()`, `_finish_without_starting()`) already used Textual's own `App.exit(message=...)`, and Textual's own implementation (`_print_error_renderables()`, confirmed by reading the installed library's real source, not assumed from the API name) prints that message to the *real* terminal only after the TUI has already torn itself down and released the alternate screen - genuinely plain terminal text a user's own terminal emulator natively mouse-selects, not text rendered live inside the running TUI (where a terminal's own click-drag selection would fight Textual's own mouse-capture instead). This work only enriched what that already-selectable message contains; no new selection mechanism was needed or built.

A direct owner follow-up after the Vaultwarden/walkthrough work above: "is dashy also still an option with all the integrations... i find dashy more eye appealing and i use it in my current setup." Dashy had been replaced 1:1 by Homepage earlier in this project's history (see the MeTube/Downtify/Netdata section above) - this doesn't reverse that decision, it adds Dashy back as a genuine second option alongside Homepage, with the identical real integration depth, not a lesser second-class add.

**Every real integration detail was confirmed against the actual image first, not assumed from Dashy's own docs** - this project's own established discipline (see the Downtify PUID/PGID gap, the Netdata host-access audit, Vaultwarden's real websocket port above) applied here too: pulled `lissy93/dashy:latest` and inspected it directly with `docker inspect`/a real running container, not read off a README. Real findings that shaped the implementation: internal port is `8080` (the `4000` most Dashy guides reference is just a conventional *host*-side mapping, never the container's own listening port); the real user-editable config path is `/app/user-data/conf.yml` (found by `find`-ing inside a running container, then `cat`-ing it to learn the real default schema rather than guessing); it runs as a fixed `uid=1000(node)`/`gid=1000(node)` with no PUID/PGID environment support at all (unlike every LSIO-style service in this stack); and it idles at ~47MB RAM via real `docker stats` against a started container - genuinely light, same `RESOURCE_PROFILES` bucket as Homepage.

**`render_dashy_config()` reuses Homepage's own tile tables rather than duplicating them** - `_HOMEPAGE_GROUPS`/`_HOMEPAGE_DESCRIPTIONS`/`_HOMEPAGE_PORTS` are the one real source of truth for what each service's tile says and links to; only the output *shape* differs, since Dashy's real schema (confirmed from its own default `conf.yml`: `sections: [{name, items: [{title, description, url, icon}]}]`) isn't Homepage's `[{group: [{title: {href, icon, description}}]}]`. `icon: favicon` - a real, documented Dashy feature that auto-fetches each linked site's own favicon - stands in for Homepage's dashboard-icons-pack filenames, which Dashy has no equivalent lookup for.

**Neither dashboard tiles itself, and `WEB_FACING_SERVICES`'s own cross-check tests were extended to cover the second exception, not just special-cased once.** Dashy needed a real Traefik-routed label block (it's genuinely reachable, same as Homepage), so it belongs in `WEB_FACING_SERVICES` - but like Homepage, it never appears inside `_HOMEPAGE_GROUPS`'s own values (no self-tile). `test_homepage_groups_match_web_facing_services` now excludes `{"homepage", "dashy"}` on the right-hand side instead of just `{"homepage"}`, keeping the drift-detection property intact for both dashboards rather than only the original one.

**`dashy_private` mirrors `homepage_private` exactly but is a fully independent question, not a shared one** - own `GenerationConfig` field, own CLI flag pair (`--dashy-private/--dashy-public`), own TUI checkbox, own `_service_href()` exception (`dashy_kept_private`) alongside the pre-existing `homepage_kept_private`/`qbittorrent_via_gluetun` ones. Enabling both dashboards doesn't imply they share one "should a stranger find this" decision.

It doesn't apply to Dashy - Jellyfin and Vaultwarden are excluded because their real native mobile/desktop apps can't complete Authelia's browser-redirect login; Dashy has no native app of its own at all, it's a plain web dashboard exactly like Homepage, which *does* get Authelia's middleware normally. **Verified against real Docker**, not just `docker compose config` (though that validated clean too - Dashy+Homepage+Traefik+domain+Authelia all active together, correct routers, correct `authelia@docker` label present on Dashy's own router, absent on Jellyfin's): pulled and started a real `lissy93/dashy:latest` container with a real pre-seeded `conf.yml` bind-mounted at `/app/user-data/conf.yml`, confirmed via a manual mount test first (a throwaway custom title round-tripped through the container's own `/conf.yml` HTTP endpoint before any code was written against that assumption), then again against the real generated config - reported healthy, answered its own `/conf.yml` endpoint with the exact real tiles generated for that stack (Jellyfin, Authelia, Traefik, and the walkthrough's "Guides" tile). Removed afterward; nothing left running.

## CrowdSec - intrusion protection at the Traefik edge

Motivated by a competitive scan against similar projects (DockSTARTer, Saltbox) ahead of a planned public release - Saltbox bundles CrowdSec in front of its own Traefik, Vulcan didn't, and it was the one gap worth closing before inviting public-domain deployments: Authelia protects the login page, but nothing sat in front of Traefik itself to blunt brute-force/scan traffic before it even got that far. A 27th real service, `optional=True` in `_HEAVY_SERVICES`, same custom-mode-only placement as Authelia/Traefik/Tailscale - genuinely useful only once Traefik is routing real traffic.

**Real integration pattern confirmed against the plugin's own current repo before writing template code, not assumed from a summarized doc fetch.** `crowdsecurity/crowdsec:latest` is the engine (log parsing, decision-making, local API); the actual Traefik integration is a community **Traefik plugin** (`github.com/maxlerebourg/crowdsec-bouncer-traefik-plugin`, pinned `v1.7.1`), not a second container - `--experimental.plugins.bouncer.modulename=...`/`--experimental.plugins.bouncer.version=...` on Traefik's own command, only added when `crowdsec` is enabled (byte-identical Traefik output otherwise, same principle every other optional Traefik feature here already follows). The plugin needs Traefik's real access log (`--accesslog`/`--accesslog.filepath=/var/log/traefik/access.log`), shared with the CrowdSec container via a plain bind mount (`./config/traefik/logs`, read-write on Traefik's side, read-only on CrowdSec's) - deliberately not a Docker named volume, since this project has never used one anywhere else in the template.

**No manual `cscli bouncers add` step, and no credential to invent** - CrowdSec's own image supports self-registering a bouncer via a `BOUNCER_KEY_<name>` env var (`BOUNCER_KEY_TRAEFIK`), and the plugin reads the same value via its `crowdseclapikey` label. Both point at one Vulcan-generated `CROWDSEC_BOUNCER_KEY` (`secrets.token_hex(32)`, same shape as Vaultwarden's `ADMIN_TOKEN` - a real value Vulcan can generate itself, not a `changeme` placeholder like Gluetun's VPN creds or Cloudflare's API token) - preserved across a regenerate via the same `_preserved_vpn_value()` helper every other Vulcan-generated secret already uses.

**`acquis.yaml` (tells CrowdSec what log to read) is a plain Python constant, not a `.j2` template** - unlike Decluttarr's config, it has zero per-install variables (the log path is fixed by the compose template's own volume mount, never user-chosen), so a template would be pure overhead. Pre-seeded once under `stack/config/crowdsec/etc/acquis.yaml`, never overwritten on a regenerate - same "never clobber a real edit" principle as Homepage's `services.yaml`/Authelia's `configuration.yml`.

**Applies to every routed service, including the two Authelia deliberately excludes.** Jellyfin and Vaultwarden skip `authelia@docker` because forward-auth's browser-redirect login breaks their native apps (see above) - but CrowdSec's IP-reputation/behavior blocking isn't an auth challenge, so it doesn't share that conflict and both still get `crowdsec@docker`, added right alongside each service's existing "deliberately never gets Authelia" comment rather than silently. Every other routed service's single hardcoded `authelia@docker` middleware line was generalized to a Jinja `[('crowdsec@docker' if ... ), ('authelia@docker' if ...)] | select | join(',')` expression, combining whichever are actually active in the correct order (CrowdSec first - it should block a malicious IP before Authelia's own login page ever renders for it). Applied identically across all 16 routed-service blocks (including Traefik's own dashboard router) via a scripted regex pass over the template, not 16 separate hand-edits, specifically so the pattern couldn't drift between blocks the way a manual pass risks.

**The bouncer middleware definition lives on CrowdSec's own container block** (`traefik.enable=true` plus the three `traefik.http.middlewares.crowdsec.plugin.bouncer.*` labels), mirroring Authelia's exact precedent for its own `forwardAuth` middleware labels - Traefik's Docker provider reads labels from any container with `traefik.enable=true`, not only ones that also carry a router of their own, and CrowdSec has no web UI/router to route to. Gated behind `{% if 'traefik' in enabled %}` (not `and domain`) for `depends_on`/the log mount/the middleware labels specifically - the CrowdSec engine itself still renders and runs standalone without Traefik at all (harmless, just has nothing to protect yet), matching the "renders cleanly either way, warns rather than silently doing nothing" shape Authelia's own without-Traefik case already established.

**Verified against real Docker, and honestly bounded where it wasn't fully verifiable in this environment.** `docker compose config` validated a full Heavy-tier stack (Jellyfin+Radarr+Traefik+Authelia+CrowdSec+Vaultwarden+domain) clean - confirmed Radarr renders `crowdsec@docker,authelia@docker` in the right order, Jellyfin renders `crowdsec@docker` alone. The CrowdSec engine was started for real: after tracing an initial platform mismatch to a stale ARM64-emulation-era cached `traefik:latest` image from this project's own earlier ARM64 work (not a Vulcan bug - re-pulled for the real host architecture), it came up clean, loaded 59 real scenarios, registered with its own local API, and started tailing the real mounted access log. **Traefik's plugin download itself failed in this dev environment** - `error: 500` from Traefik's own plugin catalog, reproduced against two different plugin versions and, decisively, against Traefik's own official `plugindemo` example plugin failing identically (outbound network access to the catalog domain itself confirmed working separately) - strong evidence this is a Traefik-plugin-catalog-side issue in this specific environment, not a CrowdSec- or Vulcan-specific misconfiguration, but genuinely unconfirmed whether it's environment-specific or a live upstream problem (see ROADMAP's Next section). Not treated as blocking - the compose shape is correct per the plugin's own official docs, the standard integration path - but `write_stack()`'s own warning tells the user exactly how to check for it (`docker compose logs traefik` for a "Plugins are disabled" error) rather than claiming full live verification that didn't actually happen. Also found live and named in the same warning: CrowdSec's own image has no PUID/PGID support, same as Authelia/Dashy - files under `stack/config/crowdsec/` end up root-owned.

## TUI theme - a whiptail/DockSTARTer-style palette, not Textual's own default dark theme

## Persistent Main Menu - a DockSTARTer-style TUI hub

A direct owner request, researched against DockSTARTer's own real source before designing anything - cloned `GhostWriters/DockSTARTer` and `GhostWriters/DockSTARTer-Docs` and traced the actual mechanism in `main.sh`/`scripts/menu_main.sh`/`scripts/menu_config.sh`: every menu level is a `while true` loop showing a persistent menu; picking an item runs that task as a sub-flow, and when it finishes you land back on the *same* menu, not exited. That's the real behavior being matched here, not just DockSTARTer's whiptail color scheme (already matched separately - see the TUI theme entry above).

**This exposed a real, pre-existing gap while researching it, not just an aesthetic mismatch.** `vulcan update`/`pull`/`backup`/`restore`/`uninstall` (`installer/post_install.py`) are real, already-built, pure-function-backed commands - `cli.py`'s own commands are thin wrappers returning the identical `{"success", "error", ...}` shape `ReviewScreen` already knows how to drive via `@work(thread=True)`/`call_from_thread` - but had zero TUI equivalent before this. Closing that gap, not just adding a menu shell, is most of what this feature actually is.

**A new root screen, not a new navigation model.** Every screen in this codebase already pops back to whatever pushed it (`self.app.pop_screen()`, no special-casing anywhere) - the "persistent hub" behavior falls out for free once `MainMenuScreen` (`installer/tui/main_menu_screen.py`) becomes the bottom of the stack via `VulcanApp.on_mount()`; any screen it pushes just needs a "Back to Main Menu" button using the exact same convention. Zero changes to Textual's screen-stack model or to `Back`'s existing semantics anywhere else.

**Button gating is real and re-checked on every return, not computed once and left stale.** `MainMenuScreen._refresh_gating()` checks `(STACK_DIR / "docker-compose.yml").exists() or stack_containers_exist(STACK_DIR.name)` (mirroring `cli.py`'s own real preconditions for `update`/`pull`/`backup`/`uninstall`) and `latest_backup() is not None` (Restore's real, independent precondition - matches `cli.py restore()`, which can restore onto a machine with nothing installed yet). **A real Textual gotcha, confirmed by reading the actual installed source, not assumed**: popping back to a screen reveals the already-mounted instance rather than remounting it (`events.ScreenResume`, not `Mount` - confirmed via `textual/app.py`'s real `pop_screen()` posting `events.ScreenResume()` to the revealed screen), so gating computed only in `compose()`/`on_mount()` would go stale the moment, say, a first backup is taken and "Restore Stack" should become enabled. `on_screen_resume()` re-runs the same `_refresh_gating()` every time the Main Menu is returned to - covered by a dedicated regression test that flips `latest_backup()`'s mock return value mid-test and confirms the button only updates after actually navigating back, not before.

**One shared `MaintenanceScreen`, not four near-duplicate files.** Update/Pull/Backup/Uninstall share an identical shape (confirm text → Confirm/Cancel → background worker → result → "Back to Main Menu"), so `installer/tui/maintenance_screen.py` is one parametrized screen (`title`, `confirm_text`, `action`, `success_message`) with four `classmethod` constructors, instantiated with different closures from `MainMenuScreen`'s button handlers - a deliberate call given this project's own established "one block per real difference" principle (the compose template stays one-block-per-service specifically because each service genuinely differs; these four actions don't). Uninstall's `purge_artifacts` checkbox is the one real per-instance variation - its `action` is deliberately left `None` at construction and built at confirm-time instead (`_confirm()`, run on the main thread, reading the checkbox *before* handing a closed-over zero-arg callable to the background worker), since Textual widget state can't safely be queried from inside a `@work(thread=True)` function - the same "capture what you need before entering the thread" discipline `DockerReadyScreen.run_fix()` already established for `self.app.system_info`.

**Restore stays a separate screen (`installer/tui/restore_screen.py`), not forced into `MaintenanceScreen`'s shape - a real, structural difference, not an arbitrary split.** `cli.py restore()` has a genuine second decision baked in (`typer.confirm("Start the restored stack now?", default=True)`) the other four don't; `RestoreScreen` mirrors it as a real two-step flow (confirm restore → run `restore_stack()` → on success, a second Start-It-Now/Not-Now choice → optionally the same `run_docker_command([..., "up", "-d"])` call `ReviewScreen._run_start()` already uses). Scoped to `latest_backup()` only for v1 - matches CLI's own default-to-latest convenience; a file-picker for a specific older archive is a real, acknowledged gap, not silently dropped (see ROADMAP).

**`WelcomeScreen` gains a real Back button for the first time.** It used to be the true root ("nothing before it," per its own long-standing precedent) - now `MainMenuScreen` is, so it needs one, following the identical `self.app.pop_screen()` pattern every other screen's Back button already uses.

**A real layout bug, found by an actual `Pilot.click()` `OutOfBounds` failure on the new tests, not assumed safe from the CSS.** The first version wrapped the menu's buttons in a `Vertical(id="menu")` nested inside a `VerticalScroll` (matching `ReviewScreen`'s established "`VerticalScroll`, not `Vertical` + `align: center middle`" fix for content exceeding the 80x24 test viewport) - but live debugging (`scroller.virtual_size`, `scroller.max_scroll_y`, per-widget `.region` printed directly) showed the *outer* `VerticalScroll`'s own `virtual_size` was capped at exactly the viewport height (24) even though the real content span was 30 rows - the nested `Vertical` was mismeasuring its own auto-height against its children's true total span, leaving `Exit` (the last of 7 stacked buttons) genuinely unreachable, both to a real click and to `scroll_visible()`. Root-caused, not patched around: removed the nested `Vertical` entirely and made the buttons direct children of the `VerticalScroll` (matching `ServiceSelectionScreen`/`TierConfigScreen`'s own flat-children structure under their scroll roots) - `virtual_size` immediately measured correctly (30 rows, `max_scroll_y=6`) and `scroll_visible()` started working. A real, generalizable finding for this codebase going forward: an extra `Vertical` wrapper nested directly inside a `VerticalScroll` root is not just unnecessary here, it can silently break virtual-size measurement - prefer flat children under a scrollable root, the same shape every other screen in this project already uses.

**Verified for real - the full test suite (23 new tests across `MainMenuScreen`/`MaintenanceScreen`/`RestoreScreen`, plus the base `_launch_at_docker_screen` helper and 6 direct `WelcomeScreen`/navigation tests updated for the new root screen) passes clean, 618 total, and all 7 `docs/screenshots/*.svg` were regenerated and visually inspected** (converted to PNG, read directly) before considering this done - not just that the code compiled or a single test passed. The Main Menu screenshot confirms the intended visual: enabled actions (Guided Setup, Exit) in bright cyan, gated-off actions (Update/Pull/Backup/Restore/Uninstall, correctly disabled with nothing installed yet) in a visibly muted tone - an accidental but genuinely useful side effect of the whiptail theme's own primary/surface contrast.

The owner's original ask (documented in the "TUI theme" and "Persistent Main Menu" sections above) was to make Vulcan's TUI *look and behave* like DockSTARTer's - and what got built was a from-scratch Python/Textual reimplementation of that look and behavior, because DockSTARTer's actual bash + `whiptail` code has no equivalent to paste into a `.py` file. ## Storage planning (`installer/storage.py`) - a real, deliberate reversal of "Vulcan never touches storage"

A direct owner request for a fresh machine scenario: drives that might already be RAIDed, might be several separate un-RAIDed drives, or might need pooling from scratch, with a warning before anything destructive. This runs straight into an existing, on-the-record principle (`README.md`, `CLAUDE.md`, `detect_media_redundancy()`'s own docstring): *"Vulcan never creates or modifies storage itself."* Asked directly whether to keep or reverse that principle before writing anything - the owner chose to reverse it. **This module is Phase 1 of that reversal only** - real execution (an actual `mdadm --create`/`mkfs`/`mount` run) is a deliberate, separate, more heavily-gated follow-up, not built here; everything in `storage.py` is either read-only or a pure planning function that returns commands without running them.

**Three follow-up design forks, resolved toward the safer end before implementation, not assumed:**
- **mdadm only, not ZFS/btrfs** - ships in Ubuntu's repos by default, matches what `detect_media_redundancy()` already reads.
- **Per-category "separation" (TV/Movies/Music/Books) is already solved and needed nothing new.** The original ask sounded like it might mean dedicating a physical drive per category - checked first, and that would be a real regression: hardlinks can't cross filesystems, and `write_stack()` already creates `media/tv`/`media/movies`/`media/music`/`media/books` as real subdirectories under one pooled `MEDIA_PATH` specifically so `*arr` imports stay hardlink-safe (instant, no duplicate disk usage) rather than falling back to slow copies. Confirmed this was already built before proposing anything new - the real gap was the storage layer *underneath* that structure, not the categorization itself.
- **Dry-run only for this pass** - partly because destructive disk operations are the single riskiest class of code this project could ship, partly because this dev environment has no spare real disk (and, checked live, no passwordless sudo) to safely verify real execution against.

**`list_block_devices()` uses `lsblk -J` (structured JSON), not text-column parsing** - specifically so NVMe's `p1`-suffix partition naming vs. SATA/virtio's bare `1` never needs hand-rolled string logic; `lsblk`'s own `pkname` field already resolves parent-disk relationships correctly for both. **A real, found-live filtering gap, not theoretical**: this project's own dev machine has a real `zram0` compressed-swap device that `lsblk` reports as `type: "disk"` - confirmed live before assuming disk enumeration was as simple as filtering on `type`; both `zram*` and `loop*` name prefixes are excluded, since neither is ever real storage a media stack could live on.

**`identify_protected_devices()` is the hard safety rule, not just a UI warning** - resolves which physical disk(s) back `/`, `/boot`, and `/boot/efi` via `findmnt` (the same tool and the same `[/subvol]`-suffix handling `detect_media_redundancy()` already established for btrfs subvolumes - confirmed live: this machine's real root reports `/dev/nvme0n1p3[/root]`) walked back to its parent disk through `list_block_devices()`'s own `pkname`-linked tree. `plan_storage_layout()` calls this itself and refuses outright if any target device is in the set - there is no override flag anywhere in this codebase, by design.

**`plan_storage_layout()`'s returned `commands` list is the real argv a future execution step would run unchanged, not a simplified preview** - one device gets `mkfs`+`mount` directly; 2+ devices get a real `mdadm --create` step first, with the RAID level chosen by `_mdadm_level_for_device_count()` (RAID1 at exactly 2 devices, RAID5 at 3+ - an honest, simple default, not an attempt to guess the "best" level for every case) unless `raid_level` is passed explicitly, validated against mdadm's own real per-level device-count minimums (`_MDADM_MIN_DEVICES`, not invented). A device already carrying a filesystem or partition table is flagged in `already_has_data`/`warnings`, not silently overwritten in the description.

**`describe_storage_plan()` is the one shared renderer** - `vulcan storage plan` calls it today; a future TUI integration (deliberately not built in this pass - see below) would call the identical function rather than a second copy, the same "single source of truth for display text" role `format_port_conflicts()` already plays for port conflicts elsewhere in this codebase. Includes a real capacity-headroom recommendation (keep 10-15% free) - advisory text, not an enforced mechanism, since Linux has no per-directory quota without filesystem-specific project quotas, a materially bigger feature this pass doesn't take on.

**CLI-only, not wired into the TUI in this pass.** `vulcan storage report`/`vulcan storage plan` (`installer/cli.py`, a new `storage_app` sub-`Typer`, the first nested command group this codebase has needed) - deliberately kept out of the guided TUI's Main Menu. The TUI's whole design language is approachable/low-risk (see the Main Menu entry above); a "plan to erase your disk" entry point doesn't belong there ahead of Phase 2's real safety gates (typed-device-name confirmation, etc.) actually existing to back it up.

**Verified for real where it's actually safe to, honestly bounded where it isn't.** `list_block_devices()`/`identify_protected_devices()`/both CLI commands were run unmocked against this real machine's real hardware (one real NVMe disk, correctly excluding its own real `zram0`, correctly flagged as protected) - completely safe, since these only ever read. **Real execution-level verification (actually running the generated `mdadm`/`mkfs`/`mount` commands against loop-device-backed virtual disks, never real hardware) was scoped as part of the plan but not completed** - this environment has no passwordless sudo, confirmed live (`sudo -n true` prompts for a password) rather than assumed either way, and privileged loop-device commands weren't run without asking first. Flagged honestly as a real, open verification gap (see ROADMAP.md), the same treatment this project already gives ZFS detection and NVIDIA GPU passthrough - not claimed as more solid than it is. 23 new tests (16 `storage.py`, 7 CLI) mock `lsblk`/`findmnt` at realistic real-output shapes (the exact JSON this machine's own `lsblk -J` produced, not invented) rather than loose mocks.

## Testing conventions

- Mock at the **importing module's namespace**, not the source (`patch("installer.cli.detect_system", ...)`, not `patch("installer.detect.detect_system", ...)`) — standard `unittest.mock` behavior, but easy to get backwards.
- `tmp_path` (pytest fixture) for anything touching the real filesystem — never the real `stack/`/`backups/` directories relative to repo root, except inside the handful of deliberate real-infrastructure checks described below, which always clean up in a `finally`/explicit teardown.
- `installer/menu.sh` (the bash + whiptail front end, replacing the old Textual TUI - see its own section above) is tested by `tests/test_menu.bats`, run in CI via `bats tests/test_menu.bats` (Ubuntu's own `bats` package). Since there's no `Pilot`-equivalent automation for `whiptail`, every test replaces the real `whiptail` binary with a shell function (`export -f whiptail`) returning scripted answers on fd 3 (the same `3>&1 1>&2 2>&3` redirect trick `menu.sh`'s own dialogs use), sources the script, and asserts on the resulting argv/exit code - the bash equivalent of mocking a widget's return value. `menu.sh` itself has a `[[ "${BASH_SOURCE[0]}" == "${0}" ]]` guard so sourcing it for tests never triggers the real interactive Main Menu loop or the whiptail-presence check.
- **Real-infrastructure verification is load-bearing in this project's history, not optional polish.** Nearly every slice includes at least one check against this actual machine's real Docker, not just mocks: real containers started/stopped, real GPU passthrough confirmed via `docker exec` + `/dev/dri`, real generated compose files validated with `docker compose config`, a real `vulcan backup` archive inspected with `tarfile`. When adding a feature that touches Docker/the filesystem/real subprocess calls, a mocked test suite passing is necessary but not sufficient — look for what a real check would look like before considering the work done, and always clean up (`docker compose down`, `rm -rf` the scratch stack) immediately after.

## Code style

Heavy vertical spacing, matching the style established from the very first commit: each function argument on its own line in a multi-arg call, a blank line after `def ...():` before the body, blank lines between most statements. Very few docstrings (module-level explaining *why*, not function-level explaining *what*). New code should match whatever file it's editing.
