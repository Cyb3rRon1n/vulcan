An unrelated conflicting service now gets an interactive remap (type a new host port, applied and regenerated on the spot, validated against every other port already in use in the same stack) instead of a dead-end refusal; your own orphaned containers get a real one-confirm cleanup (`remove_orphaned_containers()` — container teardown only, deliberately not `uninstall_stack()`, since that would delete the *freshly-generated* `stack/` the current run just wrote). `resolve_ports()` reuses `generate.py`'s existing `_HOMEPAGE_PORTS` table rather than a second one, so a remap also fixes the Homepage tile/post-start-summary link, not just the compose file. - [x] **Shared `WEB_FACING_SERVICES` constant** — closes the drift risk between Homepage's tile groups and the Traefik template's per-service label blocks, previously two independent hand-maintained lists (the same class of staleness this project has hit before — the "17 known services" count going stale, twice). `WEB_FACING_SERVICES` (`generate.py`) is every service with its own routable web UI, including `traefik` and `homepage` themselves; each consumer derives its own view by excluding just itself (`- {"traefik"}` for the template's routed set, `- {"homepage"}` for Homepage's tile set), since neither routes/tiles itself the normal way. Not a template rewrite — the per-service Jinja blocks stay hand-written (deliberately, per this project's "reads like a normal hand-written compose file" principle), the constant only backs two new regression tests: one asserting `_HOMEPAGE_GROUPS`'s flattened membership matches, one parsing the real `docker-compose.yml.j2` for every `traefik.http.routers.<key>.rule=Host` line and asserting that set matches too — so a future service added to one list and forgotten in the other now fails CI instead of silently drifting.

- [x] **ARM64 emulation-based end-to-end run — the full 21-service heavy-tier stack, not a curated subset.** Closes the software half of the ARM64 gap below; real physical ARM64 hardware is still untested (see Next). Installed `qemu-user-static-aarch64` + `qemu-user-binfmt` (QEMU user-mode emulation, `binfmt_misc` registration) on the existing x86_64 Fedora dev machine — confirmed genuinely working, not just registered, via a `--platform linux/arm64 python:3.12-slim` container correctly reporting `aarch64` from `uname -m`. Generated the real, full non-interactive heavy-tier stack through the actual CLI (all 21 services at once, including Authelia, Traefik, Gluetun, and Tailscale — not a hand-picked easy subset). **A real methodology gotcha caught before trusting any result**: `docker compose pull` under `DOCKER_DEFAULT_PLATFORM=linux/arm64` silently kept already-cached `amd64` images instead of forcing a re-pull — caught via `docker image inspect`'s `.Architecture` field still reading `amd64` despite a fresh `LastTagTime`; switched to explicit `docker pull --platform linux/arm64 <image>` per image, which is reliable. All 20 unique images pulled clean with zero errors; 19 of 20 were confirmed genuinely executing real aarch64 code via a direct `uname -m`/binary-invocation check inside each container (the 20th, `watchtower`, has no shell to test with, but its Go binary ran and printed real `--help` output under the same `--platform linux/arm64`, confirming the binary itself executes). Then ran the real `docker compose up -d` under emulation: **18 of 21 services came up and stayed running/healthy** (`tailscale` failing on a placeholder auth key is expected, matching its own documented behavior). The 3 unexpected failures were each run down to a specific, verified root cause rather than left unexplained — two turned out to be real, architecture-independent Vulcan/upstream bugs surfaced incidentally by this exercise, not ARM64 problems (both fixed below); one is a genuine, still-open ARM64-emulation question. See Next.
- [x] **Authelia no longer fatal-crashes on start when no domain is configured — fixed and verified against a real container, not just reasoned about.** Found by the ARM64 run above: `write_stack()`'s own warning claimed "Authelia will start but do nothing useful" without Traefik/a domain, but it actually crash-looped (`session: domain config #1 (domain 'None'): option 'domain' is not a valid cookie domain`) — `templates/authelia-configuration.yml.j2` was rendering `config.domain` verbatim into the session cookie's `domain` field, producing a literal `'None'` whenever no domain was set. `render_authelia_configuration()` (`generate.py`) now takes `host_ip` and falls back the cookie domain to the real detected LAN IP (or `127.0.0.1` as a last resort) when no domain is configured — a real IP satisfies Authelia's own validation rule (needs a period or to be an IP) where `None` never could. **A second, related bug found only by testing the first fix against a real container, not assumed fixed from the log message alone**: the first attempt omitted `authelia_url` entirely when no domain existed, on the assumption it was optional — a live rerun immediately surfaced `option 'authelia_url' is required`, a second fatal error the log hadn't shown yet since the first one masked it. Fixed properly: `authelia_url` falls back to pointing at Authelia's own container port directly (`https://<ip>:9091`) rather than a fictional `authelia.<ip>` subdomain that wouldn't resolve to anything. Two new regression tests cover both fallback paths (real host IP, and loopback when even that's unavailable). **Verified against a real container, twice — once per bug found**: the fixed config was loaded into a real `authelia/authelia:latest` container with real generated secrets and a real `users_database.yml`; it now reports `Startup complete` and `Up ... (healthy)` instead of crash-looping, confirmed via `docker ps`/`docker logs`.
- [x] **`containrrr/watchtower:latest` no longer crash-loops against a modern Docker daemon — fixed and verified against a real container.** Found by the same ARM64 run: `client version 1.25 is too old. Minimum supported API version is 1.40`, followed by a nil-pointer panic in the image's own metrics-error-handling path (`pkg/metrics.NewMetric`) — confirmed independent of architecture by reproducing the identical crash running the same image natively on `amd64`, not an ARM64 problem. Root cause: the image's bundled Docker client defaults to a stale hardcoded API version instead of negotiating with the real daemon. `templates/docker-compose.yml.j2`'s `watchtower` service gained `DOCKER_API_VERSION=1.41` (Docker 20.10, released 2020 — comfortably clears this daemon's real 1.40 floor while staying compatible with older still-supported daemons; tested against `1.44` and `1.41` directly, both work, `1.41` chosen for the wider compatibility floor). **Verified against a real container, not assumed from the fix's plausibility**: without the env var, a real `docker run` reproduces the exact crash; with it, the identical container reports `Session done Failed=0 Scanned=1 Updated=0` and exits cleanly.

Pre-seeds `stack/config/dashy/conf.yml` once, same never-overwrite-a-hand-edit rule as Homepage's `services.yaml`/Decluttarr's `config.yaml`. `"dashy"` was added to `WEB_FACING_SERVICES` (gets its own Traefik routing label block) and to `_HOMEPAGE_GROUPS`'s Infrastructure group specifically so *Homepage* can tile Dashy when both are enabled — with an explicit self-exclusion in `render_dashy_config()`/`render_stack_summary()` so Dashy never tiles itself or double-lists itself. - [x] **`vulcan status`** — real per-container state (running/exited, health, published ports) for an already-generated stack, rounding out the lifecycle commands alongside `update`/`pull`/`backup`/`restore`/`uninstall`. No TUI screen, matching the existing precedent that `backup`/`restore`/`uninstall` are also CLI-only.

Verified via `docker compose config` against a real generated stack, including confirming `user: 1000:1000` actually resolves; a live container pull/start wasn't reachable in this environment (no Docker daemon here).
- [x] **Pre-install drive-readiness checklist.** A direct user request. Three real checks run once, right after the media path is created: a real write-then-delete probe (not a permission-bit read — a mount can look writable and still reject every write, e.g. a read-only remount or a full filesystem), free space against a real 10GB floor for Vulcan's own footprint (deliberately not a guess at the user's media-library size, which isn't Vulcan's call), and a same-filesystem-as-root check (`os.stat().st_dev`, no new subprocess dependency) flagging the well-known pitfall of a growing library sharing the OS's own disk. All three are advisory, never a hard block — same "observe, then let the user decide" principle as the existing drive-redundancy warning. `describe_drive_readiness()` is a single shared formatter both the CLI and TUI call, avoiding a second driftable copy of the wording. Real, unmocked tests cover the writable/low-space paths directly against `tmp_path`; the same-device check is mocked, since this environment has no second real filesystem to test a genuine cross-device case against.
- [x] **Repo hygiene: ruff lint in CI + Dependabot.** The project had no linter/formatter and no dependency-update automation at all. Added both. Ruff's rule set is deliberately narrow, not a preset: `E4, E7, E9, F, B, I, UP` (pycodestyle-error-subset, pyflakes, flake8-bugbear, isort, pyupgrade), picked by first trying `--select ALL` (4950 findings, rejected outright — dominated by rules this project's own CLAUDE.md documents as deliberate style choices: sparse docstrings, no forced type annotations, natural `assert` in tests, no trailing-comma convention) and then trying and dropping `C4` too (comprehension style — `C408` would have forced rewriting `dict(...)` calls in the test suite's widely-shared `make_system_info()` helpers for zero functional benefit). The narrow set found 16 real findings on first run — 14 auto-fixed cleanly (11 import-sort/grouping, 3 safe `datetime.timezone.utc`→`datetime.UTC` modernizations, since this project's floor is already `>=3.11`), and 2 genuine `flake8-bugbear` catches (`raise typer.Exit(...)` inside an `except OSError as error:` block in `installer/cli.py`, twice) fixed by hand with `from error` since `B904` isn't auto-fixable. Full suite re-run afterward (587 passed) to confirm the auto-fixes were behavior-preserving, not just syntactically clean. CI (`.github/workflows/ci.yml`) gained a separate `lint` job running `ruff check .` once against Python 3.12 — not matrix-wide, since lint findings don't vary by Python minor version and doubling the run would add cost with no signal. `.github/dependabot.yml` (new) tracks `pip` and `github-actions` on a weekly schedule, closing the other real gap in the same "repo hygiene" bullet.

## Deliberately out of scope

Recorded so these don't get relitigated as gaps later — each was considered and rejected for a real, documented reason.

- **Let's Encrypt / ACME automation for DNS providers other than Cloudflare.** The original "don't hardcode one DNS provider among dozens" reasoning held until a user specifically named Cloudflare - Cloudflare DNS-01 shipped (see above), but every other DNS provider Traefik/Lego support (Route53, DigitalOcean, etc.) stays genuinely out of scope until someone names one of those too. HTTP-01 (needs a port-forwarded public domain) also stays unimplemented - DNS-01 covers the real request that came in.
- **Traefik routing for qBittorrent when Gluetun is enabled.** Not a bug — a real Docker networking limitation: a container using `network_mode: "service:gluetun"` has no network identity of its own for Traefik's Docker provider to discover. Explained via a `write_stack()` warning instead of silently generating labels that would never route.
- **A daemon or scheduled mode.** Every command is on-demand (`./install`, `vulcan update`/`pull`/`backup`/etc.), matching the project's "observe, then act" design principle — Heavy tier's Watchtower already covers continuous background updates for anyone who wants that specific behavior.
