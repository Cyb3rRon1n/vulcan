Found and corrected a real wrong assumption before shipping: `docker ps --filter publish=<port>` looked like the right tool and produced a real false positive when tested - parsing the real `{{.Ports}}` field is what's actually reliable. Correctly targets `gluetun` as qBittorrent's hostname when Gluetun owns its network namespace. - [x] **Tailscale (private remote access) and Cloudflare DNS-01 (real Let's Encrypt certificates)** — a 19th real service (Tailscale, custom-mode only, `network_mode: host` so every host-published port becomes tailnet-reachable automatically with zero route-approval step) plus a Traefik TLS modifier (Cloudflare DNS-01, opt-in, `--cloudflare-dns`/`--cloudflare-email`), not a 20th service. Moved from `_MEDIUM_SERVICES` into `_LIGHT_SERVICES`, both defaults (`cli.py`/`tier_config_screen.py`) flipped to `True`; `previous["enabled_optional"]` still overrides on a regenerate, so an existing deployment that explicitly disabled it stays disabled. - [x] **Port-conflict override** — step two of the three-part plan, turning the diagnosis (shipped above) into an actual fix. An unrelated conflicting service now gets an interactive remap (type a new host port, applied and regenerated on the spot, validated against every other port already in use in the same stack) instead of a dead-end refusal; your own orphaned containers get a real one-confirm cleanup (`remove_orphaned_containers()` — container teardown only, deliberately not `uninstall_stack()`, since that would delete the *freshly-generated* `stack/` the current run just wrote). `resolve_ports()` reuses `generate.py`'s existing `_HOMEPAGE_PORTS` table rather than a second one, so a remap also fixes the Homepage tile/post-start-summary link, not just the compose file. TUI gets the auto-cleanup button only (real, narrower scope, matching this project's own established "CLI has the fuller text" precedent) — full remap stays a `--plain` feature. A real bug found only by reproducing the exact orphan scenario against real Docker (not any mocked test): the first version asked once per conflicting port even though one cleanup call fixes every port from the same leftover stack at once — fixed to ask once per pass. Verified against real Docker twice: a real port squatter remapped and started successfully at the new port, and a real reproduction of the "`stack/` deleted while containers kept running" scenario correctly diagnosed and cleaned up in one confirm.
- [x] **Shared `WEB_FACING_SERVICES` constant** — closes the drift risk between Homepage's tile groups and the Traefik template's per-service label blocks, previously two independent hand-maintained lists (the same class of staleness this project has hit before — the "17 known services" count going stale, twice). `WEB_FACING_SERVICES` (`generate.py`) is every service with its own routable web UI, including `traefik` and `homepage` themselves; each consumer derives its own view by excluding just itself (`- {"traefik"}` for the template's routed set, `- {"homepage"}` for Homepage's tile set), since neither routes/tiles itself the normal way. Not a template rewrite — the per-service Jinja blocks stay hand-written (deliberately, per this project's "reads like a normal hand-written compose file" principle), the constant only backs two new regression tests: one asserting `_HOMEPAGE_GROUPS`'s flattened membership matches, one parsing the real `docker-compose.yml.j2` for every `traefik.http.routers.<key>.rule=Host` line and asserting that set matches too — so a future service added to one list and forgotten in the other now fails CI instead of silently drifting.
- [x] **Interactive port remapping in the TUI** — closes the last real gap between the CLI's `--plain` remap flow and `ReviewScreen`: a genuinely unrelated conflicting service now gets a "Remap Ports" button, dynamically-mounted `Input` rows (one per remappable conflicting port), and an "Apply Remap" that regenerates and retries the start — no more "rerun with `vulcan --plain`" dead end. A real, reproduced layout bug found along the way, not just reasoned about: with 3+ simultaneous conflicts, the dynamically-mounted rows pushed Apply/Cancel below the 80x24 test viewport into a genuine `OutOfBounds` failure — the same class of bug `TierConfigScreen` hit before (see below). Fixed by making `ReviewScreen`'s root container a real `VerticalScroll` (dropping `align: center middle`, which fought a scrollable root) instead of trying to fit unbounded conflict counts into a fixed budget — the correct fix given the roadmap's own prediction that "already-tight layout budget" was the reason this was deferred. Verified for real: a 3-conflict scenario is reproduced in `tests/test_tui.py` scrolling each target into view before clicking, the same thing a real user would need to do to see off-screen content in the first place.
- [x] **ARM64 emulation-based end-to-end run — the full 21-service heavy-tier stack, not a curated subset.** Closes the software half of the ARM64 gap below; real physical ARM64 hardware is still untested (see Next). Installed `qemu-user-static-aarch64` + `qemu-user-binfmt` (QEMU user-mode emulation, `binfmt_misc` registration) on the existing x86_64 Fedora dev machine — confirmed genuinely working, not just registered, via a `--platform linux/arm64 python:3.12-slim` container correctly reporting `aarch64` from `uname -m`. Generated the real, full non-interactive heavy-tier stack through the actual CLI (all 21 services at once, including Authelia, Traefik, Gluetun, and Tailscale — not a hand-picked easy subset). **A real methodology gotcha caught before trusting any result**: `docker compose pull` under `DOCKER_DEFAULT_PLATFORM=linux/arm64` silently kept already-cached `amd64` images instead of forcing a re-pull — caught via `docker image inspect`'s `.Architecture` field still reading `amd64` despite a fresh `LastTagTime`; switched to explicit `docker pull --platform linux/arm64 <image>` per image, which is reliable. All 20 unique images pulled clean with zero errors; 19 of 20 were confirmed genuinely executing real aarch64 code via a direct `uname -m`/binary-invocation check inside each container (the 20th, `watchtower`, has no shell to test with, but its Go binary ran and printed real `--help` output under the same `--platform linux/arm64`, confirming the binary itself executes). Then ran the real `docker compose up -d` under emulation: **18 of 21 services came up and stayed running/healthy** (`tailscale` failing on a placeholder auth key is expected, matching its own documented behavior). The 3 unexpected failures were each run down to a specific, verified root cause rather than left unexplained — two turned out to be real, architecture-independent Vulcan/upstream bugs surfaced incidentally by this exercise, not ARM64 problems (both fixed below); one is a genuine, still-open ARM64-emulation question. See Next.
- [x] **Authelia no longer fatal-crashes on start when no domain is configured — fixed and verified against a real container, not just reasoned about.** Found by the ARM64 run above: `write_stack()`'s own warning claimed "Authelia will start but do nothing useful" without Traefik/a domain, but it actually crash-looped (`session: domain config #1 (domain 'None'): option 'domain' is not a valid cookie domain`) — `templates/authelia-configuration.yml.j2` was rendering `config.domain` verbatim into the session cookie's `domain` field, producing a literal `'None'` whenever no domain was set. `render_authelia_configuration()` (`generate.py`) now takes `host_ip` and falls back the cookie domain to the real detected LAN IP (or `127.0.0.1` as a last resort) when no domain is configured — a real IP satisfies Authelia's own validation rule (needs a period or to be an IP) where `None` never could. **A second, related bug found only by testing the first fix against a real container, not assumed fixed from the log message alone**: the first attempt omitted `authelia_url` entirely when no domain existed, on the assumption it was optional — a live rerun immediately surfaced `option 'authelia_url' is required`, a second fatal error the log hadn't shown yet since the first one masked it. Fixed properly: `authelia_url` falls back to pointing at Authelia's own container port directly (`https://<ip>:9091`) rather than a fictional `authelia.<ip>` subdomain that wouldn't resolve to anything. Two new regression tests cover both fallback paths (real host IP, and loopback when even that's unavailable). **Verified against a real container, twice — once per bug found**: the fixed config was loaded into a real `authelia/authelia:latest` container with real generated secrets and a real `users_database.yml`; it now reports `Startup complete` and `Up ... (healthy)` instead of crash-looping, confirmed via `docker ps`/`docker logs`.
- [x] **`containrrr/watchtower:latest` no longer crash-loops against a modern Docker daemon — fixed and verified against a real container.** Found by the same ARM64 run: `client version 1.25 is too old. Minimum supported API version is 1.40`, followed by a nil-pointer panic in the image's own metrics-error-handling path (`pkg/metrics.NewMetric`) — confirmed independent of architecture by reproducing the identical crash running the same image natively on `amd64`, not an ARM64 problem. Root cause: the image's bundled Docker client defaults to a stale hardcoded API version instead of negotiating with the real daemon. `templates/docker-compose.yml.j2`'s `watchtower` service gained `DOCKER_API_VERSION=1.41` (Docker 20.10, released 2020 — comfortably clears this daemon's real 1.40 floor while staying compatible with older still-supported daemons; tested against `1.44` and `1.41` directly, both work, `1.41` chosen for the wider compatibility floor). **Verified against a real container, not assumed from the fix's plausibility**: without the env var, a real `docker run` reproduces the exact crash; with it, the identical container reports `Session done Failed=0 Scanned=1 Updated=0` and exits cleanly.

## Next

- [ ] **A real end-to-end run on actual physical ARM64 hardware.** Emulation-based verification (via QEMU user-mode, see Shipped above) is now done and largely clean — 18 of 21 services genuinely run under `linux/arm64`, and the two real bugs it surfaced are fixed (see Shipped). What's left needs real hardware, not more emulation: whether `gluetun`'s emulation-specific failure (below) is a QEMU artifact or a genuine ARM64 problem, plus the `detect_cpu()`/`detect_gpu()` gaps below — emulation can't validate either, since the host kernel and `/proc/cpuinfo` stay x86_64 regardless of which architecture the container believes it's running as.
- [ ] **`gluetun` fails to start under ARM64 QEMU emulation** — `ERROR creating iptables firewall: no iptables supported found`, both `iptables-legacy` (`Table does not exist (do you need to insmod?)`) and `iptables-nft`/`nft` (`Protocol not supported`) fail during its own firewall init, and the container exits. **Confirmed emulation-specific, not a general ARM64-readiness or Vulcan-config problem**: the identical image started cleanly past this exact step on native `amd64` (same host, same kernel, `--platform linux/amd64`) — it got as far as a real VPN-config error instead. Very likely a known class of QEMU user-mode limitation (netlink/nftables syscalls not translating correctly under `qemu-aarch64`), but genuinely unconfirmed without real ARM64 hardware to rule that in or out either way.
- [ ] **`detect_cpu()`'s `cpu_model` parsing is x86-only.** It looks for a `"model name"` line in `/proc/cpuinfo`; real ARM64 Linux typically exposes `CPU implementer`/`CPU part` instead, so `cpu_model` will likely read as unknown on real ARM hardware. Not a crash (already handled as "not present"), but a known display gap to fix once real ARM hardware is available to verify against.
- [ ] **`detect_gpu()` has no ARM SBC-style detection** (e.g. a Raspberry Pi's VideoCore/V4L2 stack) — falls back cleanly to software-only Jellyfin transcoding today, but hardware transcoding on real ARM SBCs was never in scope.
- [ ] **Watch for a real stable Readarr release.** Currently pinned to `0.4.19-nightly` (over a year stale as of this writing) because it's the only tag LinuxServer publishes that actually works — re-pin once a real `:latest`-equivalent exists. Re-checked 2026-08-07: still no `:latest` tag on Docker Hub, and every upstream `Readarr/Readarr` GitHub release back through `v0.4.9` is still flagged prerelease — nothing changed, no action needed yet.

## Deliberately out of scope

Recorded so these don't get relitigated as gaps later — each was considered and rejected for a real, documented reason.

- **Let's Encrypt / ACME automation for DNS providers other than Cloudflare.** The original "don't hardcode one DNS provider among dozens" reasoning held until a user specifically named Cloudflare - Cloudflare DNS-01 shipped (see above), but every other DNS provider Traefik/Lego support (Route53, DigitalOcean, etc.) stays genuinely out of scope until someone names one of those too. HTTP-01 (needs a port-forwarded public domain) also stays unimplemented - DNS-01 covers the real request that came in.
- **Traefik routing for qBittorrent when Gluetun is enabled.** Not a bug — a real Docker networking limitation: a container using `network_mode: "service:gluetun"` has no network identity of its own for Traefik's Docker provider to discover. Explained via a `write_stack()` warning instead of silently generating labels that would never route.
- **A daemon or scheduled mode.** Every command is on-demand (`./install`, `vulcan update`/`pull`/`backup`/etc.), matching the project's "observe, then act" design principle — Heavy tier's Watchtower already covers continuous background updates for anyone who wants that specific behavior.
