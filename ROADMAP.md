- [x] **`security_opt: no-new-privileges:true` on every one of the 28 services**, inspired by [Osmantic/ODS](https://github.com/Osmantic/ODS) applying the same flag broadly across its own compose. `no-new-privileges` only blocks a process from gaining *new* privileges at exec time (e.g. via a setuid binary) — it doesn't touch capabilities a container already has via `cap_add`/`network_mode`, so it's safe even for `gluetun` (`NET_ADMIN`), `tailscale` (`NET_ADMIN`/`NET_RAW`, host networking), and `netdata` (`SYS_PTRACE`/`SYS_ADMIN`, host networking) — confirmed by rendering every service (a full `custom_services` set covering all 28) and parsing the real result as YAML, not just grepping the template. `netdata` already had its own `security_opt` (`apparmor:unconfined`, needed for its host-monitoring access) — extended to a two-entry list rather than overwritten, with a regression-lock test guarding against a future edit silently clobbering it back to one entry. `cap_drop: ALL` (also common in ODS's own compose) was deliberately **not** attempted here — dropping every capability risks breaking a `linuxserver.io` image's `s6-overlay` init (which needs several capabilities during its root-to-PUID/PGID handoff) or another image's own root-level setup step, and this dev environment has no Docker to verify that per-image, so it would have been an unverified claim. Two new tests (`tests/test_generate.py`) confirm every rendered service and the netdata special case; full suite still 621/626 passing (5 pre-existing, unrelated failures, confirmed via `git stash` before this change).
- [x] **Storage teardown/reformat** — `plan_storage_teardown(mount_point)`/`apply_storage_teardown(plan, confirm_wipe)` in `storage.py`, mirroring `plan_storage_layout()`/`apply_storage_layout()` in reverse: unmount, `mdadm --stop` + `--zero-superblock` on every member if it's a RAID array (member paths read via mdadm's own `--detail --export`, the script-stable interface, not the human `--detail` table), `wipefs -a` on the array and each member, then remove the real `/etc/fstab` line (read back from the actual file, not reconstructed, so a hand-edited line still matches) — so `list_blank_unprotected_devices()` sees the member device(s) as blank again. Protected devices (backing `/`/`/boot`) are refused with no override, same hard rule `plan_storage_layout()` already enforces. `apply_storage_teardown()` mirrors `apply_storage_layout()`'s idempotency model too: re-checks real state before each step (an already-unmounted mount point or already-stopped array skips that one step and continues, so a re-run after a partial failure resumes instead of erroring), and never runs anything without `confirm_wipe=True` — unconditional here, unlike `apply_storage_layout()`'s gate which only activates when a target device already has non-blank data, since a teardown has no "safe, nothing-to-lose" case the way provisioning does. New `vulcan storage teardown --mount-point` CLI command, with a stronger confirmation bar than `storage apply`'s: typed-mount-point match in interactive mode (matching `apply`'s own typed-device-list gate) plus a separate final yesno, versus `apply`'s single yesno. `menu.sh` gained a "Reset Media Storage" Main Menu item shown only when `BLANK_STORAGE_DEVICES` is empty and `STORAGE_MOUNT` is set (the one deliberate exception to this menu's "every item always shown" rule, agreed 2026-08-17 — a teardown is narrow and destructive enough that a static always-shown label couldn't carry the same "doesn't apply yet" context Media Storage Setup's own empty-state msgbox gives) — `main_menu()`'s loop now calls `refresh_detect` on every redraw so that item's visibility reflects state changes made from the same menu session, not just what was true on entry. 18 new Python tests (`tests/test_storage.py`, `tests/test_cli.py`) + 6 new bats tests (`tests/test_menu.bats`) — full suite 655 passing, 32/32 bats. - [x] **Real domain-routing verification: 4 more bugs, whole routed stack was 404/403** (2026-09-03) — with a real domain (`--domain <domain>`) + Cloudflare Tunnel on the homelab, every routed service was unreachable. Four independent causes: (1) **crowdsec** carries only the bouncer *middleware* labels (no router, no port); Traefik's docker provider still tries to build a service for it, fails (`service crowdsec-<project> error: port is missing`) and **discards the whole container's config** — so `crowdsec@docker` never registers and every router 404s on `middleware ... does not exist`. Fix: a never-routed `traefik.http.services.crowdsec.loadbalancer.server.port=8080` (its real LAPI port). (2) **vaultwarden** defines two services on one container (main + websocket); the main router didn't name its service, so Traefik "cannot be linked automatically with multiple Services" and dropped the route — added `traefik.http.routers.vaultwarden.service=vaultwarden`. (3) **`vulcan build --domain` on a re-run didn't regenerate `config/authelia/configuration.yml`** (it was `write-if-absent`), so Authelia kept the old session-cookie domain and rejected every forward-auth request (`no configured session cookie domain matches the url`). Now regenerated every build, like `docker-compose.yml`; `users_database.yml` + secrets stay guarded.
