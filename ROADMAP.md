- [x] **Port-conflict override** — step two of the three-part plan, turning the diagnosis (shipped above) into an actual fix. An unrelated conflicting service now gets an interactive remap (type a new host port, applied and regenerated on the spot, validated against every other port already in use in the same stack) instead of a dead-end refusal; your own orphaned containers get a real one-confirm cleanup (`remove_orphaned_containers()` — container teardown only, deliberately not `uninstall_stack()`, since that would delete the *freshly-generated* `stack/` the current run just wrote). `resolve_ports()` reuses `generate.py`'s existing `_HOMEPAGE_PORTS` table rather than a second one, so a remap also fixes the Homepage tile/post-start-summary link, not just the compose file. Not a template rewrite — the per-service Jinja blocks stay hand-written (deliberately, per this project's "reads like a normal hand-written compose file" principle), the constant only backs two new regression tests: one asserting `_HOMEPAGE_GROUPS`'s flattened membership matches, one parsing the real `docker-compose.yml.j2` for every `traefik.http.routers.<key>.rule=Host` line and asserting that set matches too — so a future service added to one list and forgotten in the other now fails CI instead of silently drifting.

Installed `qemu-user-static-aarch64` + `qemu-user-binfmt` (QEMU user-mode emulation, `binfmt_misc` registration) on the existing x86_64 Fedora dev machine — confirmed genuinely working, not just registered, via a `--platform linux/arm64 python:3.12-slim` container correctly reporting `aarch64` from `uname -m`. Generated the real, full non-interactive heavy-tier stack through the actual CLI (all 21 services at once, including Authelia, Traefik, Gluetun, and Tailscale — not a hand-picked easy subset). **A real methodology gotcha caught before trusting any result**: `docker compose pull` under `DOCKER_DEFAULT_PLATFORM=linux/arm64` silently kept already-cached `amd64` images instead of forcing a re-pull — caught via `docker image inspect`'s `.Architecture` field still reading `amd64` despite a fresh `LastTagTime`; switched to explicit `docker pull --platform linux/arm64 <image>` per image, which is reliable. All 20 unique images pulled clean with zero errors; 19 of 20 were confirmed genuinely executing real aarch64 code via a direct `uname -m`/binary-invocation check inside each container (the 20th, `watchtower`, has no shell to test with, but its Go binary ran and printed real `--help` output under the same `--platform linux/arm64`, confirming the binary itself executes). Then ran the real `docker compose up -d` under emulation: **18 of 21 services came up and stayed running/healthy** (`tailscale` failing on a placeholder auth key is expected, matching its own documented behavior). The 3 unexpected failures were each run down to a specific, verified root cause rather than left unexplained — two turned out to be real, architecture-independent Vulcan/upstream bugs surfaced incidentally by this exercise, not ARM64 problems (both fixed below); one is a genuine, still-open ARM64-emulation question. See Next.
- [x] **Authelia no longer fatal-crashes on start when no domain is configured — fixed and verified against a real container, not just reasoned about.** Found by the ARM64 run above: `write_stack()`'s own warning claimed "Authelia will start but do nothing useful" without Traefik/a domain, but it actually crash-looped (`session: domain config #1 (domain 'None'): option 'domain' is not a valid cookie domain`) — `templates/authelia-configuration.yml.j2` was rendering `config.domain` verbatim into the session cookie's `domain` field, producing a literal `'None'` whenever no domain was set. `render_authelia_configuration()` (`generate.py`) now takes `host_ip` and falls back the cookie domain to the real detected LAN IP (or `127.0.0.1` as a last resort) when no domain is configured — a real IP satisfies Authelia's own validation rule (needs a period or to be an IP) where `None` never could. **A second, related bug found only by testing the first fix against a real container, not assumed fixed from the log message alone**: the first attempt omitted `authelia_url` entirely when no domain existed, on the assumption it was optional — a live rerun immediately surfaced `option 'authelia_url' is required`, a second fatal error the log hadn't shown yet since the first one masked it. Fixed properly: `authelia_url` falls back to pointing at Authelia's own container port directly (`https://<ip>:9091`) rather than a fictional `authelia.<ip>` subdomain that wouldn't resolve to anything. Two new regression tests cover both fallback paths (real host IP, and loopback when even that's unavailable). **Verified against a real container, twice — once per bug found**: the fixed config was loaded into a real `authelia/authelia:latest` container with real generated secrets and a real `users_database.yml`; it now reports `Startup complete` and `Up ... (healthy)` instead of crash-looping, confirmed via `docker ps`/`docker logs`.
- [x] **`containrrr/watchtower:latest` no longer crash-loops against a modern Docker daemon — fixed and verified against a real container.** Found by the same ARM64 run: `client version 1.25 is too old. Minimum supported API version is 1.40`, followed by a nil-pointer panic in the image's own metrics-error-handling path (`pkg/metrics.NewMetric`) — confirmed independent of architecture by reproducing the identical crash running the same image natively on `amd64`, not an ARM64 problem. Root cause: the image's bundled Docker client defaults to a stale hardcoded API version instead of negotiating with the real daemon. `templates/docker-compose.yml.j2`'s `watchtower` service gained `DOCKER_API_VERSION=1.41` (Docker 20.10, released 2020 — comfortably clears this daemon's real 1.40 floor while staying compatible with older still-supported daemons; tested against `1.44` and `1.41` directly, both work, `1.41` chosen for the wider compatibility floor). **Verified against a real container, not assumed from the fix's plausibility**: without the env var, a real `docker run` reproduces the exact crash; with it, the identical container reports `Session done Failed=0 Scanned=1 Updated=0` and exits cleanly.

- [x] **Docker install-assist now handles atomic/immutable hosts too, ported from the sibling Anvil project.** Anvil independently hit the exact gap this project's own `docker_setup.py` never covered - a real Bazzite (rpm-ostree/atomic) GPU host with no Docker and no `dnf install` path - built the fix there, live-verified it end to end against that real host (including two real bugs found only by running it, not from reasoning about the code), and it's now ported back here unchanged. `detect.py` gained `os_is_atomic` (`/run/ostree-booted` marker, checked before the plain-distro `install_plan_for` table since Bazzite/Kinoite still report `os_id="fedora"`); the atomic path adds Docker's real repo file and runs `rpm-ostree install docker-ce docker-ce-cli containerd.io docker-compose-plugin docker-buildx-plugin` (layered, not live - reports `needs_reboot: True`, both the CLI and `DockerReadyScreen` stop cleanly with real reboot instructions instead of pretending Docker is ready).
  - **The two real bugs Anvil found and fixed, both ported here unchanged** (full live-verification account in Anvil's own `CLAUDE.md`/`ROADMAP.md` "v0.9" entries): (1) `usermod -aG docker <user>` reports real success but silently writes nothing when the docker group was created by `systemd-sysusers` for a layered package and lives only in `/usr/lib/group` (the `altfiles` NSS source, never in `/etc/group`) - `add_user_to_docker_group()` now tries plain `usermod` first, verifies with a real functional check (`id -nG`, never trusted from the tool's own exit code), and falls back to a local merge-friendly `/etc/group` entry + `gpasswd` only when that check shows the plain path didn't actually work. (2) a plain `detect_docker()` re-check right after fixing group membership in the same process still inherits that process's own stale cached group list from login time - new `check_docker_ready(use_group_workaround=True)` re-verifies through the same `sg`-based workaround `run_docker_command()` already used only for the final start, now also used for this earlier re-check. Also closed a real, silently-swallowed gap this project's own `_ensure_docker_ready()` and `DockerReadyScreen` both had before this port: `add_user_to_docker_group()`'s result was never checked in either front end - both now check it and report a clear error if it fails, instead of silently proceeding to a readiness check that would just fail with no explanation.
  - **Honestly bounded, not overclaimed**: the atomic/`rpm-ostree` path itself has not been independently re-run against real hardware from *this* project - it's the identical code Anvil already live-verified end to end (fresh install, real reboot, the real `usermod`/`gpasswd` bug hit and fixed, a real `Docker is ready.`) against a real Bazzite host, ported unchanged rather than re-verified from scratch here. The non-atomic paths (`get.docker.com`, `pacman`) are this project's own pre-existing, already-real-verified code and needed no changes. 26 new/updated tests (`tests/test_docker_setup.py`, `tests/test_cli.py`, `tests/test_tui.py`) cover the ported logic; full suite (545 tests) re-run clean except two pre-existing, unrelated failures (`ServiceSelectionScreen`/Authelia auth-toggle tests, confirmed failing identically on unmodified `main` before this port - not something this change touched or caused).

- [x] **Three new services from a direct owner request (replicating and improving on a previous CasaOS-based homelab): MeTube, Downtify, and Netdata.** Tier-agnostic optional, like SABnzbd/Recyclarr/Decluttarr/Maintainerr.
  - **MeTube** (`ghcr.io/alexta69/metube`) - a paste-a-URL YouTube downloader with a real web UI, PUID/PGID support like every LSIO-style service here. Mounts `${MEDIA_PATH}/media/youtube:/downloads` - lands directly inside the media tree so Jellyfin can scan it once a library is pointed there (no automatic Jellyfin library creation - `write_stack()`'s warning names the exact one-time step).
  - **Downtify** (`ghcr.io/henriquesebastiao/downtify`) - the Spotify-downloader half of the same request, picked over the alternative that does support scheduled artist-tracking (`pjmeca/spotify-downloader`) for one real, deciding reason: Downtify needs **zero credentials** (it resolves track metadata by reading Spotify's own public embed pages, no API key or Premium account required - confirmed via its own docs, not assumed), while the alternative needs real Spotify API credentials and Spotify's recent policy change now requires the API app owner to have Premium. Matches this project's own "never make the user supply a secret it can't invent" principle. Mounts into `${MEDIA_PATH}/media/music/downtify` - nested inside the existing Music library path so Jellyfin picks it up with zero new library config, at one real, named cost: Lidarr (if enabled) may flag the subfolder as unmapped files on its own scans, cosmetic not destructive. **A real, honest gap found and documented, not hidden**: Downtify's image has no documented PUID/PGID support (unlike every other service here) - confirmed live, its own data file landed root-owned, not `PUID:PGID`-owned; `write_stack()`'s warning says so outright.
  - **Netdata** (`netdata/netdata:stable`) - real-time CPU/RAM/disk/network/temperature dashboards, matching the CasaOS system-monitor widget the owner had before. **Genuinely more invasive than anything else in this stack**, and treated that way deliberately, not glossed over: `network_mode: host`, `pid: host`, `SYS_PTRACE`/`SYS_ADMIN` capabilities, `apparmor:unconfined`, and read-only access to most of the host filesystem (`/`, `/proc`, `/sys`, `/etc/passwd`, `/var/log`) plus `/var/run/docker.sock` - the full official example config, not a trimmed-down guess. Unlike Gluetun's opt-out (defaults on) pattern, Netdata is deliberately opt-in with no default-on anywhere, and both the CLI confirm prompt and the TUI checkbox tooltip name the real host-access tradeoff explicitly before asking, not just in a post-generate warning. **Never routed through Traefik, on purpose, not an oversight**: `network_mode: host` means the container has no Docker-network identity for Traefik's provider to discover - the same real limitation qBittorrent+Gluetun already has - so it's deliberately excluded from `WEB_FACING_SERVICES` (which specifically means "gets Homepage tile AND Traefik routing") while still getting a real Homepage tile via a hand-written exception in `_service_href()` that always returns a direct `http://<host>:19999` link regardless of domain/Traefik state.
  - **Verified against real Docker, not just `docker compose config`** (though that passed clean too, exit 0, full stack with all three plus Homepage-private plus Traefik+domain): pulled and started all three for real. MeTube answered `200` (container reported `healthy`). Downtify answered `200`, and its root-owned data file was confirmed exactly as the warning describes. Netdata answered `200`, correctly recognized the real host (`fedora`) through its `/host/etc/os-release` mount, and correctly discovered and named its own container through the real `docker.sock` mount in its own logs - not a hypothetical, the exact capability the deep host access exists to provide.

## Deliberately out of scope

Recorded so these don't get relitigated as gaps later — each was considered and rejected for a real, documented reason.

- **Let's Encrypt / ACME automation for DNS providers other than Cloudflare.** The original "don't hardcode one DNS provider among dozens" reasoning held until a user specifically named Cloudflare - Cloudflare DNS-01 shipped (see above), but every other DNS provider Traefik/Lego support (Route53, DigitalOcean, etc.) stays genuinely out of scope until someone names one of those too. HTTP-01 (needs a port-forwarded public domain) also stays unimplemented - DNS-01 covers the real request that came in.
- **Traefik routing for qBittorrent when Gluetun is enabled.** Not a bug — a real Docker networking limitation: a container using `network_mode: "service:gluetun"` has no network identity of its own for Traefik's Docker provider to discover. Explained via a `write_stack()` warning instead of silently generating labels that would never route.
- **A daemon or scheduled mode.** Every command is on-demand (`./install`, `vulcan update`/`pull`/`backup`/etc.), matching the project's "observe, then act" design principle — Heavy tier's Watchtower already covers continuous background updates for anyone who wants that specific behavior.
