- [x] **`vulcan uninstall --prune-docker`** — opt-in flag to also run `docker system prune -a` after stack teardown, in both the plain CLI and the whiptail menu (own confirmation prompt, defaults to No); clearly scoped as whole-Docker-host, not vulcan-only, since `docker system prune -a` isn't container-scoped
- [x] **Cloudflare Tunnel (`cloudflared`)** — new custom-mode service, Heavy tier alongside Traefik/Authelia/CrowdSec/Tailscale, requires `traefik`. Points at Traefik as its single upstream via a new plain-HTTP, container-network-only entrypoint (`:8081`, no host port) rather than routing each service itself — inherits every existing router/TLS/Authelia/CrowdSec decision instead of duplicating it. New `TUNNEL_TOKEN` credential, preserved across regenerate, deliberately separate from `CF_DNS_API_TOKEN` (different Cloudflare product/permission scope). Removes the need to forward ports 80/443 from the router entirely; additive alongside the existing direct port-forward path, not a replacement. Real compose/env/test-suite change (28 services now, up from 27) — not yet verified against a live tunnel, see Next.
- [x] **`security_opt: no-new-privileges:true` on every one of the 28 services**, inspired by [Osmantic/ODS](https://github.com/Osmantic/ODS) applying the same flag broadly across its own compose. `no-new-privileges` only blocks a process from gaining *new* privileges at exec time (e.g. via a setuid binary) — it doesn't touch capabilities a container already has via `cap_add`/`network_mode`, so it's safe even for `gluetun` (`NET_ADMIN`), `tailscale` (`NET_ADMIN`/`NET_RAW`, host networking), and `netdata` (`SYS_PTRACE`/`SYS_ADMIN`, host networking) — confirmed by rendering every service (a full `custom_services` set covering all 28) and parsing the real result as YAML, not just grepping the template. `netdata` already had its own `security_opt` (`apparmor:unconfined`, needed for its host-monitoring access) — extended to a two-entry list rather than overwritten, with a regression-lock test guarding against a future edit silently clobbering it back to one entry. `cap_drop: ALL` (also common in ODS's own compose) was deliberately **not** attempted here — dropping every capability risks breaking a `linuxserver.io` image's `s6-overlay` init (which needs several capabilities during its root-to-PUID/PGID handoff) or another image's own root-level setup step, and this dev environment has no Docker to verify that per-image, so it would have been an unverified claim. Two new tests (`tests/test_generate.py`) confirm every rendered service and the netdata special case; full suite still 621/626 passing (5 pre-existing, unrelated failures, confirmed via `git stash` before this change).
- [x] **Storage teardown/reformat** — `plan_storage_teardown(mount_point)`/`apply_storage_teardown(plan, confirm_wipe)` in `storage.py`, mirroring `plan_storage_layout()`/`apply_storage_layout()` in reverse: unmount, `mdadm --stop` + `--zero-superblock` on every member if it's a RAID array (member paths read via mdadm's own `--detail --export`, the script-stable interface, not the human `--detail` table), `wipefs -a` on the array and each member, then remove the real `/etc/fstab` line (read back from the actual file, not reconstructed, so a hand-edited line still matches) — so `list_blank_unprotected_devices()` sees the member device(s) as blank again. Protected devices (backing `/`/`/boot`) are refused with no override, same hard rule `plan_storage_layout()` already enforces. `apply_storage_teardown()` mirrors `apply_storage_layout()`'s idempotency model too: re-checks real state before each step (an already-unmounted mount point or already-stopped array skips that one step and continues, so a re-run after a partial failure resumes instead of erroring), and never runs anything without `confirm_wipe=True` — unconditional here, unlike `apply_storage_layout()`'s gate which only activates when a target device already has non-blank data, since a teardown has no "safe, nothing-to-lose" case the way provisioning does. New `vulcan storage teardown --mount-point` CLI command, with a stronger confirmation bar than `storage apply`'s: typed-mount-point match in interactive mode (matching `apply`'s own typed-device-list gate) plus a separate final yesno, versus `apply`'s single yesno. `menu.sh` gained a "Reset Media Storage" Main Menu item shown only when `BLANK_STORAGE_DEVICES` is empty and `STORAGE_MOUNT` is set (the one deliberate exception to this menu's "every item always shown" rule, agreed 2026-08-17 — a teardown is narrow and destructive enough that a static always-shown label couldn't carry the same "doesn't apply yet" context Media Storage Setup's own empty-state msgbox gives) — `main_menu()`'s loop now calls `refresh_detect` on every redraw so that item's visibility reflects state changes made from the same menu session, not just what was true on entry. 18 new Python tests (`tests/test_storage.py`, `tests/test_cli.py`) + 6 new bats tests (`tests/test_menu.bats`) — full suite 655 passing, 32/32 bats. Real mdadm/wipefs execution against a live RAID array remains unverified against real hardware in this environment, the same honest bound `apply_storage_layout()`'s own mdadm path has always carried.
- [x] **Guided Setup output redesign** — real user feedback (2026-08-17), closed. The wall-of-text complaint had two real, separate causes, both fixed: (1) `run_install()`'s full 3-tier comparison (`tier_description()` for Light/Medium/Heavy) printed unconditionally, even in non-interactive mode where `--tier` had already decided it - now gated on `not non_interactive`, so it only shows when someone's actually choosing. (2) Everything else (detected hardware, "Docker is ready.", the Review block, per-service `!` warnings, "Stack is up" + service URLs + numbered setup order) now routes through a new `RunPanel.note()` method instead of a bare `console.print()` - a real no-op on `RunPanel` (suppressed while the live whiptail progress panel is showing) but still prints immediately via `_NoOpPanel.note()` for `--plain`/non-panel runs, so that experience is byte-identical to before. Detail isn't dropped, it's moved: `write_stack()` now persists its `warnings` list into `stack/.vulcan-state.json` (a second `save_state()` call once they're fully computed), and a new `vulcan install-summary` command re-derives detected hardware + chosen tier + those warnings + the setup order from saved state, plain text, the same "read saved state, don't recompute" pattern `vulcan urls` already established. `menu.sh`'s "Setup Complete" screen (both the started and not-yet-started branches) now embeds this output instead of the old generic landing-note text, replacing the redundant "which dashboard should I open" heuristic with the real numbered walkthrough. 664 pytest passing (was 655) + 33/33 bats (was 32), ruff clean.
- [x] **`cap_drop: ALL` on the 9 `linuxserver.io` images** (2026-08-22) — the "no Docker to verify" blocker this item carried was stale (same class of gap as the whiptail item's own 2026-08-21 correction below): Docker was confirmed live and reachable in this environment, so the real per-image research this item asked for was actually run, not deferred again. Methodology: `docker run --cap-drop=ALL` against each real image first (all 9 failed identically — `chown: Operation not permitted` on `/config` et al., then `s6-applyuidgid: fatal: unable to set supplementary group list`), then capabilities added back until clean. **All 9 converged on the identical minimal set**: `CHOWN`/`DAC_OVERRIDE`/`FOWNER` (the ownership fixup) and `SETGID`/`SETUID` (the actual root→PUID/PGID drop) — not a per-image variance the original "would need per-image research" framing left open as a possibility. Applied as `cap_drop: [ALL]` + that 5-entry `cap_add:` in `templates/docker-compose.yml.j2`, alongside the existing `no-new-privileges` block. **Verified at three levels, strongest to weakest**: (1) the real 9-service stack rendered from this exact template, brought up via a real `docker compose up -d`, all 9 containers reaching `Up`/0 restarts and returning real HTTP 200/302/303 from their actual web UIs; (2) `docker compose config --quiet` schema-validating the rendered file; (3) 2 new tests (`tests/test_generate.py`) locking the exact verified cap set for the 9 and a regression guard that the other 19 services never silently inherit it. Full suite 666/666, ruff clean. Only the linuxserver.io images were tested — the other 19 services' own capability needs remain unresearched, see Next.
- [x] **`cap_drop: ALL` on the remaining 19 services — all 28 now hardened** (2026-08-22). Same real methodology as the 9 above, extended to the rest: `docker run --cap-drop=ALL` against each real image, iterating capabilities back in until clean. Three shapes emerged, not one:
  - **12 services need zero added capabilities at all**: `downtify`, `vaultwarden`, `recyclarr`, `decluttarr`, `maintainerr`, `jellyseerr`, `flaresolverr`, `traefik`, `cloudflared`, `crowdsec`, `dashy`, `watchtower`. Notably `traefik` — confirmed via `docker inspect` (`CapDrop: [ALL], CapAdd: []`) and real listening sockets on `:80`/`:443` (`/proc/net/tcp` showing `0050`/`01BB` bound) — genuinely binds privileged ports under a fully-dropped capability set in this environment, a real measured result kept as-is rather than second-guessed with a defensive `NET_BIND_SERVICE` add that direct testing showed unnecessary.
  - **4 more converge on the same 5-capability set the 9 `linuxserver.io` images already established**: `metube`, `authelia`, `homepage`, `uptime-kuma` — same ownership-fixup + PUID/PGID-drop shape despite not being `linuxserver.io`-branded images.
  - **3 already had a real, narrow `cap_add` from before this pass** (`gluetun`: `NET_ADMIN`; `tailscale`: `NET_ADMIN`/`NET_RAW`) — both confirmed sufficient as-is under `cap_drop: ALL`, no widening needed. **`netdata`** (`SYS_PTRACE`/`SYS_ADMIN`) needed extending: the same ownership-fixup set plus `DAC_READ_SEARCH`, which its own `apps.plugin`/`debugfs.plugin` log wanting directly (`"should run with CAP_DAC_READ_SEARCH"`) — a real functionality gain, not just log noise, confirmed by that exact warning disappearing once added.
  - **A real, honest limit found in the longer verification pass, not smoothed over**: netdata's `apps.plugin` (per-process resource attribution) kept logging `setresuid(0, 0, 0) failed` even with `SETUID` granted — only surfaced once the full 28-service stack ran for several minutes, not in the shorter focused per-image checks. The core daemon, container health check, and every other collector work cleanly; this one optional collector stays degraded. Not chased further — the only fix beyond this is broader privilege than this pass's own goal, and netdata already degrades gracefully rather than crashing (documented directly in the template).
  - **Verified at the same three levels as the 9-image pass, at full scale**: a real 28-service stack (every service `custom_services` covers) rendered and brought up via `docker compose up -d` — 26 of 28 reached genuinely running/healthy state; the other 2 (`authelia`, `gluetun`) failed only on missing real secrets/VPN credentials this test environment doesn't have (same honest boundary as the project's other real-credential-gated items), with `qbittorrent` cascading from `gluetun` by design (`network_mode: service:gluetun`) — not a capability regression in either case, confirmed by inspecting each failure's actual log line. Two real test-harness artifacts hit and fixed along the way (an auto-vivified directory where a file was expected for `dashy`/`decluttarr`, and root-owned scratch config dirs for `maintainerr`/`recyclarr` that don't match those two images' direct-PUID `user:` directive) — both confirmed as environment setup gaps, not template bugs, by fixing each and re-verifying clean.
  - **4 new tests** (`tests/test_generate.py`, replacing the two 9-image-only tests from the entry above): one per capability shape (5-cap, zero-cap, the three special-cased services) plus a completeness lock asserting every one of the 28 services in `ALL_SERVICES` has `cap_drop: ALL` — a future service added without this would fail that test rather than silently ship unhardened. Full suite 668/668, ruff clean.
- [x] **Authelia RBAC** (2026-08-25) — role-based access control via Traefik's `forwardAuth` middleware: `admin` group sees every Traefik-routed service; `media` group is restricted to Jellyfin + Jellyseerr only (their native apps can't complete a browser-redirect login, so they remain outside Authelia). RBAC rules are generated per-service in `authelia-configuration.yml.j2` only when `--domain` is active (without routing there's nothing to protect); Jellyfin/Jellyseerr fall through to `default_policy: one_factor`. New `ADMIN_ONLY_SERVICES` frozenset in `generate.py` (18 management services); 2 new tests in `tests/test_generate.py` covering rule generation and no-rules-without-domain. Admin group name is `admin` (not `admins`).
- [x] **`--auth-users` multi-user support** (2026-08-25) — comma-separated `username:password:group` flag parsed and hashed by `_gather_generation_config()`, added to `GenerationConfig.auth_users` list, written into `users_database.yml` alongside the admin account. Groups validated as `admin` or `media`; passwords hashed via the existing `hash_authelia_password()` on each entry. Reviewed in the pre-start panel. Re-running never overwrites the admin account; additional users can also be added by hand-editing `users_database.yml`.
- [x] **`--dry-run`** (2026-08-25) — implies `--no-start --non-interactive --yes`: generates `stack/` with no Docker operations, prints service URLs, setup order, and Cloudflare/Authelia guidance. Dry-run-only output includes Authelia RBAC summary, `TUNNEL_TOKEN` setup instructions for cloudflared, and Cloudflare Access Zero Trust walkthrough. Tested on test machine (`sentinel@100.112.243.53`) via subprocess-based remote pytest (284/284 passing across generate, auth, tiers, services, detect suites).
- [x] **Cloudflare Access (Zero Trust) guidance** (2026-08-25) — post-install warning printed when both `cloudflared` and `traefik` with `--domain` are active: step-by-step instructions for setting up Cloudflare Access applications for Jellyfin/Jellyseerr, including email-based policies for family members. Complements Authelia's own RBAC by authenticating at the edge before traffic reaches the server.
- [x] **Jellyseerr REQUEST-only permissions guidance** (2026-08-25) — post-install warning when both `jellyseerr` and `authelia` are active, reminding admin to set Jellyseerr user permission to REQUEST-only (not ADMIN) for family members, with a link to the Jellyseerr settings page.

## Next

The following are genuine open items, not shipped:

- [ ] **aarch64/ARM end-to-end verification** — static readiness audit has been done (every referenced Docker image confirmed to publish a real `linux/arm64` manifest, both install paths confirmed architecture-agnostic, two real known gaps in CPU/GPU detection documented rather than hidden) but has never actually been run on real ARM hardware. Everything real-verified in this project's history has been on this one real x86_64 Fedora machine.
- [ ] **Real-infrastructure verification (real Docker containers, real compose files, live API calls)** — a mocked suite passing is considered necessary but not sufficient. Real-infrastructure verification is a project-wide value; this remains an open gap.
- [ ] **`whiptail` interactive testing** — `whiptail`/`bats`/passwordless `sudo`/internet access are all available in this environment as of 2026-08-21 (the earlier claim that none of them were was stale - confirmed directly, not assumed); `bats` itself is now used throughout `tests/test_menu.bats`. What's still genuinely unverified is real interactive TTY rendering/navigation - `bats`' own tests mock the `whiptail` binary as a shell function returning scripted answers (the same technique the old Textual TUI's `Pilot` gave for free), not a live terminal a `Pilot`-equivalent would drive. No such harness exists for whiptail/newt.
- [ ] **Real GUIX/GuixSD support** — not currently in scope; only x86_64/Fedora, Ubuntu/Debian/Raspbian, and Arch are tested/verified.
- [ ] **Tailscale plugin download for Traefik** — the Traefik plugin catalog itself returned `error: 500` in this dev environment against two plugin versions and the official `plugindemo` example. Strong evidence this is a Traefik-plugin-catalog-side issue, not a CrowdSec or Vulcan-specific misconfiguration, but genuinely unconfirmed whether it's environment-specific or a live upstream problem.
- [ ] **Cloudflare Tunnel: real-tunnel verification** — `cloudflared` (shipped below) has never been run against a live Cloudflare account/domain in this dev sandbox. The image, `--token` run form, and dashboard-managed Public Hostnames are confirmed real from Cloudflare's own docs; whether a wildcard Public Hostname is actually creatable from the dashboard UI (vs. needing the CLI/API) is not yet confirmed. Same class of gap as the ARM64 hardware verification above.
